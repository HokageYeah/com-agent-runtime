# 02-总体技术架构

## 一、架构结论

回忆录系统应拆成三层：

```text
情侣日记业务系统
  -> 管理关系、回忆录业务数据、权限、播放器接口

公共 Agent Runtime
  -> 管理 Agent 注册、计划、执行、评价、模型、工具、上下文、记忆、观测、重试

业务 Agent 定义
  -> MemoirAgent、CustomerSupportAgent、StudyAgent 等
```

回忆录是公共 Runtime 的第一个业务 Agent，不是 Runtime 本身。

## 二、推荐技术栈

OpenMAIC 的 TypeScript / AI SDK / LangGraph 路线是重要参考；如果公共 Agent Runtime 新启动为独立 Python 服务，则用 Python 等价栈落地，并保持 provider、tool、workflow、trace 等抽象不变。

| 层级 | 技术 | 说明 |
|---|---|---|
| 编排运行时 | LangGraph Python | 状态图、checkpoint、resume、interrupt、human-in-the-loop |
| Agent 组件 | LangChain Python | prompt、tool、parser、retriever、middleware、动态 Agent 能力 |
| 模型调用 | LiteLLM / Provider Adapter | 承接 AI SDK provider 抽象思想，支持结构化输出、fallback、成本记录 |
| 工具协议 | MCP SDK + HTTP Tool API | 外部工具走 MCP，业务内部工具走 HTTP Tool API |
| Schema | Pydantic / JSON Schema | Agent 输入输出、工具参数、模型结构化结果校验 |
| 任务与缓存 | Redis（可选增强） | 队列通知、进度缓存、限流；不作为 run 状态唯一事实源 |
| 运行数据 | PostgreSQL 推荐；复用 MySQL 时需实现同等事务/锁语义 | AgentRun、outbox、Step、ToolCall、Artifact、Checkpoint、lease/fencing |
| 观测评测 | OpenTelemetry + LangSmith 可选 | trace、debug、eval、成本分析 |
| 业务后端 | FastAPI | 情侣日记业务接口和工具 API |
| 前端 | uni-app | 回忆录列表、播放器、分享页 |

第一版必须选定一个权威运行数据库并冻结迁移方案。Redis 丢失或重复投递不能改变正确性；worker 仍以数据库中的 run 状态、outbox 和 fencing token 为准。

## 三、整体调用链

```text
解绑 / 拉黑完成
  -> 情侣日记后端创建 MemoryArchive
  -> 发布业务模板 baseline revision 0
  -> 冻结当前关系段 source manifest，并异步物化 MemorySnapshot
  -> MemoryAgentAdapter 创建 AgentRun
  -> ai-agent-runtime-service 加载 memoir_agent
  -> LangGraph 执行 MemoirAgent 工作流
     -> 调用 memory.get_snapshot
     -> 使用 LangChain prompt/parser 生成高光、章节、场景、动作
     -> 使用 Provider Adapter / LiteLLM ModelGateway 调用模型
     -> 通过 Guardrails 做隐私与情绪安全复核
     -> 调用 memory.publish_playback_document 原子发布完整作品 revision
     -> 调用 memory.enqueue_tts 创建媒体任务
  -> 情侣日记后端更新生成状态
  -> uni-app 播放器按 MemoryScene / MemoryAction 播放
```

## 四、OpenMAIC 映射关系

| OpenMAIC 概念 | 回忆录对应概念 | Agent Runtime 对应 |
|---|---|---|
| Stage | MemoryPlaybackDocument（Archive + Scenes + Actions + Media） | 最终 Artifact 引用；AgentRun 只是生成任务 |
| Scene Outline | MemoirChapterPlan | LangGraph 中间状态 |
| Scene | MemoryScene | AgentArtifact 引用 + 业务表 |
| Action | MemoryAction | AgentArtifact 引用 + 业务表 |
| Media generation | MemoryMediaAsset | 媒体工具或后续任务 |
| Generation pipeline | MemoirAgent Graph | LangGraph Workflow |
| Provider routing | ModelGateway | Provider Adapter / LiteLLM provider 适配 |
| Prompt files | Prompt Registry | LangChain PromptTemplate |
| Tool registry | ToolGateway | Native / HTTP / MCP 传输，外加 LangChain / AI SDK 框架适配 |
| Fallback | 模板卡 / 默认动作 | 节点级 fallback |

该表是概念映射，不代表直接复用 OpenMAIC 代码。建议为 Runtime 单独建立零业务依赖的契约包（Python Pydantic 模型 + 导出的 JSON Schema），承担类似 `@openmaic/dsl` 的稳定边界：

```text
Runtime Contract：AgentRun / Event / Tool / Artifact 的可序列化协议
  -> Runtime Core：计划、执行、恢复、策略、观测
     -> AgentPackage：MemoirAgent 等业务定义
        -> Business Adapter：情侣日记、客服、订单系统
```

`MemoryScene / MemoryAction` 仍属于情侣日记业务契约，不应塞进公共 Runtime Contract。Runtime 只把它们视为带 `artifact_type + artifact_schema_version` 的业务 Artifact。

## 五、模块边界

### 5.1 公共 Agent Runtime

|---|---|

| Planner | 生成或加载 AgentPlan，定义步骤、停止条件和降级策略 |
| Workflow Executor | 基于 LangGraph 执行固定流程 Agent |
| Agent Harness | 基于 LangChain createAgent 或 Runtime ToolLoopAgent 执行动态 Agent |
| Evaluator / Critic | 评价每步输出，决定通过、重试、降级或人工介入 |
| PolicyEngine | 执行 step/token/cost/tool 等硬限制 |
| ModelGateway | 模型路由、provider 适配、结构化输出、token 与成本 |
| PromptRegistry | prompt 模板、版本、变量、灰度、回滚 |
| ToolGateway | 统一 LangChain Tool、AI SDK Tool、MCP Tool、HTTP Business Tool，并按当前 authorization version 授权 |
| ContextManager | token 预算、摘要压缩、上下文拼装、脱敏、trusted instructions/untrusted content 隔离 |
| MemoryManager | Run Memory、Session Memory、Long-term Memory |
| Guardrails | schema、权限、敏感内容、工具副作用、业务规则 |
| ArtifactStore | 保存 Agent 结构化产物和过程产物 |
| Observability | AgentStep、ToolCall、Trace、错误、成本、评测 |
| PublicTracePolicy | 控制哪些 Agent 执行轨迹可以安全展示给前端 |
| AdmissionController | 按 caller/tenant/agent/provider 限制 held/queued/running，提供过载拒绝与 Retry-After |
| Runtime Operations | liveness/readiness、鉴权能力发现、共享持久化、worker draining 与优雅停机 |
| DataLifecycle | 私密数据 purge tombstone、privacy version 写屏障、保留期和删除审计 |

第一版不要做成巨型平台，但以下骨架必须完整：

| 能力 | 第一版要求 |
|---|---|
| AgentDefinition | 支持 `memoir_agent` 的版本化定义 |
| AgentPackage | 支持文件化注册业务 Agent |

| AgentPlan | 支持静态计划和停止条件 |
| AgentStep | 每个 LangGraph 节点记录状态、耗时、错误 |
| AgentToolCall | 记录工具名、输入摘要、输出摘要、耗时、错误 |
| AgentEvaluation | 记录关键步骤的评价结果 |
| AgentCheckpoint | 支持失败后从节点恢复 |
| Planner | 第一版支持 Workflow 静态计划 |
| Evaluator | 第一版支持 schema、引用、安全、完成度评价 |
| PolicyEngine | 支持 step/token/cost/tool 硬限制 |
| Workflow Executor | 支持 LangGraph workflow |
| ModelGateway | 支持 Provider Adapter / LiteLLM provider 路由和结构化输出 |
| PromptRegistry | prompt 有版本和输入输出 schema |
| ToolGateway | 支持 HTTP Business Tool，预留 MCP 适配 |
| Guardrails | schema、权限、敏感字段、回忆录情绪安全 |
| Observability | 基础 trace、日志、token、成本 |
| MemoirAgent | 完成回忆录基础生成闭环 |
| Atomic Publication | baseline revision 0、完整作品单事务发布、published_revision 指针切换 |
| Runtime Contract | API/Event/Tool/Artifact 使用版本化 JSON Schema，并有兼容性测试 |
| Worker Coordination | run 原子认领、lease/heartbeat、失联恢复、取消传播、同一 run 单写者 |
| Backpressure | 全局/租户/Agent/provider 队列与并发上限，拒绝无界排队 |
| Runtime Operations | 提供健康检查和能力发现；API/worker 共享权威数据库，不依赖临时磁盘完成长任务 |
| Package/Data Lifecycle | package 安全撤销、privacy purge 写屏障、outbox dead letter 与原事件重放 |
| Trust/Authorization Boundary | 不可信内容隔离、确定性语义校验、运行中授权复核和撤销传播 |

第一版默认运行限制需要固化为配置，而不是开发时临时决定：

| 参数 | 默认值 | 说明 |
|---|---:|---|
| `max_steps` | 16 | 单个 run 最多执行步骤 |
| `max_model_calls` | 8 | 单个 run 最多模型调用 |
| `max_tool_calls` | 20 | 单个 run 最多工具调用 |
| `max_run_seconds` | 300 | 单个 run 的活跃执行预算，不包含 held、queued 和 waiting_human |
| `max_auto_retry_per_step` | 2 | Runtime 自动执行时单个步骤最多重试 |
| `max_manual_run_retry_count` | 3 | 用户或后台手动重试 run 的上限 |
| `max_estimated_cost` | 2.0 | 单个 run 预估成本上限，具体币种由 Runtime 配置 |
| `signature_tolerance_seconds` | 300 | 服务间签名时间戳容忍窗口 |

## 七、二期能力

以下能力放到二期或更后：

| 能力 | 延后原因 |
|---|---|
| 完整 Agent 管理后台 | 第一版可用配置文件或数据库管理 |
| 多 Agent handoff / A2A | 回忆录首期不需要跨 Agent 协作 |
| 动态计划生成 | 第一版用静态 Workflow 计划即可 |
| LLM-as-judge | 第一版先做规则和 schema 评价 |
| 长期记忆向量库 | 回忆录不应默认保存私密长期记忆 |
| 复杂 RAG 平台 | 客服 Agent 接入时再建设知识库检索 |
| 代码沙箱 | 首期不执行任意代码 |
| 商业计费系统 | 先记录成本，后续再做计费 |
| 多租户市场 | 等第二个以上业务稳定接入后再平台化 |

## 九、数据一致性原则

1. 解绑时写入 `relationship_id`、`space_id`、`relationship_segment_no`。
2. 快照只读取当前关系段数据。
3. MemoirAgent 只读取 `MemorySnapshot`，不直接扫日记和赌局原表。
4. 用户删除回忆只作用于自己的 archive，但会递增 generation_epoch，并清理该 owner 的派生快照、作品和 Runtime 私密 payload。
5. 对方账号回忆记录独立存在。
6. 已正式删除、无权、被过滤的数据不得进入快照。
7. AgentRun 失败重试时默认复用原 snapshot，除非用户或后台明确触发重建快照。
8. Runtime 库与业务库不是同一事务边界，业务后端先保存 `MemoryAgentRunRef(status=pending_start)`，再创建 held AgentRun。
9. Runtime 返回 run_id 后，业务后端事务绑定 `run_id + active_run_id + generation_epoch`，随后幂等 start；create/start 任一步失败都由补偿任务复用各自 Idempotency-Key 恢复。
10. Runtime callback 失败时由 Runtime 保留事件并重试；业务后端仍可按 `run_id` 主动查询 Runtime 兜底。
11. 对账任务默认每 5 分钟扫描业务侧 pending_start、Runtime running 超时、callback 多次失败等不一致状态；同类对象连续 3 次修复失败后升级告警。
12. run 的可恢复执行必须区分 `execution_attempt`；节点恢复沿用同一 `run_id`，但每次重新认领都有新的 attempt 和 fencing token，旧 worker 的迟到写入必须被拒绝。
13. `MemoryPlaybackDocument/Scene/Action` 使用各自业务 schema version，播放器只消费其支持的版本；不支持的新版本必须迁移或拒绝，不能静默解析。
14. 交付语义是 at-least-once 执行 + 幂等副作用，不宣称 exactly-once。`memory.publish_playback_document` 是业务产物唯一发布入口。
15. archive 使用 `generation_epoch + active_run_id` 作为业务侧 fencing；删除、重建或新一轮生成后，旧 run 的 tool/callback 不得覆盖当前状态或作品指针。
16. 业务系统采用 held create -> 绑定 active_run_id -> idempotent start，避免 Runtime 在业务映射提交前开始执行。
17. `dispatch_state` 属于 AgentRun，并与业务执行 status 分离；Step、ToolCall、ModelUsage 都带 execution attempt，副作用逻辑幂等键不随 attempt 改变。
18. Runtime 的 API、worker、dispatcher 可独立扩缩，但必须共享数据库、outbox/队列和对象存储；无共享持久化的 serverless 临时磁盘不能承载 AgentRun 权威状态。
19. `max_run_seconds` 只累计活跃执行时间；held、queued、waiting_human 和最终 run deadline 使用独立 TTL。
20. 删除 Runtime 私密 payload 必须先写 privacy purge tombstone 并递增 privacy version；所有 Checkpoint/Artifact/临时结果写入使用条件校验，旧 worker 不得在清理后复活内容。
21. AgentPackage 的不可变 digest 保证可复现，`revoked` 状态提供安全优先的停止开关；被撤销 package 禁止 create/start/retry/resume。
22. run dispatch 和 callback 使用持久 outbox；投递失败进入 dead letter，重放复用原事件身份，业务系统通过幂等消费和主动查询兜底。
23. 日记、赌局、图片说明、RAG/Web Search 和工具结果都是不可信内容；模型只能返回候选结构和业务引用，代码负责 ID、归属、数量、时长、工具参数和 side effect 权限校验。
24. AgentRun 保存 `authorization_version`，Runtime 在新 execution attempt 以及每次模型、工具、callback 动作前按当前授权重新确认；撤销后不得自动切换 connector 或身份。
25. outbox dead letter 按类型恢复：callback 通过原事件重放和业务主动查询修复；run_dispatch 先重放，超过上限后把未认领 run 置为 `failed(DISPATCH_FAILED)`，不能永久 pending/queued。
