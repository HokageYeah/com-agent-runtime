## 1. 已知需求与本次目标

用户已确认：第二个 Agent 主要用于**业务数据问答，可能调用业务工具**。

本次优化希望实现：

- 代码按职责归属组织，能区分公共 Runtime、Agent 专属实现和业务系统实现。
- 接入 QA Agent 时，不继续向公共内核追加 Memoir 或 QA 专属分支。
- 复用已有运行治理能力，保持 Memoir 既有行为和版本兼容。
- 用真实的第二个 Agent 检验抽象，而不是先建设完整插件平台。

本稿暂以“只读业务查询”为 QA 首版范围；是否需要写操作、具体业务对象和工具尚未确定。**这是建议，不是用户已经确认的功能范围。**

本次不预设：微服务拆分、独立仓库、向量数据库、完整 MCP、多 Agent 协作、通用 Bash 或代码沙箱。流式输出、长期记忆和动态工具循环分别按实际需求决定。

## 2. 为什么现在需要优化

com 已有 Package、Run、Worker、模型与工具网关、预算、恢复、审计等公共能力，但部分公共模块仍承载第一业务 Memoir 的专属规则。

只有一个 Agent 时，这些固定规则可以降低实现成本；第二个业务问答 Agent 出现后，它需要不同的工作状态、工具参数、评价和成功判据。如果只复制现有 Runner 或移动目录，公共模块仍会持续修改，两个业务也容易互相影响。

因此建议的下一大块是：**公共 Runtime 解耦，并用业务问答 Agent 完成最小接入验证。**

这不是要求一次性重写工程。先处理阻碍第二个 Agent 的真实耦合，再根据代码变化频率决定是否继续整理公共目录。

## 3. 问题、原因与建议方案

以下是基于当前代码形成的证据线索，Claude Code 应复核调用者和测试后再下结论。

### 问题 1：Worker 的执行器选择绑定 Memoir

- **证据：**`app/worker.py::configured_executor`（约 387 行起）内部直接识别 `memoir_agent`，创建 MemoirNodeRunner 及媒体、音频依赖；其他情况走 BootstrapExecutor。
- **问题：**注册一个新 Package，不代表已经具备该 Agent 的真实执行器。
- **原因：**公共 Worker 的装配与首个业务的装配集中在同一处。
- **建议：**保留公共调度与 RunExecutor 接口，把具体 Agent 的依赖构造移入各自的 `bootstrap.py`，由部署内可信注册表选择工厂。
- **约束：**注册表由受信代码/部署控制，不接受调用者提供的 Python 路径，不动态执行任意插件；未知执行器明确拒绝，不表现为业务已成功执行。
- **验收：**Memoir 和 QA 分别取得正确执行器；新增业务无需修改公共执行流程；未知或被撤销的 Agent 保持受控失败。

### 问题 2：公共 AgentState 包含回忆录工作状态

- **证据：**`app/runtime/state.py::AgentState`（约 27 行起）含 snapshot、highlights、chapter_plan、scenes、actions、playback_document 等字段；工具输出目标也采用固定白名单。
- **问题：**QA 的问题、检索证据和回答不属于这套状态结构；持续添加字段会让公共状态成为所有业务字段的合集。
- **原因：**公共执行进度、内存工作数据及业务输出校验尚未充分分离。
- **建议：**公共部分只表达执行进度、受控错误、恢复元数据等；各 Agent 定义自己的强类型工作状态和结果写入规则，由可信工厂注入。
- **待审核：**采用泛型状态协议、受控状态工厂还是其他小接口，应通过两个 Agent 的实际使用比较后确定，不在本稿强制冻结。
- **约束：**不能用不受约束的 `dict[str, Any]` 替代现有安全检查；控制字段拒绝、字段类型校验和 checkpoint 白名单继续生效。Agent 工作状态不会因为类型可扩展就自动获得持久化权限。
- **验收：**两个 Agent 状态不会互相污染；工具不能覆盖身份、路由或执行代际；checkpoint 仍只保存项目允许的恢复信息。

### 问题 3：公共工具网关混合了业务绑定与公共发送能力

- **证据：**`app/runtime/tool_gateway.py` 中的固定 `memory.*` 注册、`build_tool_context`、`_validated_tool_context`，以及 Archive/Snapshot 专属参数校验。
- **问题：**QA 工具无法通过仅增加 manifest 完成接入；直接删除 Memoir 判断又会削弱已有约束。
- **原因：**HTTP 发送、签名、授权、幂等，与业务工具名称、参数映射及资源归属校验混在一起。
- **建议：**公共 Gateway 执行统一门禁与传输；Agent 模块提供受信工具绑定、参数映射和业务校验策略；工具服务端仍执行真实业务授权。
- **约束：**Package 只是声明，不能自行授予权限。身份、tenant、connector、endpoint、幂等键和审批上下文来自可信服务端状态。未知工具和未授权绑定继续拒绝。
- **验收：**QA 与 Memoir 各自只能使用获授权工具；伪造参数、跨资源访问、授权撤销和迟到结果仍被阻断。

### 问题 4：结构化解析、语义校验与评价含回忆录规则

- **证据：**`app/runtime/guardrails.py::MemoirGuardrails`、`app/runtime/evaluator.py::MemoirPlaybackEvaluator`、`app/runtime/semantic_validation.py`；`StructuredOutputParser` 当前会调用该语义校验器。
- **问题：**播放动作、场景数量、关系情绪等规则不应成为 QA 的默认验收标准；只移动文件仍可能保留公共解析器到业务校验器的依赖。
- **原因：**通用解析机制与业务正确性规则没有独立选择接口。
- **建议：**通用层保留解析、schema 和必要安全检查；Memoir 与 QA 分别提供语义校验、护栏及评价策略。
- **约束：**不因拆分而取消可信来源校验；QA 的引用优先使用受控来源标识，展示链接由可信系统解析，不能简单放开模型任意输出的 URL。
- **验收：**错误 JSON、未知引用及控制字段仍被拒绝；Memoir 规则完整回归，QA 使用自己的回答与证据标准。

### 问题 5：循环合并和 partial 判定仍带业务语义

- **证据：**`app/runtime/bounded_loop.py::merge_unique_scenes`，Executor 中的场景合并，以及 `publish_document` 成功后才允许部分降级的判断。`app/services/agent_run_service.py::_assert_partial_retryable` 也识别该发布节点名。
- **问题：**第二业务的合并键、核心产物及部分成功语义未必相同；只修改 Executor 会与 retry 判定不一致。
- **原因：**通用循环预算与业务产物合并、业务成功判据仍交织。
- **建议：**预算、逐轮门禁和停止机制留在公共层；合并规则、核心结果提交判定及 partial/retry 资格由受信业务策略提供，相关入口统一使用同一规则。
- **约束：**不能让模型声明“已成功”来解锁 partial；新策略不能绕过当前循环内副作用限制。QA 首版没有 partial 需求时，可以明确不启用，不为通用性强行增加。
- **验收：**部分成功与重试条件一致；恢复不会盲目重放已提交动作；旧 Memoir 包保持原行为。

### 问题 6：上下文预算和模型装配仍识别 Memoir 节点

- **证据：**`app/runtime/context_manager.py::_NODE_TOKEN_CAPS`，以及 Worker 的 Memoir 模型节点与路由装配。
- **问题：**QA 新节点需要新的预算与上下文策略；若继续在公共表中追加业务名，耦合会增长。
- **原因：**公共预算计算和业务节点配置尚未分离。
- **建议：**各 Agent 注册可信上下文策略；公共层统一取节点限制、模型窗口和 Run 剩余额度的交集。
- **约束：**未知节点或非法预算继续拒绝；配置只能收紧公共限制，不能由请求或模型扩大预算。可信指令与不可信资料仍分槽。
- **验收：**QA 上下文可用且受限；Memoir 原预算不变；超大资料、工具返回和失效授权均有对应行为。

### 问题 7：启动、历史业务实现与 Agent 运行实现需要区别处理

- **证据：**`app/main.py` 中的 memory adapter、cipher、media proxy 装配；`app/services/memoir/`、`app/models/memoir/`、业务路由及测试工厂中的相关依赖。
- **问题：**生产路由未暴露某业务，不代表启动依赖已完全分离；同时，仍在运行的 Agent 专属模块与已迁移的历史业务模块不能一起移动或删除。
- **原因：**迁移历史和首个业务接入在一个工程中留下了不同用途的代码。
- **建议：**先盘点消费者、生产与 dev/test 路径，再区分 Agent 实现、业务后端权威逻辑、兼容历史实现；按各自归属逐步隔离装配和目录。
- **约束：**不删除历史迁移或改写 Alembic 谱系；不因文件移动改变表、数据库所有权或密钥。当前某些命名带 MEMORY 的配置还可能承担公共 checkpoint 加密，重命名必须核验密文兼容和轮换方案。
- **验收：**纯 Runtime 启动不无意创建仅供旧业务路径使用的依赖；现有必要配置、恢复和 dev/test 验证入口保持兼容。

## 4. 职责归属原则

| 类型 | 目标归属 | 例子 |
| --- | --- | --- |
| 公共执行机制 | com 的公共 Runtime | Run、调度、lease、fencing、预算、调用审计、恢复、outbox |
| Agent 专属运行逻辑 | com 的具体 Agent 模块 | Prompt、上下文、工作状态、业务工具绑定、生成策略、评价、媒体协调 |
| 业务权威事实与业务权限 | 业务后端 | 用户、关系、Archive、会话消息、业务记录、可访问范围、最终业务产物 |
| 具体技术协议 | 通用适配模块或所属 Agent 内部 | 通用模型协议适配；只有 Memoir 使用的音频服务可先留在 Memoir 模块 |
| 已迁出的历史实现 | 隔离保留的兼容/历史模块 | 仅用于迁移证据或 dev/test 联调的旧业务路由和服务 |

**移动代码不等于迁移数据所有权。** 例如 Memoir 专属音频协调移入 Agent 模块，其 Runtime 作业账本仍可归运行库；业务 Archive 仍归业务后端。

依赖方向建议：具体 Agent 使用公共接口；公共执行内核不导入具体 Agent；组装根可以认识具体实现并注入。允许共享的业务无关安全能力留在公共层，避免每个 Agent 复制一份。

## 5. 候选目标目录

下面用于审核职责，不要求第一阶段完成全部目录调整。`contracts/` 和既有版本包先保持原位置与内容；公共模块的深层归并可在真实调用关系清楚后再做。

```text
app/
  contracts/                    # 现有冻结对外契约
  runtime/
    runs/                       # 生命周期、调度、lease、outbox
    execution/                  # 编排、恢复、公共执行状态
    gateways/                   # 公共模型/工具门禁
    policies/                   # 授权、预算、取消、隐私
    persistence/                # 运行记录、checkpoint、安全产物
  agents/
    memoir_agent/
      runner.py
      state.py
      context.py
      tools.py
      evaluation.py
      guardrails.py
      media/
      bootstrap.py
      1.0.0/ ... 1.0.8/         # 现有包路径和内容先保持不变
    qa_agent/
      runner.py
      state.py
      context.py
      tools.py
      evaluation.py
      bootstrap.py
      1.0.0/                    # 新包，名称与版本待接入时确认
  adapters/                     # 只有真实共用的技术实现才集中
    providers/
    storage/
  bootstrap/                    # API/Worker 装配和可信工厂注册
```

第一批更适合做的是：抽离 Memoir 规则、建立必要接口、修正依赖并保留旧导入兼容。**不建议同时搬迁所有 services/models/schemas，也不要求把每个类包装成一个工厂。**

测试也按 public runtime、memoir、qa 的责任逐步区分，跨模块行为由集成测试验证；避免仅为目录整齐批量改写全部测试路径。

## 6. 业务数据问答 Agent 的建议链路

### 6.1 会话与运行分开

建议由业务后端拥有 Conversation、Turn、用户消息、最终回答和历史访问权限。QA Agent 在 com 中实现任务策略，公共 Runtime 管理执行过程。

一个会话包含多个 Turn；一次被接受的提问关联一个 Run，同一任务的物理重试不新建一条用户提问。消息重复提交、并发提问和重试需要稳定请求标识与版本策略。

若未来明确由 com 同时承载会话产品，需要单独设计会话模块、业务契约和数据生命周期；不能默认将原始问题和回答塞进现有 Run、Artifact、checkpoint 或 public trace。

### 6.2 首版流程建议

```text
业务后端认证并保存提问，生成 turn_id
  → 创建 qa_agent Run，传受控问题/历史引用
  → QA 获取当前获授权上下文
  → 形成受约束查询意图
  → 调用允许的只读业务工具
  → 生成回答及来源标识
  → 校验结构、引用与业务规则
  → 幂等提交回答给业务后端
  → 前端读取回答，callback 只通知安全状态
```

这是设计建议，当前没有声称存在这些 QA 工具或接口。工具名称、输入输出、快照/历史版本及提交契约需先确认。

只读指查询业务数据；把回答保存到业务后端仍是一次写操作，需要稳定幂等身份及提交结果对账。

### 6.3 工具与权限

- 模型只能提供候选查询条件，真实身份、tenant、资源范围和凭据从可信服务端状态取得。
- 业务工具服务端执行行级/对象级权限；检索应在授权范围内进行，不能先把全量敏感数据交给模型再过滤。
- 优先提供明确、受限的查询工具，不默认开放任意 SQL、数据库直连或通用命令执行。
- 回答引用必须来自当前获授权工具结果；权限撤销后，恢复与交付都要复核。
- 若将来增加业务修改操作，单独定义批准范围、执行前复核、幂等、取消及提交未知处理。

### 6.4 工作流、动态循环与流式输出

首版优先验证固定流程或受信工具路由；确有多步探索查询需求，再增加受控工具循环。

当前 `bounded_loop` 不是自由工具 Agent：循环体及副作用受静态定义约束。不能为了 QA 直接放开原循环能力；新执行策略须继承预算、授权、取消、审计与恢复机制。

流式输出另行定义事件、顺序、断线和最终回答提交语义。public trace 是安全进度，不是回答正文流；模型 Provider 的流式能力也不等于已具备产品端流式交付。

## 7. 分阶段建议

| 阶段 | 目标 | 交付与完成条件 |
| --- | --- | --- |
| A：核验与范围冻结 | 确认现状、QA 业务对象和只读工具范围 | 事实与旧 checklist 差异明确；契约、包 digest、关键行为有基线；待决策项列清楚 |
| B：最小解耦 | 抽离阻碍第二 Agent 的状态、工具、评价、预算及装配耦合 | 公共层通过可信接口使用策略，旧 Memoir 行为保持一致；目录移动与依赖调整相匹配 |
| C：QA 最小接入 | 跑通一个真实业务查询和回答交付 | 会话/Turn/Run 关联、权限、引用、费用、取消、幂等提交及恢复验收通过 |
| D：渐进归并 | 按维护价值整理公共目录与兼容历史路径 | 不改变数据所有权和迁移谱系；消费者逐步切换，必要旧导入保持兼容 |
| E：按需扩展 | 动态工具循环、压缩、流式和更多模型协议 | 需求与收益明确，独立契约和验证完成后再启用 |

阶段 B 与 C 应由同一个第二 Agent 的需求驱动，避免先做大规模抽象。微服务拆分应等待独立扩缩容、发布周期或隔离需求出现后再评估。

## 8. 不可退化的兼容边界

1. 旧 AgentPackage 路径、内容、digest 和已创建 Run 的版本保持兼容，不用覆盖旧包来升级策略。
2. 现有 API/Event/Tool/Artifact wire 先保持不变；新增能力若影响 wire，按契约规则评估版本及跨项目消费者。
3. lease/fencing、privacy/authorization version、取消、预算和发送前/返回后复核继续生效。
4. 工具 allowlist 和安全写入规则不因“可插拔”而变成调用方自声明权限。
5. 私密正文、完整 Prompt、原始模型输出、工具载荷、凭据和私有 URL 的禁存/禁日志边界保持不变；新增会话存储另行评审。
6. 不迁移、建表或删改既有业务库；必要的未来 Runtime schema 变更单独设计迁移与回退。
7. 历史代码和迁移不未经消费者核验就删除；配置命名调整不能意外破坏旧密文解密。
8. 交付保持至少一次与幂等效果的实际语义，不因增加工厂或工作流而宣称 exactly-once。

## 9. 实施阶段的验证与回退建议

本稿只提出验证要求，不表示下列检查已完成。

- **行为兼容：**Memoir 已有版本、旧包 digest、公共契约、创建/执行/取消/恢复/partial retry 的针对性回归。
- **双 Agent 隔离：**正确工厂、独立状态与工具权限、独立评价；未知 Agent、策略及工具拒绝。
- **业务问答：**授权内查询、越权拒绝、来源正确、无证据回答策略、长历史与超大返回处理。
- **一致性：**重复提问提交、回答已保存但响应丢失、旧 Worker 迟到、权限撤销、取消和费用耗尽。
- **依赖归属：**公共内核无具体 Agent 导入；旧导入兼容可验证，公共运行与测试入口不依赖无关业务装配。
- **持久化与观测：**私密内容不进入禁止区域，回答交付与状态通知分离。
- **门禁：**先运行最小相关测试，再按影响补契约、集成、真实并发与项目要求的 Ruff/Mypy 等检查；真实业务和 Provider 验收单独记录。

回退优先通过关闭新 Agent 的注册/入口恢复旧行为，旧 Memoir 包和路由保持可用。共享模块重构仍需具备可回退的发布单元；仅“关闭 QA”不能证明共享改动安全。禁止自动 `git reset`、清理工作区或修改运行中的 Run 锁定版本。
