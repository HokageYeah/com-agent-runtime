## 一、模块目标与边界

### 1.1 核心目标

AgentRuntime 第一版要跑通生产可用的公共 Agent 执行闭环：

```text
业务后端创建 AgentRun
  -> Runtime 加载 AgentPackage
  -> 校验输入与调用权限
  -> 生成静态 AgentPlan
  -> 执行 LangGraph Workflow
  -> 通过 ToolGateway 调业务工具
  -> 通过 ModelGateway 调模型
  -> 保存 Step / ToolCall / Evaluation / Checkpoint / Artifact
  -> 执行 Guardrails 和 PolicyEngine
  -> 成功、降级、重试或失败
  -> callback 通知业务系统
```

第一版必须支持：

- Agent 注册与版本化定义。
- AgentRun 创建、查询、重试、取消、最小人工确认和 privacy purge。
- `start_mode=held|auto`、幂等 start 和 held 超时回收。
- Runtime 入站调用身份校验，业务系统创建 AgentRun 必须签名。
- 后台任务队列和 Worker，HTTP 创建请求不得同步执行长任务。
- 数据库原子认领、lease、heartbeat、fencing token、execution attempt 和取消传播。
- dispatch/callback 持久 outbox、dead letter、原事件重放和对账终止策略。
- API/Event/Tool/Artifact 版本化 Contract、兼容性测试和鉴权能力发现。
- `AgentPackage` 不可变 digest、`active/deprecated/revoked` 生命周期和安全撤销。
- 全局、caller、tenant、Agent、provider 维度的 AdmissionController 与背压。
- 静态计划 `AgentPlan`。
- Workflow Agent 执行。
- HTTP Business Tool 调用。
- 模型网关与 prompt 版本管理。
- 节点级 checkpoint、resume、retry、fallback。
- 运行中评价、护栏和硬限制。
- 结构化产物、运行记录、token 与成本记录。
- Package/授权/Checkpoint/敏感控制操作的持久 RuntimeAuditEvent。
- callback 与可公开轨迹 `public_trace`。
- privacy purge tombstone/version、私密 payload 条件写和删除联动。
- trusted instructions / untrusted content 隔离、确定性语义校验和运行中授权复核。

### 1.2 模块边界

公共 AgentRuntime 负责“Agent 如何运行”，业务 Agent 负责“要完成什么业务目标”。

| 角色 | 职责 |
|---|---|
| AgentRuntime | 注册 Agent、执行计划、调用模型和工具、记录过程、恢复失败、评价结果、推送 callback |
| 业务 Agent | 定义 workflow、prompt、工具清单、guardrails、evals、ui trace 策略 |
| 情侣日记后端 | 管理回忆录业务数据、权限、密码、删除、播放器接口、业务工具 API |
| uni-app 前端 | 调情侣日记后端，不直连 Runtime，不展示 Runtime 完整 trace |

禁止事项：

- Runtime 不直接连接情侣日记业务数据库。
- Runtime 不绕过业务后端权限读取日记、赌局、关系数据。
- Runtime 不把情侣日记原始日记正文、完整赌局内容、密码、openid、token 作为长期权威业务副本。恢复所需私密状态只能进入加密、短 TTL、可清理的 Checkpoint 或临时 payload。
- Runtime 不把 prompt、模型原始输出、工具原始输入输出直接暴露给普通前端。
- Runtime 第一版不做 Agent 市场、管理后台、复杂 RAG、长期记忆、代码沙箱和商业计费。

### 1.3 第一版业务验证目标

第一版最初以 `memoir_agent@1.0.0` 验证公共抽象；当前仓库已通过
`1.0.1`–`1.0.4` 以新包扩展能力，不覆盖旧包：

```text
MemorySnapshot
  -> MemoirHighlights
  -> MemoirChapterPlan
  -> MemoryScene[] + MemoryAction[]
  -> optional media_manifest[]
  -> SafetyReport
  -> atomic MemoryPlaybackDocument publish
```

Runtime 通过情侣日记后端暴露的业务工具完成回忆录生成闭环：

- `memory.get_snapshot`
- `memory.publish_playback_document`
- Runtime 内部 `enqueue_media_tasks` 节点负责可选生成图片，它不是业务
  Tool；媒体总开关关闭或单张生成失败时安全降级为文字场景
- `memory.enqueue_tts` 仅保留历史/后续扩展契约，当前不是图片通道的执行入口

情侣日记后端在 archive 创建时发布 `revision=0` baseline。`MemoirAgent` 只能通过 `memory.publish_playback_document` 在一个业务事务中校验并写入完整 document/scenes/actions/`media_manifest`，再原子切换 `published_revision`。Runtime Artifact 只保留 schema version、摘要、digest 和业务资源引用，不形成第二套可播放副本。第一版即使关闭媒体能力，也必须显式提交空 `media_manifest`，不能通过省略字段改变发布契约。

业务后端必须在任一合法业务触发中先完成资格与范围判定，再冻结 `space_id + relationship_segment_no + snapshot_cutoff_at + source manifest/version` 并写 snapshot outbox。当前 Memoir 允许“绑定期用户手动选择范围”和“解绑后系统自动选择范围”两种触发，但日期、门槛、选日与作品所有权始终属于情侣日记后端；异步 materializer 只能按冻结清单生成加密 `MemorySnapshot`，不能读取执行时的可变最新集合。Runtime 只接收 `archive_id + snapshot_id + generation_epoch` 等定位参数，不负责解释或维护 source manifest，也不因触发类型改变公共 Run/Tool/callback 契约。

### 1.4 回忆录业务状态写入边界

| 状态或指针 | 合法值 | 唯一写入者 |
|---|---|---|
| `MemoryAgentRunRef.status` | `pending_start/pending/running/waiting_human/succeeded/failed/partial/cancelled` | callback adapter 与业务补偿任务；Runtime 的 `planning/evaluating` 折叠为 `running` |
| `MemoryArchive.content_status` | `baseline/pending/running/waiting_human/succeeded/failed/cancelled` | callback 只在尚未发布时推进非成功状态；原子发布工具独占 `succeeded` 提交，发布后 callback 不得降级 |
| `MemoryArchive.enhancement_status` | `disabled/pending/running/succeeded/partial/failed` | 业务媒体任务创建器与 media worker |
| `MemoryArchive.generation_status` | 由 content/enhancement 派生 | 不作为第三个持久写入源 |
| `MemoryArchive.published_revision` | archive 内已完整发布 revision | baseline 创建事务或 `memory.publish_playback_document` |

callback、作品发布工具和媒体 worker 不得交叉改写对方拥有的状态。`run_succeeded/partial_succeeded` callback 只确认已经由该 run 发布的 `content_status=succeeded + published_revision`，不能自行提交成功；缺少匹配 revision 时只更新 RunRef 审计，标记 `RECONCILIATION_NEEDED` 并继续提供 baseline/上一已发布版本。

播放契约冻结 Scene 类型 `cover/stats/diary_highlight/bet_highlight/image/milestone/summary`、安全级别 `normal/sensitive/fallback`，以及 Action 类型 `show_card/focus_image/type_text/hold/play_tts/transition`。MVP 生成器和播放器只启用 `show_card/type_text/hold/transition`；`focus_image/play_tts` 保留 schema 兼容并受媒体 capability 控制，关闭时必须跳过而不是猜测执行。

每个 AI 生成的 `MemoryScene` 必须持久化 `source_refs_json`，只引用当前 `snapshot_id` allowlist 内的 material/source ID。模型只能返回候选引用，Runtime 的确定性语义校验器负责归一化并拒绝未知、跨 owner、跨关系段或已删除引用；业务后端在发布事务中把校验后的引用与 Scene 一起保存，并提供按 source ref 反查受影响 archive/revision 的可索引路径。该路径可使用数据库支持的 JSON 索引或等价引用映射表，但必须与作品发布和清理保持一致，供原素材删除时发布脱敏新 revision 或切回 baseline。

跨工程目标契约固定为 Snapshot Tool v1：响应包含 `schema_version` 与 `materials[]`，每个 material 只包含 `material_type/source_ref/sanitized_payload`；`source_ref` 固定为 `<material_type>:<opaque-source-id>`，其中 `material_type` 只允许 `diary/completed_bet/handbook_note/matured_wish/bucket_list_completion`。当前 Runtime fixture/reader 中的 `bet_items`、`bets`、`bet:<id>` 仅是已实现旧格式证据，不是新 provider 的输出契约；兼容 reader 必须在建立可信 allowlist 前单向归一化为 `completed_bet:<id>`。同一 Snapshot 混用 `bet` 与 `completed_bet` 时 fail-closed，新 provider 与发布文档不得再产生旧格式引用。

## 二、Python 技术栈映射

原探索文档推荐 TypeScript Agent Runtime + LangGraph.js + LangChain.js + Vercel AI SDK。由于本轮明确新启动独立 Python 工程，采用以下等价迁移：

| 原设计能力 | Python 工程落地 |
|---|---|
| Runtime API | FastAPI |
| LangGraph.js workflow | LangGraph Python `StateGraph` |
| LangChain.js prompt/tool/parser | LangChain Python prompt、tool、parser、middleware |
| Vercel AI SDK provider 路由 | 当前使用自研 `ModelGateway` + 版本化 Provider Adapter；未引入 LiteLLM |
| Zod schema | Pydantic v2 + JSON Schema |
| Redis 共享流量控制 | 只用于模型并发 permit、RPM/TPM、共享冷却和熔断；当前不承担 Run 权威队列，不使用 Arq |
| MySQL / PostgreSQL 运行数据 | SQLAlchemy 2 + Alembic；development/test/production 默认 MySQL，PostgreSQL 用于隔离真实并发 harness；两者都以数据库保存 run、outbox、lease、fencing、checkpoint 和幂等记录 |
| 观测与评测 | 当前以权威数据库、安全日志和 RuntimeAuditEvent 落地；OpenTelemetry Collector / LangSmith 仍属后续可选集成 |
| MCP SDK | 第一版预留 transport，二期接 Python MCP Client / Server |

技术选择原则：

- 不自研完整 Agent loop，优先复用 LangGraph 的有状态编排。
- 不在业务服务中散落模型 provider 逻辑，统一进入 ModelGateway。
- Python 版本仍保留 OpenMAIC 的核心启发：素材 -> 大纲 -> 场景 -> 动作 -> 媒体 -> 播放器。
- 第一版追求完整骨架，不追求平台化后台。
- 创建 AgentRun 的 HTTP 请求只负责校验、落库、入队并返回 `run_id`；实际执行由 Runtime Worker 异步消费，避免网关超时中断长任务。
- API、worker、dispatcher、reconciler 共享同一个权威数据库；本地文件、进程内 Map、Redis lock 和 serverless 临时磁盘都不能承担长任务正确性。

## 三、核心运行机制

### 3.1 标准链路

```text
Create Run
  -> Load AgentPackage
  -> Validate Input
  -> Build Context
  -> Plan
  -> Act
  -> Observe
  -> Evaluate
  -> Decide
  -> Persist Artifact
  -> Callback
```

### 3.2 状态机

`AgentRun.status`：

```text
pending
  -> planning
  -> running
  -> evaluating
  -> waiting_human
  -> succeeded
  -> partial
  -> failed
  -> cancelled
```

| 状态 | 说明 |
|---|---|
| `pending` | 已创建，等待执行 |
| `planning` | 正在加载或生成执行计划 |
| `running` | 正在执行节点、模型或工具 |
| `evaluating` | 正在评价当前步骤输出 |
| `waiting_human` | 等待人工确认或补充信息；第一版提供最小审批状态迁移 API，不建设复杂审核台 |
| `succeeded` | 业务目标完成 |
| `partial` | 主业务产物已发布，但 Runtime 自己负责的可选步骤未完成；下游媒体 worker 失败不回写 AgentRun |
| `failed` | 不可恢复失败 |
| `cancelled` | 用户或系统取消 |

合法状态转换必须使用条件更新并递增 `status_version`：

| 当前状态 | 允许的下一状态 |
|---|---|
| `pending` | `planning/failed/cancelled` |
| `planning` | `running/failed/cancelled` |
| `running` | `evaluating/waiting_human/failed/cancelled` |
| `evaluating` | `running/waiting_human/succeeded/partial/failed/cancelled` |
| `waiting_human` | `running/failed/cancelled` |
| `failed/partial` | 仅显式 retry 可回到 `pending`，并创建新的 execution attempt |
| `succeeded/cancelled` | 无；重新执行业务目标必须创建新 run |

`dispatch_state` 与业务执行状态分离，并且只属于 `AgentRun`：

```text
held -> queued -> claimed -> finished
                  -> queued  # lease 失效后回收
finished -> queued           # 显式 retry 或人工确认/fallback 恢复
```

worker 所有权由 `lease_owner + lease_expires_at + fencing_token` 表达，不能用 `planning/running/evaluating` 或 Redis lock 表达。

### 3.3 Plan / Act / Observe / Evaluate

公共 Runtime 显式采用 PAOE 模式，而不是把所有逻辑压成一次模型调用：

| 阶段 | 责任 |
|---|---|
| Plan | 生成或加载计划，定义步骤、依赖、停止条件和降级策略 |
| Act | 执行 deterministic、tool、model、guardrail、fallback 节点 |
| Observe | 收集模型输出、工具返回、错误、成本、摘要和 artifact |
| Evaluate | 判断 schema、grounding、安全、完整度、成本和是否需要重试 |

第一版 `MemoirAgent` 使用静态计划。后续 `bounded_loop` 仍是静态计划中的受控节点，
循环体、预算、合并与终止条件由不可变 Package 预先声明，不属于动态 Planner。
Autonomous Agent 的动态计划和计划修订仍放到二期。

### 3.4 停止条件

`PolicyEngine` 必须执行硬限制：

- 最大 step 数。
- 最大模型调用次数。
- 最大工具调用次数。
- 最大 token。
- 最大成本。
- 最大活跃执行时长。
- 最大重试次数。
- side effect 工具最大调用次数。

超出限制时，Runtime 按策略进入 fallback、partial 或 failed，禁止无限循环和重复写入。

`bounded_loop` 的每一轮不新增动态 DAG 节点，但每次物理模型调用都必须独立计入
`max_model_calls/token/cost/active-time`，并在发送前复核 deadline、取消、Package、
privacy/authorization、lease/fencing。循环 policy 的 `budget_profile` 首版只允许
`inherit_run_limits_v1`：从 AgentRun 冻结的剩余
`max_model_calls/max_tokens/max_model_cost/max_run_seconds` 导出有限上限，任一字段缺失、
非有限正值或余额为零即 fail closed；iteration 上限等于剩余 model call，每轮至多一次
调用。单批按稳定顺序完整追加安全 digest，追加后不得超过
`ModelGateway.context_token_budget` 与 Run 剩余 token，单条仍超限则拒绝且不截断。
Package/业务请求不得自选数值。首版循环体仅允许无副作用的 model/deterministic 操作；
Business Tool、媒体上传与发布必须留在循环外。

循环中途不写 Checkpoint，也不保存 iteration/cursor、素材、prompt、模型候选、Scene
或播放文档；每轮只写无内容 audit 计数。只有整个循环节点完成后才按既有节点完成边界
写安全路由 Checkpoint。节点中途 crash/resume 必须重新读取当前获授权 Snapshot 并从
循环节点起点完整重算；已提交发布仍以稳定逻辑键 query-after-commit 对账。当前
`bounded_loop` 尚未实现，实施合同以 2026-08-31 专题设计为准。（2026-09-01 更新：
`bounded_loop` 与 `memoir_agent@1.0.5` 已在本仓工作区实现并通过全量测试，
尚未提交、未部署；部署注意项见同仓 README「AgentPackage 与 MemoirAgent」节。）

运行时间必须拆成独立时钟：

- `max_run_seconds`：只累计 `planning/running/evaluating` 的活跃执行时间。
- `held_ttl_seconds`：约束业务绑定前的 held 握手。
- `queue_ttl_seconds`：约束排队等待。
- `approval_ttl_seconds`：约束 `waiting_human`。
- `max_wall_clock_seconds/run_deadline_at`：约束 run 最终存续时间。

### 3.5 队列与 Worker

AgentRuntime 第一版必须区分 API 进程和执行进程：

```text
FastAPI API
  -> 校验调用方、AgentPackage、input、callback target 和 Admission 配额
  -> 创建 AgentRun / IdempotencyRecord
  -> auto 模式同事务写 run_dispatch outbox；held 模式等待显式 start
  -> 返回 run_id

Runtime Worker
  -> 每轮调用 Dispatcher，从数据库 lease 认领 run_dispatch/callback outbox
  -> run_dispatch 事件解析出 run_id，再在数据库原子认领 run
  -> 获得 execution_attempt / lease / fencing_token
  -> Load AgentPackage
  -> Plan / Act / Observe / Evaluate
  -> 写 Step / ToolCall / Evaluation / Checkpoint / Artifact
  -> 同事务写 CallbackEvent + callback outbox
```

第一版固定实现：

| 方案 | 说明 |
|---|---|
| Worker 数据库轮询 | 当前 Worker 周期执行 `Dispatcher.dispatch_pending()` 并消费返回的 run ID；不需要 Arq 或 Redis 队列才能恢复 |
| RuntimeOutboxEvent | `run_dispatch/callback` 的权威投递意图，支持 lease、退避、dead letter 和原事件重放 |
| AdmissionBucket | global/caller/tenant/agent 的 held/queued/running 事务占用账本，可由 AgentRun.dispatch_state 对账重建 |
| Database lease | worker 单写者与迟到写入保护的权威机制；Redis lock 只能作为优化 |

Arq、RQ 和 Celery 都不是当前实现依赖。不要在
`POST /api/v1/runtime/agent-runs` 请求线程里执行 LangGraph workflow；
Run 是否可恢复只能根据数据库中的 Run/outbox/lease/checkpoint 权威状态判定。

系统级 AdmissionController 第一版至少限制全局、caller/tenant、agent 的 held/queued/running 数量，并限制 provider/model 并发与速率。create held/auto、start、显式 retry 和 human approval/fallback 恢复等外部容量迁移，必须在同一数据库事务中完成配额预留、状态条件更新和 run_dispatch outbox；禁止先查计数再单独写状态。容量不足时返回 `429 RUNTIME_OVERLOADED` 和 `Retry-After`，保持原状态且不完成幂等记录。cancel 和 privacy purge 属于释放容量/安全操作，不得被 Admission 拒绝；lease 回收属于既有任务恢复，不新增长期配额，但 worker claim 仍受执行并发限制。

held/queued/running 的权威占用账本使用 `AdmissionBucket`，而不是每次先聚合 `AgentRun` 再写状态。global 固定使用规范键 `*`，其他 scope 使用认证上下文中的规范化 ID；事务先锁定目标 AgentRun（create 时锁定幂等记录），再幂等确保 bucket 存在，并按 `(scope_type, scope_key)` 固定顺序锁定 global、caller、tenant、agent bucket。校验上限后同时更新 bucket 计数、AgentRun、IdempotencyRecord 和 outbox。重复请求或条件写失败不得重复增减计数。provider/model 的并发槽位与 RPM/TPM 在实际模型路由确定后由同一 Admission 领域的执行期集中限流器管理，不能把尚未选定 provider 的 held/queued run 预记到 provider bucket。

usage 结算是受限的安全账本写入：允许 `running -> aborted_before_send/succeeded/failed/outcome_unknown`；`outcome_unknown` 仅在同一 `usage_id` 与 provider request 身份可核对时补充为 `succeeded/failed`，其余终态不可逆。迟到 worker 只能条件补充 token、估算成本、provider request ID、状态和时间，不得写 prompt、模型原文或业务正文，也不得据此更新 AgentRun、AgentStep、Checkpoint、Artifact 或工作流状态。privacy purge 后可按治理保留这些无内容成本/状态字段；模型输出仍必须丢弃。

dispatcher 必须按 `event_type` 使用显式处理器注册表，并且认领查询只选择当前进程已启用且已注册处理器的类型。未启用或处理器缺失的持久事件保持 `pending`，不增加 attempt、不得因“未知处理器”进入 dead letter；生产 readiness 对部署声明启用的事件类型逐项校验处理器，缺失时返回 503 并告警。`run_dispatch` 与 `callback` 分类型认领和统计，避免一种类型阻塞另一种类型；Task 4.5 先启用 `run_dispatch`，Task 11 注册 callback 处理器后再启用 `callback`，此前积压的 callback 继续使用原事件身份投递。

### 4.12 AdmissionBucket

```text

queued_count
running_count

updated_at

```

`dispatch_state` 是重建 Admission 账本的权威来源：`held -> held_count`、`queued -> queued_count`、`claimed -> running_count`、`finished -> 不占用`。create/start/retry/approval/fallback、worker claim、进入 waiting_human、正常终止、直接取消和 lease reaper 都必须通过同一个 `reserve_transition(from_state, to_state)` 迁移计数：claim 执行 `queued -> running`，worker 进入等待或终态执行 `running -> none`，reaper 执行 `running -> queued`。对账任务比较 bucket 与 AgentRun 聚合结果，在锁和条件版本保护下修复漂移并记录安全审计。

### 4.13 IdempotencyRecord

```text
client_id
idempotency_key
scope: create | start | retry | cancel | human_approval | purge
request_hash
response_json
resource_type
resource_id
expires_at
created_at
updated_at
```

相同 `client_id + scope + idempotency_key` 且 request hash 一致时返回首次结果；hash 不一致返回 `409 IDEMPOTENCY_CONFLICT`。Runtime 写接口的 `request_hash` 固定为 `SHA256(upper(method) + "\n" + normalized_path + "\n" + body_sha256)`，其中 path 必须包含 `run_id` 等资源标识，timestamp 和幂等 header 不参与计算。这样空 body 的 start/cancel/purge 也能识别“同一 key 指向另一个 run”的冲突。只有事务已接受或已经产生副作用的操作才完成幂等记录，执行前 429、连接失败和可重试 5xx 不得被固化到整个 TTL。

`AgentRun.create_idempotency_key` 只保存创建请求的审计关联，不建立永久唯一约束；幂等权威边界是带 `scope/expires_at` 的 IdempotencyRecord。未过期记录按 hash 复用或冲突，过期记录可在数据库锁保护下原子换代为新请求；purge scope 至少保留到清理完成。维护任务清理过期记录，不能让 AgentRun 的长期存续把 7 天 TTL 变成永久限制。

```text
  -> END
```

节点的 `name/type/input_fields/input_trust_policy/output_fields/prompt_id/tool_names/retry_policy/fallback_node/timeout_ms` 仍需导出为可校验 manifest，供 Planner、Contract 测试和观测使用。

说明：

- `publish_playback_document` 是第一版唯一必做的业务发布节点，调用 `memory.publish_playback_document` 原子发布完整作品。
- 媒体默认关闭时，`enqueue_media_tasks` 返回
  `skipped(capability_disabled)`。`1.0.3` 起该节点已移到发布前；开启后
  在节点内按场景文案文生图、上传 OSS，再将 manifest 与文档一次原子
  发布。当前不创建二段异步 MediaTask，也不因单图失败把 Run 置为
  `partial`；失败场景就地降级文字卡。
- `package_digest` 由构建器按排序后的 package 文件路径与内容计算，不由作者写进 `agent.yaml`；签名文件、构建时间和 digest 自身等生成元数据必须排除，避免摘要自引用或同内容漂移。同版本 digest 变化时拒绝注册。

## 六、API 契约

所有 API/Event/Tool/Artifact envelope 必须包含 `schema_version` 或 `contract_version`。Contract Layer 使用无业务依赖的 Pydantic 模型并导出 JSON Schema；破坏性变更提升 major version，业务 Adapter 对不支持的 major version必须拒绝。

基础接口：

| 接口 | 责任 |
|---|---|
| `GET /api/v1/runtime/health/live` | 只判断进程和事件循环存活 |
| `GET /api/v1/runtime/health/ready` | 检查数据库 schema、Registry、outbox/queue、已启用 outbox handler 和签名配置；draining 或启用类型缺 handler 时返回 503 |
| `GET /api/v1/runtime/capabilities` | 鉴权返回 Runtime/Contract 版本、Agent 版本、逻辑 model policy 和可选能力，不返回密钥或真实 endpoint |
| `POST /api/v1/runtime/agent-runs` | 创建 held 或 auto AgentRun，快速返回固定版本与授权摘要 |
| `POST /api/v1/runtime/agent-runs/{run_id}/start` | 幂等执行 held -> queued，并同事务写 run_dispatch outbox |
| `GET /api/v1/runtime/agent-runs/{run_id}` | 返回当前运行、调度、事件和 privacy 安全摘要 |
| `GET /api/v1/runtime/agent-runs/{run_id}/steps` | 返回步骤摘要，不暴露私密 state、内部堆栈或执行凭据 |
| `POST /api/v1/runtime/agent-runs/{run_id}/retry` | 从允许的 checkpoint 创建新 execution attempt |
| `POST /api/v1/runtime/agent-runs/{run_id}/cancel` | 请求取消，或直接终止尚未被 Worker 认领的 run |
| `POST /api/v1/runtime/agent-runs/{run_id}/human-approval` | 对 waiting_human run 执行带状态版本的 approve/reject |
| `POST /api/v1/runtime/agent-runs/{run_id}/purge-private-data` | 受信任业务服务写 privacy tombstone/version，并异步清理私密 payload |

### 6.0 入站身份校验

除部署探针使用的 `/api/v1/runtime/health/live`、`/api/v1/runtime/health/ready` 外，业务系统调用受保护的 Runtime API 时必须带服务身份和签名：

```text
X-Agent-Client-Id
X-Agent-Key-Id
X-Agent-Timestamp
X-Agent-Signature
```

`runtime-capabilities`、AgentRun 查询和步骤查询属于受保护的读接口，需要验签但不要求 `Idempotency-Key`。create、start、retry、cancel、human approval 和 privacy purge 属于写接口，除上述签名头外必须携带 `Idempotency-Key`。

校验规则：

- `X-Agent-Client-Id` 必须属于 Runtime 配置的可信业务系统。
- `X-Agent-Signature` 使用 HMAC-SHA256。
- 签名原文固定为 `{method}\n{path}\n{timestamp}\n{body_sha256}`。
- 共享密钥通过环境变量或密钥管理服务注入，不写入代码和 AgentPackage。
- `X-Agent-Timestamp` 默认容忍窗口为 300 秒，超过窗口时拒绝。
- 所有 Runtime 写接口必须支持 `Idempotency-Key`，防止业务后端重试时重复创建 run、迁移状态、写 outbox 或触发清理。
- `business_type` 必须在目标 AgentPackage 的 allowlist 中。
- Runtime 需要为每个可信业务系统配置 `caller_id/tenant_id`、`secret_ref/key_id`、允许的 Agent、`business_type`、callback target、business connector、数据域和配额。
- Runtime 从服务凭据推导 caller/tenant，不接受请求 body 自报身份作为授权依据。
- callback 和 tool endpoint 使用预注册 target/connector；签名请求禁止跟随重定向，并执行协议、host、port、DNS/IP allowlist 与私网阻断。
- Runtime 发往业务后端的 callback 也必须使用同一套 HMAC-SHA256 机制签名，业务后端必须验签。
- 生产请求必须携带 `X-Agent-Key-Id`。调用方和接收方只在配置的轮换窗口内同时接受新旧 key，不同 connector 不共用 secret。
- 验签方必须基于未经重新序列化的原始请求 body 计算 `body_sha256`，并使用恒定时间比较签名；签名请求禁止跟随重定向。

### 6.2 启动 held AgentRun

```text
POST /api/v1/runtime/agent-runs/{run_id}/start
```

请求体使用冻结的 `StartAgentRunRequest`：可省略 `expected_status_version`；提供时必须为当前 `status_version`，不匹配返回冲突且不得迁移状态或写 dispatch outbox。路由必须实际解析该模型，不能只把原始 body 用于幂等 hash。

首次有效 start 在一个数据库事务中锁定幂等记录、AgentRun 和 AdmissionBucket，复核当前调用方授权、package 未 revoked 且 `privacy_state=active`，再完成 `dispatch_state: held -> queued`、Admission `held -> queued`、写入 `queued_at`、创建 `run_dispatch` outbox 和固化幂等响应；`AgentRun.status` 保持 `pending`，HTTP 请求不执行 workflow。

响应至少包含：

```json
{
  "run_id": "run_abc",
  "status": "pending",
  "dispatch_state": "queued",
  "queued_at": "2026-07-07T10:00:00Z"
}
```

start 同时区分请求幂等和资源状态幂等：相同 `client_id + start scope + Idempotency-Key + request_hash` 重放首次响应；使用新 key 调用已经 `queued/claimed` 的 run 时返回当前安全摘要，但不得重复迁移 Admission、修改状态或创建第二条 dispatch outbox。相同 key 指向不同 run 或不同 body 返回 `409 IDEMPOTENCY_CONFLICT`；held 已过期、run 已取消/结束、package 已 revoked、privacy 非 active 或当前授权失效时拒绝。Admission 在事务接受前返回 429 时保持 held，且不完成 IdempotencyRecord。

### 6.5 重试

```text
POST /api/v1/runtime/agent-runs/{run_id}/retry
```

请求体使用冻结的 `RetryAgentRunRequest`：可省略 `expected_status_version`；提供时必须与当前版本一致，否则返回冲突且不增加手动重试计数、不写 dispatch outbox。路由必须实际解析该模型。

默认从失败 checkpoint 恢复。side effect 工具必须使用幂等键防止重复写入。

Retry 约束：

- 调用方必须是原 `client_id` 或内部审计身份。
- `business_id` 与 `business_type` 必须匹配原 run。
- 第一版默认每个 run 最多手动重试 3 次。
- Runtime 自动节点重试使用 step attempt 计数，与用户/后台手动重试计数互不消耗。
- 重试时默认复用原 snapshot，不重建业务素材。
- 已经 `succeeded/cancelled` 的 run 不允许重试。
- `partial` 只重试 Runtime 自己未完成的可选步骤，复用已发布 revision，不重新发布主作品；下游媒体 worker 失败走业务媒体重试，不调用 AgentRun retry。

### 6.6 取消

```text
POST /api/v1/runtime/agent-runs/{run_id}/cancel
```

请求体使用冻结的 `CancelAgentRunRequest`，必填不含自由文本的稳定 `reason_code`；该字段进入受控审计，不得被路由忽略。

只允许取消 `pending/planning/running/evaluating/waiting_human` 状态的 run。

取消必须区分是否存在有效执行者。`pending + held/queued` 或 `waiting_human + finished` 没有 worker 可完成协作式取消，API 必须在同一事务条件写入 `cancel_requested_at`、`status=cancelled`、`dispatch_state=finished`，递增 `status_version` 并创建 callback outbox；残留 dispatch 到达时由 worker 的认领条件拒绝。`claimed` 的 `pending/planning/running/evaluating` 先条件写入 `cancel_requested_at`，阻止新模型和工具调用，再由持有有效 fencing token 的 worker 中止可中止请求并在安全边界进入 `cancelled`。取消与 retry/approval 互斥，也不能代替私密数据清理。

### 6.7 人工确认最小接口

```text
POST /api/v1/runtime/agent-runs/{run_id}/human-approval
```

第一版实现可恢复执行所需的最小 approve/reject 接口和状态迁移，不实现复杂审核后台。

进入 `waiting_human` 时必须保存 `waiting_expires_at` 和恢复 checkpoint，worker 释放 lease 并把 `dispatch_state` 收敛为 `finished`。审批请求带独立幂等键、`decision=approve|reject` 和 `expected_status_version`；approve 在条件校验后只把 `dispatch_state: finished -> queued`、递增 `status_version` 并同事务写 run_dispatch outbox，`AgentRun.status` 保持 `waiting_human`，待新 worker 取得 lease 后再迁移为 `running`。reject 或审批超时按 AgentPackage 明确的 fallback/failed/cancelled 策略处理；需要继续执行 fallback 时同样重新入队，终止策略才写 `failed/cancelled`。

### 6.8 私密数据清理

请求体使用冻结的 `PurgePrivateDataRequest`，必填不含自由文本的稳定 `reason_code`；该字段进入受控审计，不得被路由忽略。

`purge-private-data` 在同一事务中设置 `cancel_requested_at`、`privacy_state=purge_requested` 并递增 `privacy_version`，随后返回 `202 + privacy_state=purge_requested + privacy_version`，不得同步等待物理清理完成。清理 worker 删除 Checkpoint、临时 Artifact 和模型/工具私密 payload 后标记 `purged`，调用方通过鉴权的 AgentRun 查询确认终态。相同 key 与 request hash 的重复 POST 重放首次 `202/purge_requested` 接受结果，不随后台清理进度改写 `IdempotencyRecord.response_json`，也不得创建第二次清理；当前状态只通过鉴权的 AgentRun 查询返回。清理失败时 Runtime 保持写屏障，业务后端保持访问撤销，由 reconciler 重试并告警，不能回退为 `active`。所有私密写入都必须携带预期 privacy version；purge 后禁止 retry/resume。

HTTP Business Tool 的 `path` 必须是 connector 下预注册的相对路径，禁止完整 URL。`input_from` 只能读取已声明的 trusted run/manifest/deterministic state 或经过 schema 校验的候选字段；`output_to` 只能写入 AgentState manifest 声明的结果槽，不能覆盖 identity、authorization、connector、generation token 或其他可信控制字段。

### 7.2 HTTP Business Tool

第一版必须实现 HTTP Business Tool。

调用格式：

```text
POST {BUSINESS_API}/api/v1/internal/agent-tools/{tool_name}
```

请求头：

```text
X-Agent-Runtime-Id
X-Agent-Key-Id
X-Agent-Run-Id
X-Agent-Tool-Name
X-Agent-Tool-Attempt
X-Agent-Timestamp
X-Agent-Signature
Idempotency-Key
```

请求体：

```json
{
  "input": {},
  "context": {
    "agent_id": "memoir_agent",
    "agent_version": "1.0.0",
    "run_id": "run_abc",
    "step_id": "step_load_snapshot",
    "business_type": "couple_memory",
    "business_id": "archive_123",
    "trace_id": "trace_xyz"
  }
}
```

side effect 工具必须传 `Idempotency-Key`：

```text
{run_id}:{logical_step_key}:{tool_name}:{operation_key}
```

该 key 表达同一个逻辑副作用，HTTP 重试、checkpoint resume 和 worker 接管必须复用。`execution_attempt/tool_attempt` 只进入审计 header 与 ToolCall，不参与幂等键。

`X-Agent-Tool-Attempt` 只传当前工具物理尝试次数，服务端不得把它作为业务授权、幂等或 generation fencing 的依据；权威 attempt 仍以 Runtime `AgentToolCall` 为准。

`memory.publish_playback_document` 单次请求必须携带完整 document/scenes/actions/`media_manifest`、`run_id/snapshot_id/generation_epoch` 和稳定幂等键；媒体能力关闭时 `media_manifest` 为必填空数组。Business Tool v1 遵循本节冻结的 `ToolRequest/ToolResult`：请求固定为 `{"input":{...},"context":{...}}`，其中 `context` 由可信 Run/Step 构造；成功响应固定为 `{"output":{...},"schema_version":"1.0.0"}`。`X-Agent-Run-Id/X-Agent-Tool-Name` 必须与 body、路由一致；只有已落库权威物理 `AgentToolCall` 才发送 `X-Agent-Tool-Attempt`，且该值只用于审计。`document` 必填 `schema_version/scenes/actions/media_manifest`，scene 必填 `scene_id/scene_type/source_refs`、可选 `safety_level/title/body/payload/order`，action 必填 `action_id/action_type/scene_id/duration_ms`、可选 `payload/order`。业务后端在同一事务校验 schema、引用、数量、素材归属、active run 和 epoch，并对收到的未改写 `document` 执行与 Runtime 相同的规范 JSON SHA-256：UTF-8、`ensure_ascii=false`、键字典序、紧凑 `,`/`:` 分隔符。`content_digest` 在补默认值、拆分持久化行或转公开 camelCase 前计算，不得与 HMAC raw-body digest 或幂等请求 digest 混用；成功 `output` 返回 `revision + content_digest`。Runtime 先校验外层 Tool schema major，再保存为 `publish_result`；只有该结果成功后才可进入 `succeeded/partial`。

### 7.3 工具安全

必须实现：

- AgentPackage 工具 allowlist。
- 输入 schema 校验。
- 输出 schema 校验。
- 服务间 HMAC 签名。
- timestamp 过期校验。
- side effect 工具幂等键。
- 超时和重试限制。
- 工具结果敏感字段扫描。
- 工具错误结构化为 `error_code/error_type/retryable/safe_message/details_visible_to_model`；除非契约显式允许，`details_visible_to_model=false`，堆栈、内部地址和私密详情不得进入模型上下文。
- HTTP Business Tool 非 2xx body 直接使用冻结 `ToolError`；`error_code/error_type/retryable/safe_message` 必填，`details_visible_to_model` 可省略并默认 `false`，v1 若显式提供也只能为 `false`。Runtime 只接受错误码 allowlist，并校验 HTTP 状态、`error_code` 与 `retryable` 分类一致；未知 code、非法 shape 或分类矛盾时 fail closed，不解析或记录 FastAPI `detail`、响应原文与内部异常。
- trusted 参数来源校验；identity、tenant、business_id、connector、permission、callback target、generation/version token 和 operation key 只能来自已校验 run、manifest 或确定性节点。
- 出站 connector 注册、DNS/IP 校验、私网阻断和禁止重定向。
- 每次调用前按当前 `authorization_version` 重新授权，业务后端仍做二次鉴权。

禁止：

- Agent 自由拼接业务 SQL。
- Runtime 直接连接业务数据库。
- 未授权工具进入模型上下文。
- 工具错误堆栈原样返回模型。

### 7.4 框架工具适配

第一版回忆录主要通过 LangGraph 节点调用 `ToolGateway`，但公共 Runtime 的工具协议必须保留框架适配层：

| 适配 | 第一版要求 | 用途 |
|---|---|---|
| Native Tool | 必做少量 | JSON 修复、摘要压缩、敏感字段扫描等 Runtime 内部工具 |
| LangChain Tool | 必做基础包装 | 供 LangChain 组件、后续 createAgent 和部分 workflow 节点复用 |
| AI SDK Tool 等价适配 | Python 版预留接口 | 原设计中的 AI SDK ToolLoopAgent 能力在 Python 中由 Provider Adapter / ToolLoop 抽象承接 |
| MCP Tool | 二期完整接入 | 外部工具、资源和 prompt 标准化接入 |

Native/LangChain/未来 AI SDK 或 MCP 适配器只能转换 schema 与调用接口，最终执行必须统一回到 `ToolGateway`，不得自行解析 connector、发送业务 HTTP 或绕过授权、幂等、审计和脱敏。

工具返回结果进入模型上下文前必须经过 `ContextManager` 压缩和脱敏。

回忆录第一版工具清单固定为：

| 工具 | side effect | 第一版 |
|---|---:|---|
| `memory.get_snapshot` | 否 | 必做 |
| `memory.publish_playback_document` | 是 | 必做，唯一作品发布入口 |
| `memory.enqueue_tts` | 是 | 只预留契约，默认关闭 |

业务工具可以返回不可重试的 `GENERATION_SUPERSEDED`，表示 `active_run_id/generation_epoch` 已变化；Runtime 随即停止旧 run 的剩余副作用。Runtime 自身可返回不可重试的 `AUTHORIZATION_REVOKED`，不得自动更换 connector 或身份。

`cancellation_behavior` 必须固定为 `cancellable/non_cancellable/query_after_commit`。取消 run 后，Runtime 停止发起新工具；不可中止或已提交工具只能使用原逻辑幂等键查询原结果，旧 fencing/privacy version 不得推进状态或保存私密 payload。

## 八、ModelGateway 与 PromptRegistry

### 8.1 ModelGateway

第一版模型网关职责：

- 根据 `model_policy` 选择 provider 和 model。
- 调用部署预注册的内部 Provider Adapter；当前不经 LiteLLM。
- 支持结构化 JSON 输出。
- 记录 token、成本、延迟和 parse 状态。
- 支持模型超时重试。
- 支持 fallback model。
- 禁止日志记录完整 prompt 和私密素材。
- 路由优先级固定为 Runtime 紧急禁用/数据驻留/租户策略 -> AgentPackage 逻辑 policy -> 部署映射 -> 该 policy 明示 fallback；业务请求不能覆盖 provider、model、base URL、key 或 fallback 顺序。
- 按 provider/model 执行共享有界并发、RPM/TPM、超时、Retry-After 和熔断；worker 不能各自无限重试放大流量。
- 记录 `model_policy + route_config_version + capability_snapshot`，恢复执行时可以解释原路由决策。
- 调用前校验 structured output、vision、上下文长度、数据驻留和 thinking 参数等节点能力；不满足时只能走该 policy 明示 fallback，无可用路由则返回配置错误。
- provider endpoint 由管理员注册；自定义 base URL 必须执行协议/host/port allowlist、DNS/IP 校验、私网阻断和逐跳重定向复检，业务请求与 AgentPackage 不能覆盖 endpoint 或 key。
- `private_first` 只有在部署侧配置合规私有 provider 时可用；未配置时返回 capability disabled 或走该 policy 明确声明的合规 fallback，不能静默切换任意云模型。
- 每个 route 必须绑定管理员维护的 `pricing_config_version/cost_unit/input_unit_cost/output_unit_cost`。Runtime 部署只允许一种预算 `cost_unit`；内部或免费模型也要显式配置零价，缺失、单位不一致或无法解析的价格配置必须禁用 route/capability，不能把未知价格当作零成本。

第一版必须提供共享 `ProviderTrafficController`：

```text
acquire(route_key, estimated_tokens, deadline_at) -> ProviderPermit
mark_started(permit) -> None
settle(permit, actual_tokens | null, outcome, retry_after_seconds | null) -> None
```

`outcome` 固定为 `succeeded/failed/timeout/rate_limited/aborted_before_send/outcome_unknown`，不能由 provider 返回文本或模型输出扩展。

`route_key` 由管理员注册的 provider account、model 和限流分区生成，不包含 API key，也不能由业务请求或模型输出指定。`acquire` 使用 Redis 原子操作同时检查共享 `blocked_until`、熔断状态、并发 semaphore、RPM 和 TPM；`estimated_tokens` 按输入 token 估算加 `max_output_tokens` 保守预留。未取得 permit 时禁止请求上游，并返回安全的 `retry_after` 供当前 model policy 决定在剩余 deadline 内等待或切换已声明 fallback。

`ProviderPermit` 至少包含 `permit_id/route_key/acquired_at/expires_at/reserved_tokens`，Controller 在共享存储中维护 `acquired -> started -> settled` 生命周期。ModelGateway 完成发送边界复核后必须先用原子 CAS 执行 `mark_started`，成功后才能开始上游 HTTP；mark 失败时不得发送。`settle` 也使用 CAS 并保持幂等，重复或非法状态转换不能再次增减计数。

每次候选请求都在 `finally` 中 settle 并释放并发槽位。只有 `acquired` permit 可以用 `aborted_before_send` 转为 `settled`，Controller 同时回滚该 permit 占用的 RPM 与 TPM 预留；`started` permit 禁止使用该结果，即使取消、超时或响应未知也要保守结算。已经发出的请求用实际 token 结算 TPM；provider 未返回 usage 时保留 RPM 与 TPM 预留直到窗口自然过期。acquired permit 因 TTL 回收时可回滚未发送预留，started permit 超时只释放并发槽，RPM/TPM 继续保留到窗口结束。route 注册时必须满足 `permit_ttl_seconds >= request_timeout_seconds + settle_margin_seconds`，请求硬超时还要受当前 deadline 约束；配置不满足时禁用该 route，防止 permit 先过期而上游请求仍在执行。重试等待期间不得持有 permit，每次候选请求都重新 acquire。上游 429 的 `Retry-After` 写入共享 `blocked_until`，使其他 worker 同步停止放大请求；fallback route 使用自己的 route key 和 permit。

Redis/共享流量控制不可用时，ModelGateway 禁止退化到进程内无限调用。当前节点按 policy 进入显式 provider fallback、模板 fallback 或安全失败，capabilities 同时把受影响的模型增强标为不可用。permit 等待计入活跃执行时间，并受节点 timeout、剩余 `max_run_seconds` 和 `run_deadline_at` 的最小 deadline 限制。

模型调用必须携带 Runtime 从有效 lease 构造的可信上下文，不能从 prompt、业务请求或模型输出读取这些字段：

```text
ModelCallContext
  run_id
  step_id
  execution_attempt
  lease_owner_id
  fencing_token
  privacy_version
  authorization_version
  deadline_at
```

`ModelGateway.generate_structured(prompt_id, variables, output_schema, policy, call_context)` 在 `acquire` 返回后必须重新校验 lease/fencing、cancel、package、privacy、authorization、route/capability 和 deadline；等待期间已失效时立即 settle permit 为 `aborted_before_send`，不创建 usage，也不请求 provider。校验通过后，ModelUsageService 使用同一可信上下文条件写并提交 `AgentModelUsage.running`；提交后、真正发送 HTTP 前再执行一次发送边界复核。此时失效则把既有 usage 与 acquired permit 都结算为 `aborted_before_send`。复核通过后必须成功执行 `mark_started` 才能发送 HTTP；mark 失败则不发送，并把 usage 结算为 `aborted_before_send`。上游返回后再次执行同一安全边界校验：只有仍有效的执行上下文可以消费结构化输出并推进工作流；失效上下文只允许结算同一条无内容 usage 记录、释放 permit 和写安全审计。

单 run 的 `max_model_calls/max_estimated_cost` 以实际或可能已发出的物理 attempt 计数：`aborted_before_send` 不计入；已结算且观察到 usage 的记录按该 attempt 固化的 pricing version 计算实际估算成本，`running/outcome_unknown` 或未观察到 usage 的记录使用预留成本，同一行不能把实际值和预留值重复相加。存在未决预留时，PolicyEngine 必须先扣除该额度，再决定是否允许 retry 或 fallback。

模型策略：

| 策略 | 用途 |
|---|---|
| `reasoning` | 章节规划、复杂判断 |
| `balanced` | 高光挖掘、普通生成 |
| `emotional_writing` | 高质量中文情感文案 |
| `cheap_structured` | 简单 JSON、动作脚本 |
| `strict` | 安全复核 |
| `private_first` | 隐私敏感任务 |

每个模型节点必须输出 JSON，并通过 Pydantic schema 校验。

## 九、ContextManager 与 MemoryManager

### 9.1 ContextManager

`ContextManager` 是第一版必做能力，用来避免模型上下文失控和隐私外泄。

职责：

- 按 `model_policy` 和节点类型计算 token 预算。
- 将 run input、业务元信息、Agent 规则、工具结果和 prompt 变量拼装为节点上下文。
- 对素材分块，长日记只使用短摘录。
- 对工具结果做摘要压缩，再进入模型上下文。
- 对手机号、地址、openid、token、图片私有 URL 等敏感字段做二次扫描。
- 保存上下文摘要，便于评测和复盘，但不保存完整私密原文。
- 明确区分 trusted instructions 与 untrusted content；日记、赌局、图片说明、RAG/Web Search 和工具返回只能进入独立结构化数据槽，不能拼入 system/developer 指令、工具描述或 schema。
- 标记 injection risk 并记录安全摘要；分类器只提供风险信号，静态 workflow、tool allowlist、trusted 参数映射、语义校验和业务二次鉴权共同形成执行边界。

第一版 `MemoirAgent` 的上下文来源必须遵循：

```text
run.input 只定位 archive/snapshot/owner
  -> memory.get_snapshot 获取脱敏快照
  -> sanitize_materials 生成可进模型的素材
  -> ContextManager 拼装 prompt 变量
```

### 9.2 MemoryManager

公共 Runtime 的记忆分层：

| 类型 | 第一版策略 | 说明 |
|---|---|---|
| Run Memory | 必做 | 当前 run 的 state、step 输出、checkpoint、artifact |
| Session Memory | 可选 | 多轮对话类 Agent 使用，回忆录第一版不用 |
| Long-term Memory | 不做 | 回忆录私密素材默认不进入长期记忆 |

`MemoryManager` 第一版可以由 `AgentCheckpoint`、`AgentArtifact` 和 `AgentStep` 共同承接，不需要单独引入向量库。二期客服 Agent 接入时再扩展长期记忆和 Retriever。

## 十、Public Trace 与 Callback

### 10.1 Public Trace

Runtime 内部 trace 不等于前端可见轨迹。每个 AgentPackage 通过 `ui-trace.yaml` 控制可见等级：

| 等级 | 说明 |
|---|---|
| `none` | 不展示轨迹 |
| `status_only` | 只展示生成中、成功、失败 |
| `public_summary` | 展示脱敏步骤文案 |
| `debug_staff` | 仅内部人员看详细轨迹 |
| `full_internal` | 仅审计后台看完整 trace |

回忆录第一版建议使用 `public_summary`，但只展示：

- “整理素材”
- “寻找值得保留的片段”
- “生成回忆卡片”
- “检查隐私与表达”
- “保存回忆作品”
- “补齐旁白任务”

### 10.2 Callback

Runtime 对业务系统回调：

```text
POST {resolved_callback_target_url}
```

Runtime 只允许从创建 run 时保存的 `callback_target_id` 解析预注册固定 URL；业务请求、AgentPackage、AgentState 和模型输出都不能提供或覆盖任意 callback URL，dispatcher 也不得跟随重定向。

请求头：

```text
X-Agent-Runtime-Id
X-Agent-Key-Id
X-Agent-Run-Id
X-Agent-Business-Id
X-Agent-Event-Id
X-Agent-Event-Seq
X-Agent-Timestamp
X-Agent-Signature
Idempotency-Key
```

事件：

- `run_started`
- `step_changed`
- `waiting_human`（AgentPackage 启用人工确认 callback 时）
- `partial_succeeded`
- `run_succeeded`
- `run_failed`
- `run_cancelled`

callback 内容只允许包含安全摘要：

```json
{
  "event": "step_changed",
  "event_id": "evt_123",
  "event_seq": 12,
  "status_version": 8,
  "run_id": "run_abc",
  "agent_id": "memoir_agent",
  "business_id": "archive_123",
  "status": "running",
  "public_trace": [
    {"step": "generate_scenes", "label": "生成回忆卡片", "status": "running"}
  ],
  "error": null
}
```

`CallbackPayload` 使用 `extra=forbid`，body 只允许 `event,event_id,run_id,event_seq,status_version,agent_id,business_id,status,error,public_trace`；`current_step/progress` 不属于 callback 字段。业务后端需要修复进度或当前步骤时，使用 6.3 的 AgentRun 主动查询安全摘要，不得从 callback body 接收兼容别名或额外字段。

callback 必须支持：

- HMAC 签名。
- 业务后端必须按 `X-Agent-Runtime-Id` 找到密钥并验签，校验 `run_id/business_id/event_id/event_seq` header 与 body 一致。
- 最大 5 次重试。
- 指数退避。
- 持久 outbox、dispatcher lease、`Retry-After` 和 dead letter。
- `Idempotency-Key` 固定为 `callback:{event_id}`；首次投递、自动重试和 dead-letter 重放必须复用同一值。
- 业务后端以 `event_id` 为权威去重标识；同一事件与相同 body hash 重放时返回成功，不重复写入，同一事件对应不同 body hash 时返回 HTTP `409 Conflict` + `IDEMPOTENCY_CONFLICT`。
- 单个 run 内单调递增的 `event_seq`。
- `event_seq` 采用方案 A：在同一个 `run_id` 的完整生命周期内全局单调递增，手动 retry、checkpoint resume 或自动恢复后继续从当前最大值累加，不重置为 1。
- 业务后端分别保存并比较 `last_event_seq` 与 `last_runtime_status_version`；任一倒退都只记审计，不更新业务状态，本地 `row_version` 不参与 Runtime 事件排序。

业务后端必须按 Runtime 合法状态转换和事件版本处理 callback，不能用一条线性大小关系比较状态。`step_changed(running)` 不得覆盖已经处理的 `run_succeeded`、`partial_succeeded`、`run_failed`、`run_cancelled` 或更高版本事件。

Runtime 在状态事务内创建不可变 CallbackEvent 和对应 outbox 行。重放必须复用原 `event_id/event_seq/status_version/Idempotency-Key`；callback dead letter 不改变 run 终态，业务系统通过主动查询 Runtime 修复本地摘要。

### 10.3 RuntimeEvent 与业务 Callback 的边界

Runtime Contract 第一版冻结详细内部事件类型：

```text
run_started
step_started
model_call_started
model_call_finished
tool_call_started
tool_call_finished
step_failed
fallback_used
human_review_requested
partial_succeeded
run_succeeded
run_failed
run_cancelled
```

第一版不提供 Runtime 原生 `/events` SSE。详细事件通过 `AgentStep/AgentModelUsage/AgentToolCall/AgentEvaluation` 等权威记录持久化并可查询；对业务系统只映射为 10.2 的安全 callback 集合，例如内部 `step_started/step_failed/fallback_used` 映射为脱敏 `step_changed`，`human_review_requested` 映射为 `waiting_human`。只有 workflow 可能进入人工等待且 AgentPackage 显式启用该 callback 时才发送 `waiting_human`；否则该 AgentPackage 第一版不得进入无法被业务侧发现和处理的人工等待分支。映射不得把 prompt、工具 payload、模型原文或隐藏推理带入 CallbackEvent。二期开放事件订阅时继续使用同一版本化 `RuntimeEvent` envelope，不能另造不兼容事件语义。

## 十一、幂等、补偿与默认参数

### 11.1 幂等键生命周期

Runtime 需要统一记录入站和出站幂等键：

| 场景 | 幂等键 | 存储方 | 默认 TTL | 重复请求行为 |
|---|---|---|---|---|
| 创建 AgentRun | 业务后端传 `Idempotency-Key` | Runtime | 7 天 | 重放首次创建响应；当前状态通过 AgentRun 查询 |
| Start / Retry / Cancel / Human approval | 业务后端传 `Idempotency-Key` | Runtime | 7 天 | 返回原操作结果 |
| Privacy purge | 业务后端传 `Idempotency-Key` | Runtime | 至少保留到清理完成 | 重放原 `202/purge_requested + privacy_version` 接受结果；当前 state 通过 AgentRun 查询 |
| HTTP Business Tool side effect | Runtime 生成稳定逻辑操作键，不含 attempt | Runtime 摘要记录 + 业务后端 | 30 天 | 业务后端返回第一次写入结果 |
| Callback | Runtime 生成 `event_id`，`Idempotency-Key=callback:{event_id}` | Runtime + 业务后端 | 30 天 | 相同事件与 body hash 返回成功；同事件不同 body hash 返回 `409 IDEMPOTENCY_CONFLICT` |

如果相同 `Idempotency-Key` 的 Runtime 写请求在 method、normalized path 或 body hash 任一项不一致，必须返回 HTTP `409 Conflict`，错误码 `IDEMPOTENCY_CONFLICT`，不得创建新 run 或推进目标资源；资源型路径中的 `run_id` 必须参与 request hash。

### 11.2 跨库一致性与补偿

Runtime 库和情侣日记业务库不是同一个事务边界。第一版采用“状态对账 + 幂等补偿”，不做分布式事务。

必须实现：

- Runtime 接受 auto create 或显式 start 后，在同一事务保存 `AgentRun/dispatch_state` 和 run_dispatch outbox；队列投递失败不丢失调度意图。
- auto create 或显式 start 在同一事务更新 `dispatch_state` 并写 run_dispatch outbox；队列投递只负责唤醒 worker。
- worker 使用数据库条件写原子认领、heartbeat 续租和 fencing token；Redis lock 只能优化竞争，不能作为最终写保护。
- heartbeat 超时后 reaper 回收并创建新 execution attempt；旧 worker 的迟到写入因 fencing 失败。
- Runtime 调业务 side effect 工具前记录 `AgentToolCall.running` 和幂等键。
- Runtime 调模型前在 permit 后二次校验执行边界并记录 `AgentModelUsage.running`；过期 running 由对账标为 `outcome_unknown`，按预留成本保守计量。
- 业务工具成功但 Runtime 写回状态失败时，重试同一幂等键，业务后端返回第一次写入结果。
- Callback 失败时 Runtime 保留 callback outbox，由 dispatcher 退避派发，超过窗口进入 dead letter。
- 情侣日记后端保留按 `run_id` 查询 Runtime 的兜底能力，避免 callback 丢失导致状态永久卡住。
- Runtime 已创建 held run 但业务侧绑定 `run_id` 失败，或 `MemoryAgentRunRef` 长时间停留在 `pending_start` 时，业务补偿任务必须复用原 create `Idempotency-Key` 恢复绑定或明确标记失败，不得创建第二个 run。
- 对账任务默认每 5 分钟扫描 pending/queued 未投递、dispatch dead letter、lease/heartbeat 失效、活跃执行预算耗尽、人工等待超时、callback dead letter、tool call running 和 model usage running 超时；同一对象连续 3 次修复失败后升级告警。
- 第一版单实例 Runtime 可由单个调度器执行对账任务；扩展为多实例时必须使用数据库/分布式 lease 或按 `run_id` 哈希分片，避免同一个 run 被多个实例重复补偿或重复告警。

情侣日记后端创建 archive/snapshot 后调用 Runtime 时，推荐流程：

```text
创建 MemoryArchive / MemorySnapshot
  -> 本地保存 MemoryAgentRunRef(status=pending_start)
  -> 调 Runtime POST /api/v1/runtime/agent-runs(start_mode=held)
  -> 成功后事务绑定 run_id + active_run_id + generation_epoch
  -> 调 Runtime POST /api/v1/runtime/agent-runs/{run_id}/start
  -> create 失败只重试 create；start 失败只重试 start，两者使用独立稳定 Idempotency-Key
```

### 11.3 第一版默认参数表

| 参数 | 默认值 | 说明 |
|---|---:|---|
| `max_steps` | 16 | 覆盖 MemoirAgent 主链路和 fallback |
| `max_model_calls` | 8 | 高光、章节、场景、安全复核及 repair 余量 |
| `max_tool_calls` | 20 | 读取、保存、状态、媒体任务和重试余量 |
| `max_run_seconds` | 300 | 只累计 planning/running/evaluating 的活跃执行时间，不含 held、queued 和 waiting_human |
| `held_ttl_seconds` | 600 | held run 最长等待 10 分钟 |
| `queue_ttl_seconds` | 900 | queued 最长等待 15 分钟 |
| `approval_ttl_seconds` | 86400 | 人工等待默认最长 24 小时 |
| `max_wall_clock_seconds` | 172800 | run 最终存续上限 48 小时 |
| `lease_timeout_seconds` | 60 | worker 失联回收阈值，必须大于 heartbeat 间隔 |
| `max_auto_retry_per_step` | 2 | Runtime 自动执行时单节点最多重试次数 |
| `max_manual_run_retry_count` | 3 | 用户或后台手动重试 run 的上限 |
| `max_estimated_cost` | 2.0 | 单 run 估算成本上限，单位由部署配置定义 |
| `callback_max_attempts` | 5 | callback 最大派发次数 |
| `callback_retry_alert_threshold` | 5 | callback 连续失败达到该值后告警 |
| `outbox_retention_days` | 30 | delivered/dead-letter 事件审计保留期，payload 仍只允许安全摘要 |
| `signature_tolerance_seconds` | 300 | 入站和出站签名时间窗口 |
| `idempotency_ttl_days` | 7 | 入站 run 操作幂等记录保留时间 |
| `reconciliation_interval_seconds` | 300 | 对账任务扫描间隔 |
| `reconciliation_failure_threshold` | 3 | 同一对象连续修复失败后的升级告警阈值 |
| `pending_start_timeout_seconds` | 600 | 业务侧 pending_start 超过 10 分钟仍未绑定 run_id 时触发补偿 |

AgentPackage 可以收紧这些默认值，但不能放宽到超过 Runtime 全局上限。

`memoir_agent@1.0.5` 的待实现 `loop_policy` 固定使用 `inherit_run_limits_v1`，不新增
独立数字预算：它按上文公式继承 Run 冻结的剩余额度与模型 context window/route 容量，
任一必要全局预算缺失或耗尽即 fail closed，并始终取更严格限制。Scene、
图片和总素材不设业务数量上限，但也不得借循环绕过任何通用技术预算。

### 11.5 标准错误与治理分类

以下名称同时用于 Contract 错误码或内部治理分类；不适合作为接口响应的治理事件只进入安全审计和指标，不把内部细节返回调用方。

| 错误码 | retry | Runtime 行为 |
|---|---|---|
| `IDEMPOTENCY_CONFLICT` | 否 | 返回 HTTP 409，不覆盖首次请求结果 |
| `RUNTIME_OVERLOADED` | 按 `Retry-After` | run Admission 拒绝时不创建或推进；provider traffic 拒绝时不请求上游，由 model policy 在 deadline 内等待或 fallback |
| `MODEL_TIMEOUT` | 按 policy | 退避、显式 fallback 或失败 |
| `MODEL_PARSE_FAILED` | repair 后一次 | semantic validation 仍失败则 fallback |
| `TOOL_TIMEOUT` | 按工具策略 | 复用同一逻辑幂等键 |
| `TOOL_PERMISSION_DENIED` | 否 | 失败并记录安全审计 |
| `BUSINESS_DATA_INVALID` | 否 | 快照缺失或业务数据异常，失败并告警 |
| `SAFETY_BLOCKED` | 模板或人工审核 | 不发布高风险内容 |
| `COST_LIMIT_EXCEEDED` | 否 | 停止增强节点；必需产物未发布时进入 fallback/failed |
| `CALLBACK_SIGNATURE_INVALID` | 否 | 接收侧拒绝并告警，不推进业务状态 |
| `CALLBACK_OUT_OF_ORDER` | 否 | 只记审计，不覆盖较新状态 |
| `RECONCILIATION_NEEDED` | 对账策略 | 由对账任务修复或升级告警 |
| `INDIRECT_PROMPT_INJECTION` | 隔离/降级 | 不可信指令不能改变 workflow、工具、connector 或权限 |
| `GENERATION_SUPERSEDED` | 否 | 停止旧业务世代副作用，不覆盖当前作品 |
| `PACKAGE_REVOKED` | 否 | 取消 run，禁止 retry/resume |
| `PRIVATE_DATA_PURGED` | 否 | 丢弃迟到私密结果，禁止 retry/resume |
| `AUTHORIZATION_REVOKED` | 否 | 终止后续模型、工具和 callback，不切换身份 |
| `DISPATCH_FAILED` | 否 | 未认领 run 明确失败并生成 callback |
| `SEMANTIC_VALIDATION_FAILED` | repair/fallback | 不发布引用、数量或工具参数非法的结果 |

错误响应和持久记录只保存 `error_code + error_type + safe_message + retryable + details_visible_to_model` 等安全字段；默认不保存或暴露工具堆栈、内部地址、模型原文或私密输入。

## 十二、安全、隐私与运行治理

### 12.1 隐私原则

- 后端先脱敏，再调用 AI。
- 原文最小化外传。
- 工具输入输出只保存摘要。
- 模型完整 prompt 不进普通日志。
- 日记正文、赌局完整内容、图片私有签名、openid、token、手机号、地址不得入日志。

### 12.2 Guardrails

公共护栏：

- 输入 schema 校验。
- 输出 schema 校验。
- 工具权限校验。
- 敏感字段扫描。
- token / cost / step 限制。
- 工具结果压缩。
- trusted/untrusted 上下文隔离。
- 引用、数值和工具参数的确定性语义校验。
- authorization version 运行中复核。

业务护栏由 AgentPackage 补充。`MemoirAgent` 所有版本必须包含：

- 不评价关系对错。
- 不暗示复合。
- 不制造愧疚。
- 不使用刺激性分手词。
- 不编造不存在的事件。
- 素材引用必须可追溯到 snapshot material id。

数量和正文长度是 **AgentPackage 版本合同**，不是全局 Runtime 护栏：

| AgentPackage | 场景数 | 单场景 `body` | 用途 |
|---|---:|---:|---|
| `1.0.0`–`1.0.3` | 3–8 | 最多 80 字 | 旧 Run 恢复和历史产物的冻结行为 |
| `1.0.4` | 至少 3，不设上限 | 不设上限 | 当前按实际素材量生成，避免把合法长作品误判为整批失败 |
| `1.0.5`（待实现） | 至少 3，不设产品上限 | 不设产品上限 | 五类安全素材交错分批、模型动态编排；技术预算耗尽按覆盖判定 partial |

“不设产品上限”不会绕过资源治理：图片生成仍受节点墙钟预算、
逐张 lease 心跳/fencing、模型成本和 provider 并发限制；预算耗尽或租约
失效后剩余场景降级文字卡。正文仍必须通过
类型、敏感词、URL、引用和结构校验。

### 12.3 双重脱敏边界

| 层级 | 职责 |
|---|---|
| 情侣日记后端 | 权限过滤、删除过滤、跨段号过滤、手机号/openid/token/地址等强规则脱敏、图片私有 URL 处理 |
| Runtime `sanitize_materials` | 身份代称映射、长文本截断、敏感情绪片段打标、素材引用归一化 |
| ContextManager | 进入模型前二次扫描、token 预算、工具结果摘要压缩 |

如果后端已经过滤掉的敏感字段再次出现在 Runtime 中，视为 P0 隐私告警。Runtime 必须立即阻断当前 run 的模型/工具继续执行，转入 `waiting_human` 或 `failed`，并只保存脱敏后的告警摘要。

### 12.4 SSE 第一版路径

第一版前端生成进度基线：

```text
小程序前端 -> 情侣日记后端 HTTP 状态接口
  -> 响应携带 status_version/updated_at/retry_after_ms
  -> 按 retry_after_ms 退避轮询
  -> 进入后台、离页或终态后停止
```

H5 或已验证流式能力的平台可以由业务后端提供 SSE，并在断线时回退轮询。可选 SSE 使用约 15 秒 heartbeat、`Last-Event-ID`/事件序号恢复和唯一终态事件；Runtime 原生 `/events` SSE 放到二期。小程序正确性不能依赖 SSE。

### 12.5 数据生命周期与授权撤销

- AgentPackage Registry 管理 `active/deprecated/revoked`，安全撤销优先于 package digest 的可复现性。
- Runtime 每次新 execution attempt、模型调用、工具调用和 callback 前复核当前 authorization version；撤销后停止动作，不自动切换身份或 connector。
- privacy purge 先写 tombstone/version，再异步物理删除；所有私密 payload 写入使用 privacy version 条件。
- purge 后 run 禁止 retry/resume；cancel 成功不能视为清理完成。
- API、worker、dispatcher、reconciler 只依赖共享持久化恢复。Worker 进入 draining 后立即停止认领新 run，readiness 返回 503、liveness 保持成功；在途 Worker 继续为当前 lease heartbeat。run 在宽限期内完成则正常终止；先到安全 checkpoint 时先持久化 checkpoint，再主动让 lease 到期并停止全部写入；宽限期先耗尽时停止发起新模型/工具调用，让 lease 到期并停止全部写入。Admission 占用由 reaper 在 `claimed -> queued` 事务中迁移，新 Worker 创建新的 execution attempt。

### 12.6 观测对象

第一版必须形成权威持久记录；ReconciliationReport 可按 4.14 输出持久结构化日志/指标，RuntimeAuditEvent 可按 4.15 写入独立持久审计 sink：

- AgentRun
- AdmissionBucket
- AgentPlan
- AgentStep
- AgentToolCall
- AgentEvaluation
- AgentCheckpoint
- AgentArtifact
- AgentModelUsage
- CallbackEvent
- RuntimeOutboxEvent
- IdempotencyRecord
- ReconciliationReport
- RuntimeAuditEvent

第一版必须能按 run、execution attempt、step 和 caller/tenant 聚合：

- step/tool/model 成功率、耗时、attempt、fallback 与错误码。
- token、成本、model policy、route config version 和 capability snapshot。
- 模型候选 attempt 的 running/aborted_before_send/succeeded/failed/outcome_unknown、预留成本与观察到的实际成本；aborted 与未知结果必须分开统计，未知结果不得混入零成本成功率。
- held/queued/running 深度、queue wait、Admission 拒绝、provider permit wait/reject/TTL recovery/shared cooldown/circuit 和 lease heartbeat。

- package status、privacy state/version、purge 时延和迟到私密写入拒绝数。
- authorization version 变化、撤销拒绝、untrusted item、injection risk 与 semantic validation 失败数。

日志、span attribute、event 和 baggage 只能记录标识、计数和安全摘要，禁止携带 prompt、日记正文、工具原始 payload、签名媒体 URL、隐藏推理和 Checkpoint 内容。`thinking_summary` 只记录推理能力开关、预算或归一化参数。

外部 OpenTelemetry Collector、LangSmith 或调试样本导出默认关闭。启用前必须登记数据分级、采样字段、部署区域/跨境路径、保留期、访问审计和按 privacy purge 删除能力；调试样本先脱敏，敏感排查仅允许独立审计权限，不能把第三方平台当作 Runtime 权威存储。

二期再接 OpenTelemetry Collector、LangSmith 评测项目和可视化后台。

## 十四、验收标准

第一版完成后必须满足：

- 情侣日记后端能通过 `POST /api/v1/runtime/agent-runs` 创建 `memoir_agent@1.0.0` run。
- 合法签名的 `runtime-capabilities`、AgentRun 和 steps GET 不带 `Idempotency-Key` 时仍可访问；签名缺失或越权读取被拒绝，写接口缺少幂等键被拒绝。
- held run 在业务绑定 `active_run_id` 前不会执行工具或发出 `run_started`；同 key/hash 的 `/start` 重放首次响应，新 key 命中 queued/claimed 时不重复迁移 Admission 或创建 dispatch outbox。
- Runtime 创建成功但业务侧未绑定 `run_id` 时，`pending_start` 超过 600 秒会触发业务补偿；补偿复用原 create 幂等键恢复或明确失败，不创建第二个 run。
- 同一 Runtime 幂等键指向不同 `run_id` 时，因 normalized path 参与 request hash 而返回 `409 IDEMPOTENCY_CONFLICT`，不会命中空 body 的旧响应。
- AgentRun 查询返回当前 dispatch、status/event version 和 privacy version，业务后端能据此恢复 callback 摘要并确认 purge 终态。
- Runtime 能加载 `memoir_agent` AgentPackage。
- 同一 `agent_id + version` 内容变化时拒绝注册；revoked 后 create/start/retry/resume 与在途执行按规范停止。
- 相同 package 内容仅签名或构建时间等生成元数据变化时 digest 保持一致，真实受管文件变化时 digest 必须变化。
- Runtime 能生成静态 AgentPlan 并落库。
- Runtime 能执行 `load_snapshot -> generate_scenes -> persist_result` 等核心 workflow。
- Runtime 能调用 `memory.get_snapshot`，并通过 `memory.publish_playback_document` 原子发布包含 scenes/actions/`media_manifest` 的完整作品 revision；媒体关闭时空清单可发布，字段缺失、结构非法或 digest 不一致时不得切换 `published_revision`。
- Native/LangChain Tool adapter 的业务执行全部经过 ToolGateway，不能绕过 connector、授权、幂等和审计。
- Runtime 能保存 Step、ToolCall、Evaluation、Checkpoint、Artifact、ModelUsage。
- Package 生命周期、Checkpoint 解密读取、授权变化、approval/cancel/retry/purge 和敏感调试访问都有不含私密内容的持久 RuntimeAuditEvent。
- 详细 RuntimeEvent 契约可兼容演进，并能确定性映射为不含内部数据的安全 callback。
- 可能进入人工等待的 AgentPackage 必须启用 `waiting_human` callback；业务系统能接收该状态或通过主动查询对账恢复。
- workflow 进入 `waiting_human` 前已持久化恢复 checkpoint，并设置 `waiting_expires_at`、释放 lease 和 Admission 占用；人工等待超时后按 AgentPackage 的 `waiting_human_timeout_action` 恢复或终止，迟到审批不能覆盖超时结果。
- Runtime 能通过 ContextManager 管理 token 预算、工具结果摘要和敏感字段二次扫描。
- 模型 JSON 解析失败时能 repair 或 fallback。
- 多 Worker 竞争同一 provider/model 时不超过共享并发、RPM/TPM；acquired permit 崩溃后由 TTL 回收并回滚未发送预留，started permit 崩溃后只回收并发槽且保留速率预留；上游 429 的 Retry-After 对其他 Worker 生效。
- permit TTL 小于请求 timeout 与 settle margin 之和的 route 不能注册或宣告 capability 可用。
- route 缺少版本化价格、价格单位与 Runtime 预算单位不一致或价格配置非法时，不能注册或宣告 capability 可用；未知价格不得按零成本执行。
- 共享模型流量控制不可用时不退化为进程内无限请求；节点按显式 policy fallback 或安全失败。
- 模型请求等待 permit 或 usage 预写后、真正发送前若发生取消、lease/fencing 失效、package/authorization 撤销、privacy version 变化、route/capability 禁用或 deadline 到期，必须释放 permit、原子回滚该 permit 的 RPM/TPM 预留且不请求上游；已预写 usage 结算为 `aborted_before_send`。HTTP 请求开始后禁止再使用该状态。
- 模型请求发出后 Worker 崩溃或丢失 lease 时，迟到输出不能推进工作流；对应物理 attempt 保留为可结算 usage，无法确认结果时按 `outcome_unknown + reserved_estimated_cost` 保守计量。
- 工具超时能按策略重试或失败。
- side effect 工具重复调用不会重复写业务结果。
- 网络重试、checkpoint resume 和 worker 接管复用同一逻辑副作用幂等键，attempt 只用于审计。
- side effect 工具先持久化 running ToolCall、稳定幂等键和最终请求 digest，再发出请求；相同 key 不同 digest 返回幂等冲突且不重试。
- 相同 `Idempotency-Key` 且请求体一致时返回原结果，请求体不一致时返回幂等冲突。
- 幂等冲突返回 HTTP `409 Conflict` 和错误码 `IDEMPOTENCY_CONFLICT`。
- 媒体能力关闭时节点正常 `skipped(capability_disabled)`；开启后在发布前按场景串行生成图片，整个媒体节点受 `MEMOIR_MEDIA_NODE_BUDGET_SECONDS` 墙钟预算约束。图片生成会增加 Run 的发布前耗时；单场景失败只降级当前文字卡，预算耗尽后剩余场景降级，全部失败仍可发布纯文字 revision。
- callback 重复发送不会造成业务后端重复写入。
- callback 签名伪造、过期或 header/body 不一致时业务后端拒绝处理。
- callback 乱序到达时，业务状态不会被旧事件覆盖或倒退。
- Runtime 与业务后端状态不一致时，能通过对账任务或业务补偿恢复。
- held/queued/waiting_human 等没有有效 worker 的 run 可被 API 或对账任务直接终止；claimed run 采用协作取消。
- run_dispatch dead letter 重放失败后 run 进入 `failed(DISPATCH_FAILED)`，不会永久 pending/queued。
- AdmissionBucket 在 create/start/claim/waiting/terminal/cancel/reaper 的并发迁移后与 AgentRun 聚合结果一致，重复请求不重复占用或释放配额，计数永不为负。
- dispatcher 未启用某事件类型时不认领、不累计 attempt 或误入 dead letter；注册 callback 处理器后能投递原事件，且 callback 堆积不阻塞 run_dispatch。
- worker 失联接管后旧 worker 无法写入 Runtime 状态或重复推进业务副作用。
- 删除或新一轮生成后，旧 run 因 `generation_epoch + active_run_id` 无法切换 `published_revision`。
- purge 与迟到结果并发时，privacy version 写屏障阻止 Checkpoint/Artifact 私密内容复活。
- 日记、RAG 或工具结果中的提示注入不能改变 workflow、工具、connector、权限、统计和发布参数。
- 运行中授权撤销后，后续模型、工具和 callback 动作停止。

- 仅当业务后端已按有效业务规则创建 Archive 与 ready Snapshot 时，MemoirAgent 才可在素材稀疏场景生成基础卡片或触发模板兜底；手动生成要求所选范围内至少 7 篇共享日记和 2 个 `completed` 赌局，任一不足时业务后端不得创建 AgentRun；解绑时两类核心素材均为 0 时同样不得创建 AgentRun。门槛只属于 Business 资格判断，不进入 Runtime PolicyEngine。
