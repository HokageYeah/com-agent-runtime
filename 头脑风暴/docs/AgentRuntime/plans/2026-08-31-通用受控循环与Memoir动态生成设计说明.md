# 通用受控循环与 Memoir 动态生成设计说明

> 状态：设计冻结；`bounded_loop` 与 `memoir_agent@1.0.5` 已在当前工作区实现
> 并有自动化测试证据（2026-09-02 复核：Runtime 全量 `965 passed/16 skipped`，
> 聚焦五件套 `132 passed`），尚未提交、注册或部署，生产仍运行 `1.0.4`。
> 不得据此宣称生产注册、部署、切流或真实环境验证已经完成。
> 跨仓实施任务编号统一为 **R5**，对应 Runtime 总控/后端计划的 **Task 14 / R5**。

## 1. 目标与边界

本设计解决两个相互关联的问题：公共 Runtime 需要在静态、可审计的 DAG 内执行
有限循环；Memoir 需要让五类冻结素材都能进入生成链，由模型根据素材丰富度决定
场景数量和叙事组合，不再被单次“前 8 条素材、1～3 章”的隐性裁剪限制。

`bounded_loop` 不是 Autonomous Agent、动态 Planner 或自由工具循环。循环节点、
循环体、允许调用的模型、合并规则、预算和终止条件全部由不可变
AgentPackage 预先声明；业务输入、模型输出和工具结果均不能新增节点、修改路由、
扩大权限或放宽预算。首版通用 schema 的 allowed operations 只允许
`deterministic/model`，循环内任何 Tool 或副作用节点都在注册期拒绝；图片、Business
Tool、上传与发布继续位于循环外的普通静态节点。未来若要支持循环内 Tool，必须另行
提升内部合同版本并完整冻结幂等、恢复与审计语义，不能在 v1 中预留可执行分支。

## 2. `bounded_loop` 静态 DAG 合同

### 2.1 Package 声明

`workflow.graph.py` 新增 `node_type="bounded_loop"`，节点必须声明
`loop_policy`，且 Package 加载时一次性校验：

```python
{
    "node_id": "generate_scene_batches",
    "node_type": "bounded_loop",
    "next_nodes": ["finalize_scenes"],
    "safe_to_rerun": True,
    "loop_policy": {
        "cursor_source": "sanitized_material.materials",
        "budget_profile": "inherit_run_limits_v1",
        "allowed_operations": ["deterministic", "model"],
        "merge_strategy": "append_unique_by_key",
        "merge_key": "scene_id",
        "on_iteration_error": "continue",
        "on_budget_exhausted": "partial"
    }
}
```

- `inherit_run_limits_v1` 是唯一首版预算算法，不留实现者自选数字：`begin_loop` 从
  AgentRun 冻结的 `model_policy.max_model_calls/max_tokens/max_model_cost` 与
  `execution_policy.max_run_seconds` 读取剩余额度；任一字段缺失、非有限正值或余额为零
  时 fail closed。`iteration_limit = remaining_max_model_calls`，每轮至多一次模型调用；
  循环累计 token、费用与 active seconds 分别不得超过对应 Run 剩余额度，并继续受
  wall-clock、route 和 provider 更严格限制。Package/业务请求只能选择此 profile，不能
  传入或覆盖数值。
- 单轮切片算法同样冻结：按五类交错后的稳定顺序逐条追加完整安全 `text_digest`，每次
  追加前用既有 tokenizer/ContextManager 估算；仅当“固定 prompt + 已选条目 + 下一条”
  不超过 `ModelGateway.context_token_budget(route,prompt)` 且不超过 Run 剩余 token 时才
  加入。超出则当前批次结束并进入模型；单条本身仍超限视为 Snapshot 合同错误并
  fail closed，禁止截断 digest。该限制只约束单次上下文，不是总素材或总场景上限。
- `merge_strategy` 首版通用策略为 `append_unique_by_key`，Package 必须声明
  `merge_key`；Memoir 配置为 `scene_id`。重复 key 拒绝，不允许模型覆盖已验证批次。
- `allowed_operations` 首版只能是 deterministic/model 的非空子集；未知值、Tool、媒体、
  上传、发布或其他副作用节点一律拒绝注册。
- `on_iteration_error=continue` 只跳过当前无副作用内容批次；结构错误最多经过一次
  既有 repair。`on_budget_exhausted=partial` 进入统一收尾判定，不直接伪造成功。

### 2.2 Runner 状态

Runner 协议固定拆分为三个方法，不把生命周期留给实现者自行解释：

```text
begin_loop(loop_node, state, lease_context) -> LoopContext
run_loop_iteration(loop_context) -> LoopIterationResult
finalize_loop(loop_context, iteration_result) -> LoopResult
```

`LoopIterationResult.result` 与 `LoopResult.result` 只允许
`continue|complete|partial|failed`，其余公开字段只能是安全计数和受控原因码；素材、
处理位置、模型原文和工具 payload 不得进入返回值。`begin_loop` 建立内存态并执行首轮
门禁，`run_loop_iteration` 每次只执行一个受控 iteration，`finalize_loop` 负责确定性
merge/终止与节点完成边界，不得在三者之外引入隐式循环出口。

循环私密工作态仅存在于当前 Worker 内存：当前处理位置、当前批次素材、已验证 Scene、
已覆盖素材类型、已覆盖 source ref、失败批次索引和累计 token/成本。权威数据库只写
以下无内容审计计数：

- `iteration_index`、累计成功/失败批次数；
- `input_count/covered_ref_count/covered_type_count/scene_count`；
- 累计 model call、token、估算成本和 elapsed；
- 受控 `reason_code`、Package digest、privacy/authorization version、lease/fencing。

不得把 `sanitized_material`、批次正文、prompt、模型候选、Scene body、完整 Scene 或
PlaybackDocument 写入 AgentStep 输出、Checkpoint、Artifact、RuntimeEvent、callback、
public trace 或日志。循环结束后，完整 Scene 仍只在当前执行内存中流向发布工具。

### 2.3 预算与终止

每轮开始前和模型发送前都必须同时检查：循环 policy、AgentRun 全局 step/model/tool/
token/cost/active-time/wall-clock、route 输入输出窗口、取消、deadline、Package 状态、
privacy/authorization version 以及 lease/fencing。任何一项失效均不得再请求模型。

循环仅允许以下终止原因：`source_exhausted`、`loop_budget_exhausted`、
`run_budget_exhausted`、`cancelled`、`authorization_revoked`、`privacy_revoked`、
`lease_lost`、`package_revoked`。前两种进入内容收尾；其余沿既有 Run 终态规则停止。
循环次数不是 `AgentStep` 数，但每次物理模型调用都必须独立写 `AgentModelUsage`，并计入
Run 的 `max_model_calls/token/cost`，不能借一个循环 Step 绕过全局治理。

### 2.4 审计、恢复与重算

每轮只记录安全审计事件 `loop_iteration_started/finished/rejected`，字段限于 run/step/
node、iteration、batch item count、计数、耗时、usage id、`continue|complete|partial|failed`
结果和受控原因码。禁止记录处理位置对应的 source refs 或素材文本。

`bounded_loop` 首版只支持 `safe_to_rerun=True`。循环中途不写 checkpoint，也不保存
iteration、cursor、循环内容或已生成 Scene；只有整个 `bounded_loop` 节点完成后，才按
既有节点完成边界写安全路由 checkpoint。Worker 在节点中途崩溃、接管、显式 retry 或
resume 后必须重新读取当前获授权的同一 Snapshot，从节点起点按冻结排序完整重算。发布节点继续以稳定 logical key 执行
query-after-commit：如果完整文档已经提交则只对账，不因重算候选摘要漂移而再次发布。
循环内不存在 Tool，因此重算不会重复图片、Business Tool、上传或发布副作用；这些
循环外节点继续沿用既有稳定逻辑幂等键与 query-after-commit。

## 3. `memoir_agent@1.0.5` 动态生成

### 3.1 五类素材与排序

`1.0.5` 只消费 Snapshot v1 的 canonical `materials[]`：`diary`、
`completed_bet`、`handbook_note`、`matured_wish`、`bucket_list_completion`。
Business 提供的 `sanitized_payload.text_digest` 是五类合格素材进入模型的统一文本通道；
标记敏感或不合格的条目不进入模型正文。某个实际存在的合格类型缺少安全 digest 时，
Snapshot 合同不完整，Runtime 必须 fail closed，不得为满足覆盖而编造内容。

Runner 先按 material type 的固定顺序做轮询交错，再在各类型内保持 Snapshot 冻结顺序，
避免日记/赌局排在前面时长期挤掉可选素材。所有合格素材的安全 digest 都会被循环扫描；
不存在固定“只取全局前 N 条”。单轮切片大小由模型上下文和通用预算计算，不作为总素材上限。

### 3.2 静态工作流

新包使用以下不可变 DAG：

```text
load_snapshot -> sanitize_materials -> compute_stats
  -> prepare_scene_batches -> generate_scene_batches(bounded_loop)
  -> finalize_scenes -> generate_actions -> enqueue_media_tasks
  -> safety_review -> publish_document
```

`prepare_scene_batches` 确定性生成交错批次和 `available_material_types`；模型只决定每批
生成几个 Scene、场景主题、叙事形式、scene type、body、title word 与合法 source refs。
它不能决定批次、跳过安全校验、添加 scene/action 类型或调用工具。

`finalize_scenes` 负责去重、顺序和覆盖验证：第一张为 `cover`，最后一张为
`summary`；中间场景不按“日记时光/赌约回顾”固定分段，可以跨素材类型组合主题。
Scene 数量只保留至少 3 的产品下限，不设产品上限；实际数量由模型、素材量与 Runtime
技术预算共同决定。现有冻结 Scene/Action 枚举和 PlaybackDocument v1 wire 不变。

### 3.3 覆盖与 partial

“五类都要体现”定义为：Snapshot 中每个实际存在的合格素材类型，最终文档至少有
一个 Scene 的 `source_refs` 引用该类型。Business Snapshot v1 必须为五类合格素材提供
安全 `text_digest`；若某个实际存在类型缺少该投影，Runtime 必须以契约错误 fail closed，
不得把无来源卡片或编造内容计为覆盖。Scene 可以同时引用多个类型。

收尾采用以下确定性判定：

1. 全部安全素材批次处理完成、至少 3 个合法 Scene、所有实际存在类型均覆盖：循环结果
   为 `complete`，发布后内容/Run 结果按既有映射记为 `succeeded`。
2. 因循环/Run 预算或个别批次失败未处理完全部安全素材，但至少 3 个合法 Scene 且所有
   实际存在类型均覆盖：发布已有完整文档，循环结果为 `partial`、Run 记为 `partial`，安全摘要只报告未处理条目数、
   失败批次数和原因码。
3. 实际存在类型未全部覆盖：只允许一次 ModelGateway repair；输入只含缺失类型的受控
   安全 `text_digest` 与真实 `source_ref`，并执行与普通 iteration 相同的模型、token、
   费用、时间、授权、隐私和 fencing 检查。没有剩余模型许可/预算，或 repair 后仍未
   覆盖时，循环结果均为 `failed`。Runtime 不使用 deterministic 模板自行生成 Scene，
   不得把缺类作品、无来源卡或编造引用发布为 `complete`/`partial`。
4. 图片失败不改变文本内容的 succeeded/partial 判定。`enqueue_media_tasks` 仍对每个
   Scene 尝试一张图；单图失败或 900 秒媒体预算耗尽只把对应场景降级为文字卡，并记录
   `media_degraded` 安全计数。

业务 callback 继续使用既有 `partial_succeeded -> partial` 映射；业务端只能在收到与
当前 run/snapshot/epoch 匹配、且发布工具已提交 revision 的情况下确认 partial，不能由
callback 自行发布或推进 `published_revision`。

## 4. 契约与版本

- 新增 `bounded_loop/loop_policy` 属于 AgentPackage loader/executor 的内部公共能力，
  需要 Package schema 与加载器兼容测试，但不改变 Runtime HTTP API v1。
- `memoir_agent@1.0.5` 必须新建不可变目录并冻结 digest；`1.0.0`～`1.0.4` 的 prompt、
  graph 和 Runner 版本行为不得改写。
- Snapshot、Scene、Action、media manifest 与发布 Tool 字段不变时，PlaybackDocument
  `schema_version`、Runtime `contract_version` 继续为 `1.0.0`，Business Tool wire
  继续协商 `1.1.0`；Runtime wire 版本表、capabilities、部署模板和 Business 调用版本
  常量必须显式登记 `1.0.5`。
- 业务后端必须先保证五类 `text_digest` 投影和 `1.0.5` 发布接收兼容，再注册 Runtime
  新包，最后切换新 Run 的显式版本。磁盘存在新包不代表生产已启用；旧 Run 不迁移。
