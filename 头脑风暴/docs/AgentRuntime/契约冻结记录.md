## 已冻结的边界

- Runtime API：健康检查、capabilities，以及 AgentRun 的 create/start/query/retry/cancel/human-approval/purge 请求与响应模型均使用 `contract_version=1.0.0`。
- 状态与调度：Run 状态、`held -> queued -> claimed -> finished` 调度状态、held create/start、独立 active/held/queue/approval/wall-clock 时间预算遵循总控计划第 3 节。
- 事件：详细 RuntimeEvent 只映射到安全 callback 事件；模型、工具内部事件统一压缩为 `step_changed`，`waiting_human` 只允许显式启用该能力的 Package 使用。
- 工具与产物：Business Tool 只允许可信 connector 的相对路径，预留 MCP 元数据但不连接 MCP；Artifact 只保存版本、摘要、digest 和业务资源引用。
- 安全与可靠性：签名原文为 `{method}\n{path}\n{timestamp}\n{body_sha256}`，默认时间容忍 300 秒；写请求按 client + scope + key 幂等，request hash 覆盖 method、包含资源 ID 的 normalized path 和 body hash；事件序号在单个 Run 生命周期内单调递增。
- 并发与隐私：Worker 使用 lease/heartbeat/fencing 和 execution attempt；副作用键使用稳定逻辑操作键，不能包含物理 attempt；privacy version、authorization version、trusted/untrusted envelope 与语义校验是后续所有写入的前置条件。
- 生命周期与审计：Package 生命周期固定为 active/deprecated/revoked；AuditEvent 只记录无私密内容的操作摘要，生产环境必须具备持久且访问受限的审计 sink 才能 ready。

## 2026-08-31 待实现增量的冻结边界

- `bounded_loop` 仍是声明在受信 AgentPackage 中的**静态 DAG 节点**；循环体、出口、merge 和预算在注册时确定。它不得动态发现工具、生成新边、修改 connector 或把 Runtime 变成 Autonomous/ToolLoop Agent。
- `loop_policy.budget_profile` 首版唯一允许 `inherit_run_limits_v1`：从 AgentRun 冻结的剩余 `max_model_calls/max_tokens/max_model_cost/max_run_seconds` 计算有限上限，任一缺失、非有限正值或余额为零即 fail closed；`iteration_limit=remaining_max_model_calls` 且每轮至多一次模型调用。单批按稳定顺序完整追加安全 digest，追加后不得超过 `ModelGateway.context_token_budget` 与 Run 剩余 token，单条仍超限则契约失败且不截断。Package 和业务请求均不能传入自选数值。
- runner 每轮与每次模型发送前复核 fencing、privacy、authorization、cancel、deadline 和预算；循环内仅允许受控模型/确定性内容节点，Business Tool、媒体生成、上传和原子发布全部位于循环外。
- 循环状态只允许在当前 Worker 内存保存处理位置。循环中途不写 checkpoint；每轮可持久化 audit 仅含 iteration、已处理数量、模型调用/token/耗时计数、`continue|complete|partial|failed` 和受控结果码，不得包含素材正文、`text_digest`、source refs、prompt、模型原文、Scene 正文或媒体 URL。只有整个循环节点完成后才按节点完成边界写安全路由 checkpoint。
- retry/resume 不从循环中途续跑：必须按当前授权重新读取 Snapshot，从 `bounded_loop` 节点起点确定性全量重算。已提交发布/媒体副作用继续以稳定逻辑幂等键 query-after-commit；旧 lease/execution 的迟到结果不得推进新 execution。
- `memoir_agent@1.0.5` 新建独立版本目录并产生新 digest；`1.0.0`～`1.0.4` 的文件、digest、历史生成规则和已锁定 Run 均不可修改。部署顺序固定为 runner/loader 兼容能力先上线，再注册 `1.0.5`，最后由 Business 切换新 Run 的显式版本。
- Snapshot 五类 canonical material 继续为 `diary/completed_bet/handbook_note/matured_wish/bucket_list_completion`。`1.0.5` 只把安全 `sanitized_payload.text_digest` 送入模型，类型内保持冻结顺序、类型间轮转分批，并扫描全部合格素材；单轮切片由模型上下文与既有通用预算计算，不是总素材上限。
- 模型可按素材密度决定主题、形式和场景数量；最终文档只保留 `scene_count >= 3`，不新增 8/16 场景上限或 80 字单卡上限。每个最终 Scene 均产生一个循环外媒体尝试，但 provider/Run 时间与成本预算仍是安全上限，不等价于无限资源。
- 五类覆盖按“Snapshot 中实际存在的合格素材类型”计算，每类至少由一个 Scene 的真实 source_ref 引用。Business 必须为每类合格素材提供安全 `text_digest`；缺失时 Runtime 契约 fail closed，不能把敏感 payload、无来源卡或编造引用用于凑覆盖。
- 循环结果统一为 `continue|complete|partial|failed`。预算耗尽或局部批次失败后，若场景数和类型覆盖成立则结果为 `partial` 并可发布；缺失覆盖只允许一次受相同 ModelGateway/预算/guardrail 治理的 repair，输入为缺失类型安全 digest 与真实 source_ref。无剩余许可/预算或 repair 仍缺失均为 `failed`；Runtime 不用 deterministic 模板自行补写 Scene。单图失败或媒体预算耗尽只降低 enhancement，不回滚已发布文本主产物。

## 兼容性规则

- 新增 optional 字段可在同一 major 内发布；删除 required 字段、改变枚举含义或改变既有字段类型必须提升 major。
- `memoir_agent@1.0.0` 是首个 Workflow AgentPackage，后续版本通过新目录发布，不覆盖旧包；当前不支持 ToolLoopAgent、动态 Agent、完整 MCP 与 Runtime 原生 SSE。
- Runtime 模块固定在当前 com-agent-runtime 根工程的 `app/` 目录，权威运行数据已由 SQLAlchemy/Alembic 落地；Runtime 不连接情侣日记业务数据库。
