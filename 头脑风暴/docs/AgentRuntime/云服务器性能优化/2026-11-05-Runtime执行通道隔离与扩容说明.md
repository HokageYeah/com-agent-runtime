# Runtime 执行通道隔离与扩容说明

> 日期：2026-11-05
> 目标：让需要秒级返回的智能体（当前是 `soothe_agent`）不再被耗时几分钟的智能体（当前是 `memoir_agent`）挡住；并给出用户量增长后的扩容方法。
> 原则：只改 Runtime 的领取与部署，不改业务仓、不改智能体包、不做数据库迁移、不引入新中间件。
> 读者：实施本方案的开发者（含 Codex）、后续负责部署和扩容的人或智能体。

---

## 1. 为什么要做

### 1.1 2026-11-05 本地联调事故

| 时间 | 事件 |
|---|---|
| 14:53:13 | 测试账号解绑，业务端为双方各生成一份 `UNBIND_ARCHIVE` 回忆录作品 |
| 14:53:35 | 两条 `memoir_agent` Run 入队 |
| 14:53:44 | 用户提交 AI 帮哄（`soothe_agent`），Run 入队 |
| 14:53–15:00 | 唯一的 Worker 在执行回忆录：火山视觉 12 张图每张 25 秒超时，跑了 5 分钟以上 |
| 15:00:32 | 帮哄模拟器轮次超过业务 180 秒上限，判 `TIMEOUT` |
| 15:00:43 | 帮我回 Run 晚了 7 分钟才执行完；前端早已显示失败 |
| 15:01 之后 | Worker 空闲，后续帮哄全部在 6–16 秒内完成 |

### 1.2 根因（生产环境同样存在）

1. **只有一个 Worker，串行执行。**
   - `docker-compose.yml` 只有一个 `worker` 服务，本地 `agent-runtime.sh start` 也只起一个 Worker。
   - `WorkerLoop.run_once()` 逐个执行本轮领到的 Run。
2. **一次领走全部待派发任务。**
   - `app/dispatcher.py` 的 `dispatch_pending()` 会把所有 pending 的 `run_dispatch` 一次性领取，并只通知本 Worker。
   - 因此即使再加一个通用 Worker，先到的 Worker 仍可能把帮哄和回忆录一起领走，帮哄照样排在回忆录后面。
3. **回忆录天然很慢。**
   - 回忆录正常需要 1–3 分钟，媒体节点预算最长 900 秒（`MEMOIR_MEDIA_NODE_BUDGET_SECONDS`）。
   - 一次解绑会同时产生两条回忆录任务。

## 2. 方案：执行通道（lane）

### 2.1 概念

- **通道按“用户是否在页面上等结果”划分，不是一个智能体一个通道。**
  - `interactive`：用户在页面上等结果，要求秒级返回。例如 `soothe_agent`。
  - `default`：可以在后台慢慢跑的长任务。例如 `memoir_agent`。
- 智能体归属哪个通道写在部署配置里；没写的智能体自动归 `default`。
- Worker 启动时声明自己服务哪个通道。

### 2.2 配置

| 配置 | 位置 | 说明 |
|---|---|---|
| `RUNTIME_AGENT_LANES_JSON` | Runtime 私有 env | JSON 对象，`agent_id → 通道名`。默认 `{}`，表示全部归 `default`。当前取值：`{"soothe_agent":"interactive"}` |
| Worker `--lane` | 启动参数 | 默认 `default`。interactive Worker 传 `--lane interactive` |
| Worker `--worker-id` | 启动参数 | 每个 Worker 进程必须唯一，lease 归属依赖它 |

**校验规则（启动即检查，错误不得静默）：**
- JSON 不是对象、键或值不是字符串：启动失败。错误码沿用现有风格，例如 `RUNTIME_AGENT_LANES_JSON_INVALID`。
- 通道名必须匹配 `^[a-z][a-z0-9_]{0,31}$`。
- `agent_id` 必须是本 Runtime 已部署的智能体包（复用现有包发现逻辑，不在代码里写死列表）。写错名字要直接失败，不能当成 `default`。
- Worker 的 `--lane` 不是 `default`、但配置里没有任何智能体映射到它：打 WARNING 后继续运行（只是领不到任务），不能让容器反复重启。

### 2.3 领取规则

| Worker 通道 | 领取哪些 `run_dispatch` |
|---|---|
| `default` | **所有通道**的任务（兜底）。interactive Worker 没部署或挂了时，帮哄仍能跑，只是退化为排队 |
| 其他通道（如 `interactive`） | 只领 `agent_id` 映射到本通道的任务 |

- **每轮最多领 1 条 `run_dispatch`，按入队先后（outbox 主键升序）领取。**
  - default Worker 在执行回忆录时不会去领新任务，所以抢不到帮哄。
  - 同一通道开多个 Worker 时，任务能平均分配。
- **回调（callback）投递和过期 lease 回收不分通道**，任何 Worker 照旧处理。
- 对账器（reconciler）重放 `run_dispatch` 的逻辑不变；重放出的 outbox 仍按上述规则领取。

### 2.4 部署拓扑（当前，注册用户不到 10 人）

| 服务 | 命令 | 说明 |
|---|---|---|
| `api` | 不变 | |
| `worker` | `app.worker --worker-id agent-runtime-worker`（通道 `default`） | 原服务，行为改为“每轮领 1 条” |
| `worker-interactive`（新增） | `app.worker --lane interactive --worker-id agent-runtime-worker-interactive` | 只跑帮哄 |
| `reconciler` | 不变 | |
| `launcher` | 不变（production 默认仍停用） | |

本地 `./agent-runtime.sh start development` 同样启动两个 Worker。

### 2.5 解决什么、不解决什么

**解决：**
- 帮哄不再被回忆录这类长任务挡住，排队最多只等其他帮哄（每条约 8 秒）。
- 不会再出现“前端显示失败、几分钟后后台又成功了”。
- 新增智能体通常只改配置，不改代码。

**不解决：**
- 帮哄自身的并发容量：一个 interactive Worker 约每分钟 7 轮，扩容方法见第 3 节。
- 第三方变慢（DeepSeek、微信内容检测）。
- 回忆录之间仍然排队（没有秒级要求，可接受）。
- 回忆录自身问题（火山视觉超时/签名错误、重试时 `LOOP_SUMMARY_MISSING`），由回忆录侧单独处理。

## 3. 容量与扩容指南

### 3.1 当前容量估算

- 帮哄一轮约 8 秒：模型约 4 秒，输出内容安全检测约 3 秒，其余约 1 秒。
- 一个 interactive Worker ≈ **每分钟 7 轮**。业务超时上限 180 秒，所以同一时刻排队的帮哄超过约 20 轮，就会开始出现超时。
- 当前注册用户不到 10 人，1 个 interactive Worker 足够。

### 3.2 观测指标（扩容前先看数据）

在 Runtime 库执行，只读：

```sql
-- 各智能体最近 24 小时的排队时长（入队到开始执行，秒）
SELECT agent_id,
       COUNT(*) AS runs,
       ROUND(AVG(TIMESTAMPDIFF(SECOND, queued_at, started_at)), 1) AS avg_wait_s,
       MAX(TIMESTAMPDIFF(SECOND, queued_at, started_at)) AS max_wait_s
FROM agent_runs
WHERE queued_at >= NOW() - INTERVAL 1 DAY AND started_at IS NOT NULL
GROUP BY agent_id;
```

在业务库执行，只读：

```sql
-- AI 帮哄最近 24 小时的超时率（时间列为 UTC naive）
SELECT COUNT(*) AS turns,
       SUM(error_code = 'TIMEOUT') AS timeouts,
       ROUND(100 * SUM(error_code = 'TIMEOUT') / COUNT(*), 2) AS timeout_pct
FROM soothe_turns
WHERE created_at >= UTC_TIMESTAMP() - INTERVAL 1 DAY;
```

### 3.3 什么时候做什么

| 信号 | 动作 | 是否改代码 |
|---|---|---|
| `soothe_agent` 平均排队 > 10 秒，或最大排队 > 60 秒 | 给 interactive 通道加 Worker（3.4） | 否 |
| 帮哄超时率 > 1% | 先看排队时长：排队长就加 Worker；排队短说明是模型或内容检测慢，查 Provider | 否 |
| 回忆录排队明显变长，用户投诉生成太慢 | 给 default 通道加 Worker（3.4） | 否 |
| 新增一个用户在页面等结果的智能体 | 在 `RUNTIME_AGENT_LANES_JSON` 里加一行，归 `interactive` | 否 |
| 新增一个长任务智能体 | 什么都不用做，自动归 `default` | 否 |
| 新的长任务（如视频生成）会拖慢回忆录 | 新增通道（如 `heavy`）+ 新 Worker 服务（3.5） | 否 |
| 单台服务器内存/CPU 撑不住更多 Worker | 进程内并发或拆机器（3.6） | 是 |

### 3.4 给某个通道加 Worker

在 Runtime 的 `docker-compose.yml`（以及 `docker-compose.production.yml` 和 `docker-compose.test.yml` 中对应的覆盖块）里，复制一份同通道的服务，**换一个唯一的 worker-id**：

```yaml
  worker-interactive-2:
    # 与 worker-interactive 相同的镜像、env、依赖、加固配置
    command: ["python", "-m", "app.worker", "--lane", "interactive", "--worker-id", "agent-runtime-worker-interactive-2"]
```

注意：
- **不要用 `docker compose up --scale`**：副本会共用同一个 worker-id，lease 归属会混乱。
- 每加一个 Worker 大约多占一个 Python 进程的内存。先用 `docker stats` 看服务器余量。
- GitHub Actions 中校验服务集合的步骤需要同步加上新服务名。
- 部署后在日志里搜 `Worker 启动`，确认新 Worker 的通道与 ID。

### 3.5 新增一个通道

1. 在私有 env 的 `RUNTIME_AGENT_LANES_JSON` 里把对应智能体映射到新通道，例如 `{"soothe_agent":"interactive","video_agent":"heavy"}`。
2. 按 3.4 的方式新增 `worker-heavy` 服务，启动参数 `--lane heavy`。
3. `stop_grace_period` 按该智能体最长节点预算设置（参考回忆录 Worker 的 16 分钟）。
4. 同步 Actions 的服务集合校验、`ENV_CONFIG.md` 和部署文档。

### 3.6 更远期（单机放不下更多 Worker 时才考虑）

- **进程内并发**：一个 Worker 进程同时执行多个 Run，需要改造执行器与 lease 心跳。
- **拆机器**：Worker 与 API 分开部署到多台机器，共享同一个 Runtime 数据库。现有 lease + fencing 已支持多 Worker 并发领取。
- **外部队列**：目前不需要。数据库 outbox 在每分钟数百轮以内都够用。

## 4. 部署配置操作手册

### 4.1 首次上线本方案

1. 服务器 Runtime 私有 env 增加一行（与其他 JSON 配置写法一致）：

   ```bash
   RUNTIME_AGENT_LANES_JSON={"soothe_agent":"interactive"}
   ```

2. 按正常流程部署 Runtime（GitHub Actions）。新服务 `worker-interactive` 会随 compose 一起启动。
3. 验证：
   - `docker compose ps` 能看到 `worker` 和 `worker-interactive` 都在运行。
   - 日志中两个 Worker 的启动行分别带 `lane=default` 和 `lane=interactive`。
   - 小程序里提交一次帮哄，日志里该 run 由 `agent-runtime-worker-interactive` 领取。

### 4.2 回滚

- **只想关掉隔离**：删掉 `RUNTIME_AGENT_LANES_JSON`（或设为 `{}`）。interactive Worker 会领不到任务并打 WARNING，所有任务由 default Worker 执行，恢复到改造前的行为（但仍是每轮领 1 条）。
- **彻底回滚**：回退 Runtime 代码版本并重新部署。本方案不涉及数据库结构变化，回滚没有数据风险。

## 5. 实施范围（供开发者）

| 文件 | 改动 |
|---|---|
| `app/core/config.py` | 新增 `RUNTIME_AGENT_LANES_JSON`，提供解析与校验，写法参考 `agent_model_node_routes` |
| `app/dispatcher.py` | `run_dispatch` 按通道筛选、按主键升序、每轮最多领 1 条；其他事件类型行为不变 |
| `app/worker.py` | 新增 `--lane`；把通道传给 Dispatcher；启动日志带通道；无映射时 WARNING |
| `app/scripts/agent_runtime_cli.py` | 本地 `start` 启动 default + interactive 两个 Worker |
| `docker-compose.yml` / `.production.yml` / `.test.yml` | 新增 `worker-interactive` 及对应覆盖块 |
| `.github/workflows/com-agent-runtime.yml` | 服务集合校验加入 `worker-interactive` |
| `docker/backend/*.env.example`、`configure-runtime-env.sh`（如涉及） | 增加 `RUNTIME_AGENT_LANES_JSON` 示例 |
| `ENV_CONFIG.md`、`README.md`、`docker/backend/DOCKER_DEPLOY.md` | 说明配置与新服务，链接本文 |
| `tests/` | 通道筛选、每轮 1 条与 FIFO、default 兜底、配置校验、Worker 参数、CLI 进程列表、compose 服务集合 |

**非目标：** 业务仓、智能体包、数据库迁移、回忆录逻辑、外部队列、进程内并发。
