
## 二、核心设计原则

### 2.1 敏感操作低权重展示

“解绑”和“拉黑”都不是鼓励用户频繁点击的主路径，因此入口必须低权重：

- 已绑定态“我的”页只展示“管理关系”入口，不直接暴露强操作按钮。
- 关系管理页中，“申请解绑”使用次级按钮或普通卡片按钮。
- “拉黑对方”使用更低位置、更严肃文案和更明显的二次确认。

### 2.2 后果先说明，再执行

用户点击任何解除关系动作前，页面必须说明后果：

- 和平解绑：需要对方同意；7 天未处理会失效；同意后关系解除并进入回忆录归档流程。
- 强制拉黑：无需对方同意；立即解除关系；双方 7 天内不可重新绑定；冷却结束后不会自动恢复关系。

### 2.3 温柔视觉，不弱化风险

全局视觉仍然使用暖粉、圆角、轻阴影，但不能把强制拉黑包装成“普通设置项”。

- 和平解绑可使用豆沙红、浅粉边框和柔和提示。
- 强制拉黑应使用更深的豆沙红、明确警示图标和确认文案输入。
- 不使用刺眼纯红大面积铺底，避免破坏产品整体气质。

## 三、页面信息架构

### 3.1 关系管理页结构

页面结构固定为：

1. 顶部导航栏
2. 当前情侣关系卡片
3. 关系状态说明卡片
4. 和平解绑操作区
5. 强制拉黑操作区
6. 底部说明与帮助文案

### 3.2 和平解绑申请弹窗结构

弹窗必须挂载在页面层，使用公共 `xxt-common-modal`：

1. 标题：“申请和平解绑”
2. 说明：对方同意后才会解除关系
3. 后果清单：回忆录归档、7 天有效期、拒绝后关系保持
4. 主按钮：“确认申请”
5. 次按钮：“再想想”

### 3.3 解绑处理卡片结构

当当前用户收到对方的解绑申请时，关系管理页顶部展示待处理卡片：

1. 发起方头像与昵称
2. 发起时间与过期时间
3. 申请说明
4. “同意解绑”按钮
5. “拒绝解绑”按钮

### 3.4 强制拉黑确认结构

强制拉黑必须比和平解绑多一层确认成本：

1. 第一次确认弹窗：说明立即解除与 7 天冷却
2. 确认文案输入：用户必须输入 `确定拉黑`
3. 第二次确认按钮：输入正确后才可点击
4. 成功后跳转或刷新为拉黑冷却期状态

## 四、状态展示规则

### 4.1 已绑定态

- 展示双方头像、昵称、绑定天数。
- 主提示为“你们正在共享情侣空间”。
- 入口为“管理关系”，不直接展示“解绑 / 拉黑”。

### 4.2 解绑申请中

- 发起方看到“等待对方处理”，参考 [code/和平解绑待处理/code.html](./code/和平解绑待处理/code.html)。
- 接收方看到“对方申请解除关系”，参考 [code/对方处理申请/code.html](./code/对方处理申请/code.html)。
- 双方都应看到过期时间。
- 关系仍然保持 `BOUND` 的业务可用状态，但状态提示必须明确“有待处理解绑申请”。
- 发起方页面必须提供“撤回申请”弱入口，撤回前必须二次确认。
- 撤回申请只关闭当前待处理申请，不解除关系、不触发回忆录归档、不清空双方关系数据。
- 撤回成功后，发起方和接收方都回到普通 `BOUND` 关系展示；接收方原处理入口必须失效。
- 接收方页面必须把“同意解绑”和“拒绝继续保持关系”视觉区分开：同意是高后果动作，需要二次确认；拒绝是保持关系，也需要轻确认。

### 4.3 已解绑归档态

- 展示“关系已解除，回忆已归档”。
- 不自动跳回绑定页，先给用户解释状态变化。
- 提供“返回我的页”和“重新进入绑定流程”的低权重入口。

### 4.4 拉黑冷却期

- 展示冷却截止时间，参考 [code/拉黑冷却期/code.html](./code/拉黑冷却期/code.html)。
- 禁用邀请、输入邀请码、扫码绑定等关系建立入口。
- 明确说明：冷却结束后只是恢复重新绑定资格，不会自动恢复原关系。
- 底部导航仍可保留，但涉及共享关系的页面入口应降权或由业务接口兜底拦截。
- 禁用按钮不能只做灰色样式，点击后也必须提示“冷却期内暂不可绑定”，避免用户以为页面坏了。

## 五、交互规则

- 点击“申请和平解绑”前必须弹出二次确认。
- 点击“撤回申请”前必须弹出二次确认，并说明撤回后关系保持绑定。
- 点击“同意解绑”前必须弹出二次确认。
- 点击“拒绝解绑”可使用轻确认，但仍要说明拒绝后关系保持。
- 点击“强制拉黑”必须输入确认文案 `确定拉黑`。
- 接口失败时由公共请求层展示后端失败文案，页面只负责关闭 loading、恢复按钮状态和保留当前表单。
- 每次关系操作成功后，必须重新调用关系查询接口刷新 `relationshipStatus`，不能只靠本地推断。

---

## 六、组件复用要求

- 顶部导航优先使用 `xxt-top-app-bar`。
- 二次确认弹窗必须使用 `xxt-common-modal`。
- 底部说明和风险说明可复用 `tui-text`、`tui-icon` 和普通卡片结构。
- 页面背景如需恋爱氛围动效，优先使用 `xxt-romantic-bg`，但强制拉黑确认弹窗内不使用强动效。

## 七、文案基线

| 场景 | 推荐文案 |
|---|---|
| 关系管理页标题 | 管理我们的关系 |
| 和平解绑入口 | 申请和平解绑 |
| 和平解绑说明 | 这会向 TA 发送解绑申请，对方同意后关系才会解除。 |
| 解绑待处理 | TA 申请解除关系，请在 7 天内处理。 |
| 撤回申请入口 | 撤回申请 |
| 撤回申请确认 | 撤回后关系会继续保持绑定，对方将不再看到处理入口。 |
| 同意解绑确认 | 同意后关系会解除，共同回忆将进入归档流程。 |
| 强制拉黑入口 | 强制拉黑对方 |
| 强制拉黑说明 | 该操作会立即解除关系，并让双方 7 天内无法重新绑定。 |
| 冷却期说明 | 冷却结束后只恢复重新绑定资格，不会自动恢复关系。 |

## 八、验收标准

- 已绑定态从“我的”页能进入关系管理页。
- 和平解绑申请、处理、拒绝、过期都有清晰状态展示。
- 强制拉黑必须经过确认文案输入，不能误触。
- 拉黑冷却期禁用绑定入口，并展示冷却截止时间。
- 所有敏感操作都符合全局暖粉视觉，但风险文案明确、不含糊。
