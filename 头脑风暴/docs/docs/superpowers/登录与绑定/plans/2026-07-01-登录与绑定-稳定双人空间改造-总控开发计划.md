# 登录与绑定稳定双人空间改造 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在已完成的登录、绑定、和平解绑、强制拉黑闭环上，补齐“同一对用户复用稳定双人空间 `space_id`、每次重新绑定递增 `relationship_segment_no`”的数据模型、接口契约和前端状态同步。

**Architecture:** 本计划是设计变更补充计划，不重写 2026-06-17 与 2026-06-29 已完成计划。后端新增稳定双人空间模型并把绑定创建、解绑、拉黑统一收口到同一段号规则；前端只消费后端返回的空间与段号上下文，不在本地推导空间归属。

**Tech Stack:** FastAPI + MySQL + SQLAlchemy + Alembic + UniApp/Vue3/TypeScript + Pinia。

## Global Constraints

- 需求主定义以 [../需求设计文档.md](../需求设计文档.md) 为准，本计划只补执行顺序和验收边界。
- 同一对用户重新绑定时必须复用原 `space_id`，并创建新的 `relationship_segment_no`。
- 用户换人绑定时必须进入新的 `space_id`，绑定段号从 `1` 开始。
- `space_id` 表示两个人长期共同数据归属；`relationship_id` 表示一次具体绑定关系；`relationship_segment_no` 表示该空间下第几段关系。
- 解绑或拉黑只关闭当前关系段，不删除稳定双人空间。
- 回忆录归档边界必须是 `space_id + relationship_segment_no`，本轮只产生可归档上下文，不实现回忆录模块。
- 前端、后端新增或修改字段必须补中文业务注释。
- 不把真实业务写入 `demo_*`；后端继续使用 `auth_*`、`relationship_*` 正式业务域。

## 2. 为什么新增计划而不是改写旧计划

旧计划已经包含执行记录、测试结果和验收状态，直接重写会破坏历史事实。稳定双人空间是已完成模块上的契约变更，合理做法是新增补充计划，并在旧计划入口中引用它；这样后续 LLM 能区分“已完成 MVP”和“新设计变更”。

## 3. 核心判断

【核心判断】
✅ 值得做：这是底层数据归属问题，不改会导致重绑后赌局、日记、回忆录口径互相打架。

【关键洞察】
- 数据结构：`couple_space` 是长期双人归属，`couple_relationship` 是一段关系，业务数据引用两者加段号。
- 复杂度：不要让业务模块各自判断“是不是同一对人”，统一由关系模块下发 `space_id` 和当前段号。
- 风险点：历史已完成绑定数据需要补齐空间和段号，不能让旧用户重绑后丢失历史数据。

【Linus式方案】
1. 先建正确的数据结构：稳定空间表 + 关系段号字段。
2. 把绑定创建变成“查空间、递增段号、创建关系”一个原子流程。
3. 所有接口只返回后端算好的上下文，前端别猜。
4. 保留旧接口路径和状态枚举，避免破坏前端已完成页面。

## 4. 契约冻结

### 4.1 新增/强化字段

| 字段 | 所属 | 说明 |
|---|---|---|
| `space_id` | `couple_relationships`、关系响应 | 同一对用户长期复用的双人空间 ID |
| `relationship_segment_no` | `couple_relationships`、关系响应 | 当前关系属于该空间下第几段绑定 |
| `current_segment_no` | `couple_spaces` | 当前空间已创建到第几段关系 |
| `current_relationship_id` | `couple_spaces` | 当前有效关系 ID；解绑、拉黑或未绑定时为空 |
| `user_low_id` / `user_high_id` | `couple_spaces` | 排序后的双方用户 ID，用于保证 A+B 与 B+A 命中同一空间 |

### 4.2 关系查询响应要求

`GET /api/v1/relationship/me` 当前真实契约是直接返回 `CoupleRelationshipInfo`，本次改造必须保持这个外形，不能为了新字段把响应改成 `relationship/space` 嵌套对象。正确做法是在原 data 对象上追加字段：

```json
{
  "status": "BOUND",
  "coupleId": 1001,
  "relationshipId": 1001,
  "spaceId": 88,
  "relationshipSegmentNo": 2,
  "currentSegmentNo": 2,
  "currentRelationshipId": 1001,
  "boundAt": "2026-07-01T10:00:00+00:00",
  "partner": {}
}
```

兼容规则：

- `coupleId` 是历史字段，当前代码里实际写的是 `relationship.id`，本轮保留它作为旧前端兼容字段，不再把它解释成稳定空间 ID。
- `relationshipId` 是新增明确字段，语义等同当前这一次绑定关系 ID。
- `spaceId` 是新增稳定空间字段，业务模块恢复历史数据时使用它。
- `relationshipSegmentNo` 是新增分段字段，回忆录按段归档时使用它。
- 前端只使用后端返回字段，不允许按双方用户 ID 在前端拼 `space_id`。

### 4.3 绑定创建规则

```text
输入绑定码
  -> 后端确认双方用户 ID
  -> 后端按 min(user_id), max(user_id) 查找 couple_space
  -> 不存在则创建 couple_space，current_segment_no=0
  -> 校验双方当前没有其他有效关系
  -> 校验双方没有未结束拉黑冷却
  -> current_segment_no + 1 得到新 relationship_segment_no
  -> 创建 couple_relationship(space_id, relationship_segment_no, status=BOUND)
  -> 更新 couple_space.current_segment_no 与 current_relationship_id
  -> 返回最新关系上下文
```

## 8. 风险与处理

- 历史关系没有 `space_id`：迁移必须按双方用户 ID 回填，且同一对历史关系归并到同一空间。
- 并发绑定可能重复创建空间：后端需要数据库唯一约束和事务，不能只靠 service 查询。
- 前端缓存旧关系状态：绑定、解绑、拉黑成功后必须重新拉取 `/relationship/me`。
- 业务模块可能继续只用 `relationship_id` 查询历史：后续打赌、日记必须改为默认按 `space_id` 查询。
