## 2. 核心原则

- 绑定成功才算正式登录完成，微信授权成功不等于产品可用。
- 前端负责流程推进、视觉还原和状态展示；后端负责身份、关系、邀请码、唯一性、冷却期等强规则。
- 接口契约先冻结，再分别开发前后端，避免联调时字段互相漂移。
- 新增业务模块不能写入 `demo_*`，后端新增 `auth_*` 和 `relationship_*`。
- 前端不能继续保留脚手架绿色登录页，需要按设计稿切换为暖粉情侣日记视觉。
- 所有核心逻辑保留中文注释和可搜索日志。

## 3. 契约冻结

### 3.1 统一响应

所有后端接口仍返回：

```json
{
  "platform": "AUTH",
  "api": "api/v1/auth/wechat-login",
  "data": {},
  "ret": ["SUCCESS::微信登录成功"],
  "v": 1
}
```

### 3.2 状态枚举

```text
RoleTag: HE / SHE
RelationshipStatus:
  UNBOUND
  INVITING
  BOUND
  UNBIND_REQUESTED
  UNBOUND_ARCHIVED
  BLOCK_COOLDOWN
```

### 3.3 接口清单

| 接口 | 方法 | 责任 |
|---|---|---|
| `/api/v1/auth/wechat-login` | POST | 微信 code 登录、创建/更新用户、签发 token |
| `/api/v1/auth/me/profile` | PATCH | 更新当前登录用户昵称 |
| `/api/v1/relationship/me` | GET | 查询当前用户关系状态 |
| `/api/v1/relationship/invites` | POST | 生成或复用我的邀请码 |
| `/api/v1/relationship/invites/{binding_code}` | GET | 预览邀请方信息 |
| `/api/v1/relationship/bind` | POST | 输入邀请码完成绑定 |

### 3.4 前端正式登录判定

```ts
const formalLoggedIn = userStore.isLogin && userStore.relationshipStatus === 'BOUND';
```

如果 `isLogin === true` 但 `relationshipStatus !== 'BOUND'`，只能进入绑定流程，不能把来源页刷新为已登录可用态。

## 7. 风险与处理

- 微信真实 `code2session` 依赖线上 appid/secret：测试必须 mock，开发环境使用 `.env.development.local` 配置。
- 当前前端请求 base URL 由环境变量控制：联调前确认 `VITE_GLOB_API_URL` 和 `VITE_GLOB_API_URL_PREFIX`。
- 当前项目没有完整前端单测体系：以 `type-check`、小程序构建和手工链路验证作为本阶段最小验收。
- 绑定唯一性存在并发风险：后端 service 校验之外，数据库层需要唯一索引或事务保护。
- 角色标签首次设置不可修改：后端必须拒绝已存在用户修改角色，前端只做提示不能作为强约束。
