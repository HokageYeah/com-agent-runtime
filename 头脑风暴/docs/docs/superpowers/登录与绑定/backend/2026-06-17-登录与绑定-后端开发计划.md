# 登录与绑定后端 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在 `backend/couple-diary-b` 中新增登录与情侣关系模块，提供微信登录、会话 token、角色标签、邀请码绑定、关系查询和后续解绑/拉黑扩展基础。

**Architecture:** 后端新增 `auth_api` 与 `relationship_api` 两个正式业务路由，业务逻辑下沉到 service，schema 单独定义，持久化模型独立于 `diary_*`。微信登录采用小程序常见的 `wx.login code -> 后端 code2session -> openid -> user/session token` 模式；测试中 mock 微信接口与数据库服务，确保接口契约先稳定。

**Tech Stack:** FastAPI、Pydantic v2、SQLAlchemy 2、Alembic、MySQL、httpx、pytest、ruff、loguru。

## 1. 成功标准

- `/api/v1/auth/wechat-login` 能接收微信 code 和角色标签，返回 token、用户信息、关系状态。
- `/api/v1/auth/me/profile` 能在鉴权后更新当前用户昵称，昵称最多 5 个字，且不会越权修改其他用户。
- `/api/v1/relationship/me` 能返回当前用户关系状态。
- `/api/v1/relationship/invites` 能为未绑定用户生成唯一邀请码。
- `/api/v1/relationship/invites/{binding_code}` 能预览邀请方基础信息。
- `/api/v1/relationship/bind` 能校验邀请码并创建一对一情侣关系。
- 已绑定用户不能重复发起或接受绑定。
- 邀请码过期、绑定自己、绑定已绑定用户、拉黑冷却期等情况有明确错误。
- 统一响应格式保持 `platform/api/data/ret/v`，新增平台枚举不破坏既有 demo/diary 测试。
- 新代码包含中文注释和关键日志，敏感信息不写入日志。
- 执行 `poetry run ruff check app tests` 与 `poetry run pytest` 通过。

## 3. 数据模型

### `couple_users`

```text
id bigint pk
openid varchar(128) unique not null
nickname varchar(100) nullable
nickname_updated_by_user boolean default false
avatar varchar(512) nullable
role_tag enum/string HE|SHE not null
role_locked_at datetime nullable
created_at datetime
updated_at datetime
```

### `auth_sessions`

```text
id bigint pk
user_id bigint index not null
token_hash varchar(128) unique not null
expires_at datetime not null
revoked_at datetime nullable
created_at datetime
```

### `couple_relationships`

```text
id bigint pk
user_a_id bigint not null
user_b_id bigint not null
status string not null  # BOUND / UNBOUND_ARCHIVED
bound_at datetime
unbound_at datetime nullable
created_at datetime
updated_at datetime
unique active relationship constraint handled by service + indexes
```

### `binding_invites`

```text
id bigint pk
binding_code varchar(32) unique not null
inviter_user_id bigint not null
status string not null  # ACTIVE / USED / EXPIRED / CANCELLED
expires_at datetime not null
used_by_user_id bigint nullable
used_at datetime nullable
created_at datetime
```

### `relationship_blocks`

```text
id bigint pk
blocker_user_id bigint not null
blocked_user_id bigint not null
cooldown_until datetime not null
created_at datetime
```

### Task 5: Relationship Service

**Files:**
- Create: `backend/couple-diary-b/app/services/relationship_service.py`
- Test: `backend/couple-diary-b/tests/test_relationship_api.py`

- [ ✅ ] **Step 1: 查询我的关系**

若存在 active relationship，返回 `BOUND`、`couple_id`、`bound_at`、`partner`。

若不存在，检查拉黑冷却期；有冷却返回 `BLOCK_COOLDOWN`，否则返回 `UNBOUND`。

- [ ✅ ] **Step 2: 生成邀请码**

规则：

- 用户已绑定：`HTTPException(409, "当前已绑定另一半，不能重复生成邀请码")`
- 拉黑冷却中：`HTTPException(403, "拉黑冷却期内暂不可绑定")`
- 复用未过期 ACTIVE 邀请，否则生成 6 位大写字母数字码。
- 默认过期时间建议 24 小时。

- [ ✅ ] **Step 3: 预览邀请码**

校验存在、ACTIVE、未过期，返回邀请方昵称头像和角色。

- [ ✅ ] **Step 4: 绑定邀请码**

必须按顺序校验：

1. 邀请码存在且未过期。
2. 接收方不能绑定自己。
3. 发起方和接收方都未处于 active relationship。
4. 双方不存在有效拉黑冷却。
5. 创建 `couple_relationships`。
6. 标记 invite 为 USED。

## 5. 业界实践校准

- 微信 openid 只在后端保存，前端使用业务 token。
- token 明文只返回一次，数据库存 hash，降低泄露风险。
- 关系唯一性以后端 service 和数据库索引共同保证，避免前端竞态绕过。
- 邀请码设置过期时间，避免长期有效凭证带来绑定风险。
- 解绑、拉黑先建数据结构和状态枚举，不在 MVP 登录绑定闭环里提前展开复杂 UI。
- 和平解绑、强制拉黑、拉黑冷却期已转入下一阶段计划：[2026-06-29-登录与绑定-和平解绑与强制拉黑-后端开发计划](./2026-06-29-登录与绑定-和平解绑与强制拉黑-后端开发计划.md)。
- 所有接口继续由路由层显式构造统一响应，不依赖中间件自动包装。
