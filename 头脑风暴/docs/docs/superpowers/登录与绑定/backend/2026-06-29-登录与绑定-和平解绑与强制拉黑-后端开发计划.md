## 1. 成功标准

- `POST /api/v1/relationship/unbind-requests` 能为已绑定用户创建和平解绑申请。
- 同一关系同一时间最多存在一条 `PENDING` 和平解绑申请。
- `GET /api/v1/relationship/unbind-requests/current` 能返回当前待处理或最近申请。
- `POST /api/v1/relationship/unbind-requests/{request_id}/accept` 只能由接收方调用，成功后关系解除并进入归档状态。
- `POST /api/v1/relationship/unbind-requests/{request_id}/reject` 只能由接收方调用，成功后关系保持已绑定。
- `POST /api/v1/relationship/unbind-requests/{request_id}/cancel` 只能由发起方调用，成功后关系保持已绑定。
- 过期申请不能再处理或撤回，关系保持已绑定。
- `POST /api/v1/relationship/block` 必须校验 `confirmText === "确定拉黑"`，成功后立即解除关系并写入 7 天冷却。
- 强制拉黑会关闭当前关系下待处理和平解绑申请。
- 拉黑冷却期内生成邀请码、预览邀请码、绑定邀请码都被拒绝。
- 执行 `poetry run ruff check app tests` 与 `poetry run pytest` 通过。

## 3. 数据模型

### `relationship_unbind_requests`

```text
id bigint pk
relationship_id bigint not null index
requester_user_id bigint not null index
receiver_user_id bigint not null index
status string not null  # PENDING / ACCEPTED / REJECTED / CANCELLED_BY_REQUESTER / EXPIRED / CANCELLED_BY_BLOCK
reason varchar(255) nullable
expires_at datetime not null
handled_at datetime nullable
created_at datetime
updated_at datetime
```

约束：

- `relationship_id` 必须指向当前有效或刚被解除的关系。
- `requester_user_id` 和 `receiver_user_id` 必须都是该关系成员。
- `PENDING` 状态同一 `relationship_id` 只能存在一条；MySQL 可通过 service + 普通索引兜底，后续再按数据库能力补函数索引或唯一约束。

### `relationship_blocks` 扩展

```text
id bigint pk
relationship_id bigint nullable index
blocker_user_id bigint not null index
blocked_user_id bigint not null index
cooldown_until datetime not null
released_at datetime nullable
release_source string nullable  # AUTO_EXPIRED / ADMIN_RELEASED
created_at datetime
updated_at datetime
```

约束：

- 强制拉黑时必须写入 `blocker_user_id` 和 `blocked_user_id`。
- 冷却期判断必须同时覆盖 A 拉黑 B 与 B 被 A 拉黑两个方向。
- 冷却到期后可通过查询时判断 `cooldown_until <= now` 视为失效，第一版不强依赖定时任务。

### `couple_relationships` 解除字段

```text
status string not null  # BOUND / UNBOUND_ARCHIVED
unbound_at datetime nullable
unbound_by_user_id bigint nullable
unbound_reason string nullable  # PEACE_ACCEPTED / FORCE_BLOCK
```

**Files:**
- Modify: `backend/couple-diary-b/app/services/relationship_service.py`
- Test: `backend/couple-diary-b/tests/test_relationship_api.py`

- [ ✅ ] **Step 1: 实现 `create_unbind_request()`**

校验顺序：

1. 当前用户必须存在 `BOUND` 关系。
2. 当前关系不能已有 `PENDING` 申请。
3. 创建 7 天后过期的 `PENDING` 申请。
4. 返回申请详情和当前关系状态。

- [ ✅ ] **Step 2: 实现 `get_current_unbind_request()`**

返回当前关系下 `PENDING` 申请；如没有，可返回最近一条申请或 `null`，由 schema 明确。

- [ ✅ ] **Step 3: 实现 `accept_unbind_request()`**

校验顺序：

1. 申请存在。
2. 申请状态必须是 `PENDING`。
3. 当前用户必须是 `receiver_user_id`。
4. 未超过 `expires_at`。
5. 更新申请为 `ACCEPTED`。
6. 更新关系为 `UNBOUND_ARCHIVED`，写入 `unbound_at`、`unbound_by_user_id`、`unbound_reason="PEACE_ACCEPTED"`。

- [ ✅ ] **Step 4: 实现 `reject_unbind_request()`**

校验同意接口的 1-4 步，成功后更新申请为 `REJECTED`，关系保持 `BOUND`。

- [ ✅ ] **Step 5: 实现 `cancel_unbind_request()`**

校验顺序：

1. 申请存在。
2. 申请状态必须是 `PENDING`。
3. 当前用户必须是 `requester_user_id`。
4. 未超过 `expires_at`。
5. 更新申请为 `CANCELLED_BY_REQUESTER`。
6. 关系保持 `BOUND`，不写 `unbound_at`，不触发回忆录归档。

- [ ✅ ] **Step 6: 覆盖测试**

覆盖发起成功、重复发起、非关系成员发起、发起方自处理、非接收方处理、同意成功、拒绝成功、发起方撤回成功、非发起方撤回失败、过期不可处理、过期不可撤回。

## 5. 业界实践校准

- 和平解绑申请独立成表，避免关系表状态承载太多临时过程数据。
- 强制拉黑不复用和平解绑状态机，避免“单方立即生效”和“双人确认”语义混乱。
- 冷却期用查询时判断过期，第一版不引入不必要的定时任务。
- 服务层统一处理关系关闭，避免多个接口各自改表导致状态不一致。
- 数据库层尽量补索引，但唯一性和权限校验仍必须在 service 中明确表达。
