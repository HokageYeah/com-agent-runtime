# 登录与绑定稳定双人空间后端 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在 `backend/couple-diary-b` 中新增稳定双人空间能力，让同一对用户重绑复用 `space_id`，并为每次绑定生成递增的 `relationship_segment_no`。

**Architecture:** 新增 `couple_spaces` 作为双方长期共同数据归属表，`couple_relationships` 继续表示具体绑定关系段。绑定 service 负责查找/创建空间、递增段号、创建关系和维护当前关系指针；解绑与拉黑 service 只关闭当前关系并清空空间指针，不删除空间。

**Tech Stack:** FastAPI、Pydantic v2、SQLAlchemy 2、Alembic、MySQL、pytest、ruff、loguru。

## Global Constraints

- 后端是空间与段号唯一事实源，前端和业务模块不能自行推导 `space_id`。
- `couple_spaces.user_low_id + user_high_id` 必须唯一，保证 A+B 与 B+A 命中同一空间。
- `relationship_segment_no` 在同一 `space_id` 内递增，换人绑定重新从 1 开始。
- 新增模型字段、schema 字段必须有中文业务注释或 `description`。
- 不破坏既有接口路径，不删除旧字段；新增字段向后兼容返回。
- 当前真实契约中 `coupleId` 已被前端当作旧字段使用，但后端实际返回的是 `relationship.id`；本轮必须保留 `coupleId`，同时新增语义明确的 `relationshipId` 与 `spaceId`。

## 1. 成功标准

- 首次 A+B 绑定时创建一个 `couple_space`，`current_segment_no=1`，关系段号为 `1`。
- A+B 解绑或拉黑后，`couple_space` 不删除，`current_relationship_id` 置空。
- A+B 再次绑定时复用原 `space_id`，创建段号 `2` 的新关系。
- B+A 反向发起绑定时仍命中同一 `space_id`。
- A+C 绑定时创建新的 `space_id`，段号从 `1` 开始。
- `/api/v1/relationship/me`、绑定成功响应、解绑/拉黑结果响应携带 `spaceId` 与 `relationshipSegmentNo`。
- 历史已存在关系能通过迁移回填空间与段号。
- 执行 `poetry run ruff check app tests` 与 `poetry run pytest` 通过。

## 3. 数据模型契约

### 3.1 `couple_spaces`

```text
id bigint pk
user_low_id bigint not null index   # 双方用户 ID 较小值，用于稳定确定空间归属
user_high_id bigint not null index  # 双方用户 ID 较大值，用于稳定确定空间归属
current_segment_no int not null default 0  # 该空间已经创建到第几段绑定关系
current_relationship_id bigint nullable index  # 当前有效关系 ID，未绑定/已解绑/冷却时为空
created_at datetime not null
updated_at datetime not null
```

数据库约束：

```text
unique(user_low_id, user_high_id)
check(user_low_id < user_high_id)
```

### 3.2 `couple_relationships` 扩展

```text
space_id bigint not null index
relationship_segment_no int not null
```

数据库约束：

```text
unique(space_id, relationship_segment_no)
```

### 3.3 Schema 输出字段

当前 `CoupleRelationshipInfo` 定义在 `backend/couple-diary-b/app/schemas/auth.py`，`relationship.py` 只是复用它。执行时不要在两个 schema 文件里各定义一套关系结构。

```python
class CoupleRelationshipInfo(BaseModel):
    status: RelationshipStatus = Field(description="当前用户的关系状态")
    coupleId: str | int | None = Field(
        default=None,
        description="历史兼容字段：当前代码实际返回 relationship.id，不再解释为稳定空间 ID",
    )
    relationshipId: str | int | None = Field(
        default=None,
        description="当前绑定关系 ID，只代表本次绑定关系段",
    )
    spaceId: str | int | None = Field(
        default=None,
        description="稳定双人空间 ID，同一对用户多次绑定时保持不变",
    )
    relationshipSegmentNo: int | None = Field(
        default=None,
        description="该关系在稳定空间下的绑定段号，供回忆录按段归档",
    )
    currentSegmentNo: int | None = Field(
        default=None,
        description="当前稳定空间已创建到第几段绑定关系",
    )
    currentRelationshipId: str | int | None = Field(
        default=None,
        description="当前稳定空间内的有效关系 ID，未绑定或冷却时为空",
    )
```

兼容要求：`/relationship/me`、`/relationship/bind`、`/auth/wechat-login` 中的 `relationship` 仍返回这个扁平对象，不改成嵌套 `relationship/space`。

## 6. 风险与处理

- 历史数据回填可能遇到缺失双方用户 ID 的关系：迁移必须记录并失败，不要默默生成脏空间。
- 并发绑定可能重复递增段号：绑定创建必须在事务内完成，必要时使用行锁或唯一约束失败重试。
- 旧测试只断言 `relationship_id`：新增断言时保留旧字段，避免破坏前端兼容。
