# 登录与绑定需求设计文档

> **模块定位：** 负责用户身份建立、情侣关系建立与解除，是所有核心业务的前置模块。
> **上级入口：** [情侣日记总文档](../../2026-06-11-情侣日记小程序-需求设计总文档.md)

---

## 一、模块目标与边界

### 1.1 模块目标

- 完成微信登录与基础身份识别
- 让用户选择情侣空间内的角色标签
- 建立一对一情侣绑定关系
- 提供和平解绑与强制拉黑机制

### 1.2 模块边界

- 本模块只负责用户身份与情侣关系管理
- 绑定成功后跳转到共享业务空间，不承载日记和赌局详细逻辑
- 通知消息由 [通知与消息](../通知与消息/需求设计文档.md) 定义

---

## 二、角色与前置条件

### 2.1 参与角色

- 用户 A：发起登录、绑定或解绑的一方
- 用户 B：接收绑定邀请或解绑请求的一方
- 系统：负责校验关系状态、生成绑定码、发送通知、维护冷却期

### 2.2 前置条件

- 用户必须完成微信登录
- 用户必须选择角色标签「他」或「她」
- 同一时刻一个用户只能存在一个有效情侣关系

---

## 三、页面与入口

| 页面 | 入口 | 作用 |
|---|---|---|
| 登录页 | 打开小程序 | 发起微信登录 |
| 角色选择页 | 登录成功后 | 选择「他 / 她」标签 |
| 绑定页 | 首次登录 / 我的页 | 展示绑定码、二维码或输入框 |
| 我的页昵称编辑弹窗 | 我的页当前用户昵称旁编辑按钮 | 创建或编辑当前用户昵称 |
| 解绑页 | 我的页 | 发起和平解绑或强制拉黑 |

## 四、核心流程

### 4.1 微信登录流程

```text
打开小程序
  -> 调用 wx.login 获取 code
  -> 后端换取 openid
  -> 创建或更新 user
  -> 进入角色选择
  -> 进入未绑定态
```

### 4.2 绑定流程

```text
用户 A 点击邀请另一半
  -> 系统生成绑定码 / 二维码
  -> 用户 B 扫码或输入绑定码
  -> 用户 B 看到用户 A 基础信息
  -> 用户 B 确认同意绑定
  -> 系统创建情侣关系
  -> 双方进入共享情侣空间
```

### 4.2.1 绑定双人交互示意

```text
用户A（发起方）                    用户B（接收方）
    │                                  │
    ├─ 点击「邀请另一半」               │
    │   生成专属绑定码 / 二维码          │
    │                                  │
    │       发送绑定邀请 ──────────►    │
    │                                  ├─ 扫码 / 输入绑定码
    │                                  ├─ 看到对方昵称和头像
    │                                  ├─ 点击「同意绑定」
    │                                  │
    │   ◄────────── 绑定成功通知 ────────┤
    │                                  │
    ├─ 双方进入主页（日记时间线）         │
```

### 4.2.2 昵称创建与编辑流程

```text
用户完成微信登录
  -> 后端用微信昵称初始化用户昵称
  -> 用户进入我的页
  -> 用户点击当前昵称旁的编辑按钮
  -> 前端在页面层弹出昵称编辑模态框
  -> 用户输入 1-5 个字的新昵称
  -> 后端校验 token，只允许修改当前登录用户
  -> 后端写入 nickname，并标记 nickname_updated_by_user=true
  -> 前端同步本地 userInfo.nickname
  -> 我的页未绑定态、已绑定态、绑定预览中的用户昵称统一刷新
```

规则：用户手动设置昵称后，后续微信登录不得再用微信昵称覆盖该昵称；头像仍可继续跟随微信登录资料刷新。

### 4.2.3 稳定双人空间与重复绑定恢复流程

```text
用户 A 与用户 B 首次绑定
  -> 系统按双方用户 ID 生成稳定双人空间 couple_space
  -> 系统创建第 1 段绑定关系，关系段号 relationship_segment_no=1
  -> 赌约、日记等共同数据写入该 space_id 与 relationship_segment_no=1
  -> 双方和平解绑或强制拉黑后，关系段关闭，但 space_id 不删除
  -> 冷却结束后 A 与 B 再次绑定
  -> 系统复用同一个 couple_space
  -> 系统创建第 2 段绑定关系，关系段号 relationship_segment_no=2
  -> 赌约、日记、情侣空间默认恢复展示该 space_id 下的历史共同数据
  -> 新产生的数据写入 relationship_segment_no=2，供回忆录按段归档
```

稳定双人空间是“这两个人共同数据的长期归属”，绑定关系是“这两个人第几次在一起的时间段”。同一对用户无论谁发起邀请，都必须命中同一个 `space_id`；用户换人绑定时进入另一套 `space_id`，绑定段号从 1 重新计算。

### 4.3 和平解绑流程

```text
用户 A 发起解绑申请
  -> 系统校验双方当前仍处于已绑定关系
  -> 系统创建 7 天有效的解绑申请
  -> 系统通知用户 B
  -> 用户 A 可在对方处理前撤回申请
  -> 用户 B 同意或拒绝
  -> 同意则解除关系并触发回忆录归档事件
  -> 拒绝则关系不变，解绑申请关闭
  -> 撤回则关系不变，解绑申请关闭
  -> 7 天未处理则申请失效，关系不变
```

和平解绑是“双方确认”的低冲突解除关系方式，业务上必须保留申请记录，不能只在关系表里放一个临时状态硬扛。一个有效情侣关系同一时间最多存在一条待处理和平解绑申请。

### 4.3.1 和平解绑双人交互示意

```text
用户A（发起方）                    用户B（接收方）
    │                                  │
    ├─ 点击「申请解绑」                 │
    ├─ 确认提示：对方同意后解除关系      │
    ├─ 点击确认                         │
    │                                  │
    │       发送解绑申请 ──────────►    │
    │                                  ├─ 收到解绑请求
    ├─ 对方处理前可撤回申请              ├─ 若已撤回：处理入口失效
    │                                  ├─ 查看后果提示
    │                                  ├─ 选择同意 / 拒绝
    │                                  │
    │   ◄────────── 处理结果通知 ────────┤
    │                                  │
    ├─ 若同意：关系解除并触发归档        │
    └─ 若拒绝、撤回或过期：维持当前绑定关系 │
```

### 4.3.2 和平解绑处理规则

| 规则 | 说明 |
|---|---|
| 发起资格 | 只有 `BOUND` 关系中的任一方可以发起 |
| 申请唯一性 | 同一有效关系同一时间只能有一条 `PENDING` 申请 |
| 处理资格 | 只有被申请方可以同意或拒绝，发起方不能替对方处理 |
| 撤回资格 | 只有发起方可以在申请仍为 `PENDING` 且未过期时撤回 |
| 有效期 | 默认 7 天，到期自动视为 `EXPIRED`，关系保持 `BOUND` |
| 同意结果 | 关系变为 `UNBOUND_ARCHIVED`，记录 `unbound_at`，触发回忆录归档事件 |
| 拒绝结果 | 申请变为 `REJECTED`，关系继续保持 `BOUND` |
| 撤回结果 | 申请变为 `CANCELLED_BY_REQUESTER`，关系继续保持 `BOUND`，接收方处理入口失效 |
| 再次申请 | 拒绝、撤回或过期后允许再次发起，但应复用后端冷却或频控策略防刷 |

### 4.4 强制拉黑流程

```text
用户 A 选择拉黑对方
  -> 系统弹出严肃提示
  -> 用户 A 输入确认文案「确定拉黑」
  -> 系统立即解除当前绑定关系
  -> 系统写入双方拉黑冷却记录
  -> 双方进入拉黑冷却状态
  -> 7 天内不可重新绑定
  -> 到期后自动解除冷却，但不会自动恢复关系
```

强制拉黑是“单方立即生效”的高风险解除关系方式，它不是和平解绑的一个特殊分支，而是独立动作。后端必须保证它可以关闭当前关系、关闭待处理解绑申请，并阻断双方在冷却期内再次绑定。

### 4.4.1 强制拉黑结果示意

```text
用户A 点击「拉黑对方」
    │
    ├─ 弹出严肃提示
    ├─ 输入「确定拉黑」
    ├─ 二次确认
    │
    └─ 立即生效
         ├─ 强制解绑
         ├─ 关闭待处理和平解绑申请
         ├─ 双方互相不可发起绑定
         ├─ 冷却期 7 天
         └─ 冷却结束后仅恢复“可重新绑定资格”，不会自动恢复关系
```

### 4.4.2 强制拉黑处理规则

| 规则 | 说明 |
|---|---|
| 发起资格 | 只有 `BOUND` 或存在当前有效关系上下文的用户可以拉黑对方 |
| 确认文案 | 前端必须要求输入 `确定拉黑`，后端仍以 token 和关系状态为准 |
| 关系结果 | 当前关系立即变为 `UNBOUND_ARCHIVED`，记录强制解除来源 |
| 申请处理 | 当前关系下待处理和平解绑申请统一关闭为 `CANCELLED_BY_BLOCK` |
| 冷却限制 | 双方互相进入 7 天 `BLOCK_COOLDOWN`，禁止生成邀请码、预览绑定和绑定 |
| 到期结果 | 冷却到期后只恢复可绑定资格，不恢复原关系、不自动创建新关系 |
| 通知边界 | 通知与消息模块只负责送达，不拥有关系状态决策权 |

## 五、状态流转

### 5.1 用户关系状态

```text
未绑定 UNBOUND
  -> 绑定中 INVITING
  -> 已绑定 BOUND
  -> 解绑申请中 UNBIND_REQUESTED
  -> 已解绑归档 UNBOUND_ARCHIVED
  -> 拉黑冷却中 BLOCK_COOLDOWN
  -> 可重新绑定 UNBOUND
```

### 5.2 关键状态说明

| 状态 | 触发条件 | 结果 |
|---|---|---|
| 未绑定 `UNBOUND` | 登录后未建立情侣关系，且没有拉黑冷却 | 可发起或输入绑定码 |
| 绑定中 `INVITING` | 已生成有效邀请码但尚未完成绑定 | 可复制邀请码或等待对方输入 |
| 已绑定 `BOUND` | 双方确认绑定成功 | 进入共享情侣空间 |
| 解绑申请中 `UNBIND_REQUESTED` | 一方发起和平解绑且申请未处理、未过期 | 关系仍可用，但关系管理页必须展示待处理状态 |
| 已解绑归档 `UNBOUND_ARCHIVED` | 和平解绑同意或强制拉黑导致关系解除 | 当前关系关闭，历史数据进入回忆录归档流程 |
| 拉黑冷却中 `BLOCK_COOLDOWN` | 一方强制拉黑，冷却截止时间未到 | 7 天内双方不可重新绑定 |

### 5.3 状态流转约束

| 当前状态 | 动作 | 下一个状态 | 说明 |
|---|---|---|---|
| `BOUND` | 发起和平解绑 | `UNBIND_REQUESTED` | 只创建待处理申请，不立即解除关系 |
| `UNBIND_REQUESTED` | 对方同意 | `UNBOUND_ARCHIVED` | 关系解除，触发归档事件 |
| `UNBIND_REQUESTED` | 对方拒绝 | `BOUND` | 关系保持，申请关闭 |
| `UNBIND_REQUESTED` | 发起方撤回 | `BOUND` | 关系保持，申请关闭，接收方处理入口失效 |
| `UNBIND_REQUESTED` | 7 天未处理 | `BOUND` | 申请过期，关系保持 |
| `BOUND` / `UNBIND_REQUESTED` | 强制拉黑 | `BLOCK_COOLDOWN` | 当前关系关闭，双方进入冷却期 |
| `BLOCK_COOLDOWN` | 冷却到期 | `UNBOUND` | 只恢复重新绑定资格 |

前端展示可以临时把 `UNBIND_REQUESTED` 视为“已绑定但有待处理事项”，但正式登录判定仍只能以 `BOUND` 或后端返回的可用关系上下文为准；涉及能否进入共享业务空间时，以后端鉴权与关系查询结果为准。

## 六、字段与约束

### 6.1 用户字段

| 字段 | 说明 | 约束 |
|---|---|---|
| openid | 微信唯一标识 | 必填，唯一 |
| 昵称 | 用户在情侣空间展示的名称 | 初始来源微信；用户可在我的页手动更新；手动更新后不再被微信登录覆盖 |
| 昵称手动设置标记 | 标识昵称是否由用户主动编辑过 | 默认为 false；用户在我的页保存昵称后置为 true |
| 头像 | 用户头像 | 来源微信，可随微信登录更新 |
| 角色标签 | 他 / 她 | 首次设置后不可修改 |

### 6.2 绑定字段

| 字段 | 说明 | 约束 |
|---|---|---|
| 绑定码 | 绑定邀请凭证 | 需唯一，支持过期 |
| 发起方 ID | 绑定邀请创建者 | 必填 |
| 接收方 ID | 确认绑定者 | 确认时写入 |
| 稳定双人空间 ID `space_id` | 同一对用户长期复用的共同空间标识 | 必填；由排序后的双方用户 ID 唯一确定，A+B 与 B+A 必须相同 |
| 绑定段号 `relationship_segment_no` | 该双人空间下第几段绑定关系 | 必填；首次绑定为 1，同一对用户每次重新绑定递增，换人绑定重新从 1 开始 |
| 状态 | 当前关系状态 | 必填 |

### 6.2.1 稳定双人空间字段

| 字段 | 说明 | 约束 |
|---|---|---|
| 空间 ID | 同一对用户共享数据的长期主键 | 必填，供赌约、日记、情侣空间和回忆录统一引用 |
| 较小用户 ID | 双方用户 ID 中较小的一方 | 必填，与较大用户 ID 组成唯一约束 |
| 较大用户 ID | 双方用户 ID 中较大的一方 | 必填，与较小用户 ID 组成唯一约束 |
| 当前绑定段号 `current_segment_no` | 该空间已创建到第几段绑定关系 | 必填；每次重新绑定同一人时递增 |
| 当前关系 ID `current_relationship_id` | 当前有效绑定关系 | 可空；解绑、拉黑或未绑定时为空 |

稳定双人空间只表达“两个人是谁”，不表达当前是否仍然绑定；当前是否可用以后端关系状态、冷却期和权限校验为准。

### 6.3 解绑申请字段

| 字段 | 说明 | 约束 |
|---|---|---|
| 解绑申请 ID | 和平解绑申请唯一标识 | 必填，唯一 |
| 关系 ID | 本次申请归属的情侣关系 | 必填，只能指向当前有效关系 |
| 发起方 ID | 点击申请和平解绑的一方 | 必填，必须是关系成员 |
| 接收方 ID | 需要处理申请的一方 | 必填，必须是关系另一方 |
| 申请状态 | 当前申请处理状态 | `PENDING` / `ACCEPTED` / `REJECTED` / `CANCELLED_BY_REQUESTER` / `EXPIRED` / `CANCELLED_BY_BLOCK` |
| 申请说明 | 发起方可选说明 | 可为空，前端第一版可不开放输入 |
| 过期时间 | 申请自动失效时间 | 默认创建后 7 天 |
| 处理时间 | 对方同意、拒绝或系统关闭时间 | 未处理时为空 |

### 6.4 拉黑冷却字段

| 字段 | 说明 | 约束 |
|---|---|---|
| 拉黑记录 ID | 拉黑冷却记录唯一标识 | 必填，唯一 |
| 关系 ID | 触发拉黑时的关系 | 可空；有当前关系时必须记录 |
| 拉黑发起方 ID | 主动点击强制拉黑的一方 | 必填 |
| 被拉黑方 ID | 被拉黑的另一方 | 必填 |
| 冷却截止时间 | 双方禁止重新绑定的截止时间 | 默认创建后 7 天 |
| 解除时间 | 冷却结束或人工解除时间 | 未结束时为空 |
| 解除来源 | 冷却如何结束 | `AUTO_EXPIRED` / `ADMIN_RELEASED`，第一版只规划自动到期 |

### 6.5 规则约束

- 一个用户同一时间只能绑定一个情侣
- 已绑定用户不能发起新绑定邀请
- 拉黑冷却期内双方不能互相发起绑定
- 和平解绑申请超过 7 天未响应自动失效
- 同一关系同一时间最多存在一条待处理和平解绑申请
- 强制拉黑会关闭当前关系下所有待处理和平解绑申请
- 同一对用户解绑或拉黑后再次绑定时，必须复用原稳定双人空间，并生成新的绑定段号
- 换人绑定时必须进入新的稳定双人空间，绑定段号从 1 重新开始
- 回忆录归档由回忆录模块承接，本模块只产生“关系已解除，需要归档”的业务事件或状态；归档边界必须是 `space_id + relationship_segment_no`

### 6.6 昵称编辑接口契约

| 项 | 说明 |
|---|---|
| 接口 | `PATCH /api/v1/auth/me/profile` |
| 鉴权 | 必须携带当前登录 token |
| 请求体 | `{ "nickname": "新昵称" }` |
| 昵称规则 | trim 后 1-5 个字，禁止全空 |
| 成功响应 | 返回最新当前用户信息：`id`、`nickname`、`avatar`、`roleTag` |
| 失败响应 | 未登录返回 401；昵称为空或超长返回 400 / 422 |

该接口不接收 `user_id`，被修改用户只能来自 token 解析结果，避免前端传参导致越权修改。

### 6.7 和平解绑接口契约

| 项 | 说明 |
|---|---|
| 发起申请 | `POST /api/v1/relationship/unbind-requests` |
| 查询当前申请 | `GET /api/v1/relationship/unbind-requests/current` |
| 同意申请 | `POST /api/v1/relationship/unbind-requests/{request_id}/accept` |
| 拒绝申请 | `POST /api/v1/relationship/unbind-requests/{request_id}/reject` |
| 撤回申请 | `POST /api/v1/relationship/unbind-requests/{request_id}/cancel` |
| 鉴权 | 全部必须携带当前登录 token |
| 发起请求体 | `{ "reason": "可选说明" }`，第一版前端可不传 `reason` |
| 拒绝请求体 | `{ "reason": "可选说明" }`，第一版前端可不传 `reason` |
| 撤回请求体 | `{ "reason": "可选说明" }`，第一版前端可不传 `reason` |
| 成功响应 | 返回最新关系状态、解绑申请状态、过期时间、双方基础信息 |
| 失败响应 | 未登录返回 401；非关系成员返回 403；无有效关系返回 409；重复申请返回 409；申请过期返回 410；非发起方撤回返回 403 |

### 6.8 强制拉黑接口契约

| 项 | 说明 |
|---|---|
| 接口 | `POST /api/v1/relationship/block` |
| 鉴权 | 必须携带当前登录 token |
| 请求体 | `{ "confirmText": "确定拉黑" }` |
| 确认规则 | 前端必须要求输入 `确定拉黑`；后端必须再次校验该字段 |
| 成功响应 | 返回最新关系状态 `BLOCK_COOLDOWN`、冷却截止时间、被拉黑用户基础信息 |
| 失败响应 | 未登录返回 401；非关系成员返回 403；确认文案错误返回 400；无有效关系返回 409；重复拉黑返回 409 |

## 七、异常与边界场景

- 昵称为空或只有空格：禁止保存，提示“昵称不能为空”
- 昵称超过 5 个字：禁止保存，提示“昵称不能超过5个字”
- 未登录状态提交昵称：返回登录失效，前端引导重新登录
- 手动昵称已设置后再次微信登录：保留手动昵称，只刷新头像等非手动字段
- 绑定码已过期：提示用户重新生成
- 用户已绑定他人：禁止继续绑定
- 双方重复扫码：提示当前关系已存在
- 和平解绑过程中对方拒绝：维持原关系
- 同一关系重复发起和平解绑：禁止创建第二条待处理申请，返回当前待处理申请
- 非接收方处理解绑申请：禁止处理，返回无权限
- 发起方试图同意自己的解绑申请：禁止处理，必须由对方决定
- 非发起方撤回解绑申请：禁止撤回，返回无权限
- 发起方在对方处理前撤回解绑申请：申请关闭为 `CANCELLED_BY_REQUESTER`，关系保持
- 已同意、已拒绝、已撤回或已过期申请再次撤回：禁止重复撤回，返回当前申请已关闭
- 和平解绑申请超过 7 天后再处理或撤回：返回申请已过期，关系保持
- 解绑申请待处理时发起强制拉黑：允许拉黑，系统关闭待处理申请并立即进入冷却
- 解绑申请待处理时重新生成绑定码：禁止，当前仍处于关系上下文内
- 强制拉黑确认文案错误：禁止提交，提示必须输入“确定拉黑”
- 拉黑后尝试再次绑定：冷却期内必须禁止
- 拉黑冷却到期后：允许重新进入绑定流程，但不会自动恢复旧关系；如果双方重新绑定，系统会复用原稳定双人空间并创建新的绑定段号，赌约、日记等历史共同数据可按空间恢复展示

## 八、与其他模块的数据关系

- 绑定成功后为 [日记](../日记/需求设计文档.md) 和 [打赌系统](../打赌系统/需求设计文档.md) 提供稳定双人空间上下文 `space_id`、当前绑定关系 `relationship_id` 和绑定段号 `relationship_segment_no`
- 解绑或拉黑成功后触发 [回忆录](../回忆录/需求设计文档.md) 按 `space_id + relationship_segment_no` 生成该段关系的归档
- 同一对用户重新绑定后，日记、赌约和情侣空间默认按 `space_id` 恢复历史共同数据，新数据写入新的 `relationship_segment_no`
- 绑定、解绑、拉黑过程中的通知由 [通知与消息](../通知与消息/需求设计文档.md) 承接
