# 打赌系统稳定双人空间后端 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在 `backend/couple-diary-b` 的打赌系统中补齐 `space_id`、`relationship_id`、`relationship_segment_no`，让赌局支持同一对用户重绑后按稳定空间恢复展示，并支持回忆录按段读取。

**Architecture:** 打赌系统不拥有情侣空间计算逻辑，只调用关系模块获取当前绑定上下文。`bets` 主表保存创建时的空间和段号快照；当前时间线/统计按 `space_id` 查询，归档读取按 `space_id + relationship_segment_no` 查询。

**Tech Stack:** FastAPI、Pydantic v2、SQLAlchemy 2、Alembic、MySQL、pytest、ruff、loguru。

## Global Constraints

- `space_id`、`relationship_id`、`relationship_segment_no` 来自关系模块，不能由请求体传入。
- 未绑定期间不能读取真实赌局、统计、详情操作入口；重绑后才按同一 `space_id` 恢复。
- 新建赌局写当前最新 `relationship_id` 和 `relationship_segment_no`，旧赌局字段不被重绑覆盖。
- 回忆录后续只读 `space_id + relationship_segment_no` 的赌局快照，本轮不写回忆录表。
- 新增模型字段、schema 字段必须有中文业务注释或 `description`。
- 当前 `bets.couple_id` 虽然名叫 couple，但代码里实际写入和查询的都是 `relationship.id`（见 `bet_service.get_bound_couple_or_403` 的 `couple_id=relationship.id`）。本轮**保留 `couple_id` 不删**，迁移时用它作为旧关系 ID 回填 `relationship_id`，再按该关系所属空间回填 `space_id` 和段号；不要把 `couple_id` 直接当 `space_id` 用。
- `BoundCoupleContext` 当前字段名 `couple_id` 也是旧关系 ID 语义，改造时建议重命名为 `relationship_id` 并补 `space_id`，但需同步更新所有引用点，不能只改一半。

## 3. 数据模型契约

### 3.1 `bets` 扩展字段

```text
space_id bigint not null index
relationship_id bigint not null index
relationship_segment_no int not null index
```

字段含义：

- `space_id`：赌局属于哪一对用户的长期空间。
- `relationship_id`：赌局创建时处于哪一次具体绑定关系。
- `relationship_segment_no`：赌局创建时处于该空间下第几段绑定，供回忆录按段读取。

推荐索引：

```text
idx_bets_space_id(space_id)
idx_bets_space_segment(space_id, relationship_segment_no)
idx_bets_relationship_id(relationship_id)
```

## 6. 风险与处理

- 旧字段 `couple_id` 语义不清：执行前必须确认它是旧关系 ID 还是空间概念，不能盲目复用。
- 未终态历史赌局重绑后可继续操作：这是需求允许的“状态机继续推进”，但权限必须要求当前双方已重新绑定。
- 归档读取不检查当前绑定：这是服务内部归档能力，不能直接暴露为普通用户接口。
