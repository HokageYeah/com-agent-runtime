## 1. 成功标准

- 未登录请求返回鉴权错误，不进入赌局业务逻辑。
- 已登录未绑定用户访问真实赌局接口时返回 `403`，错误文案明确提示“请先绑定另一半”。
- 已绑定用户可以创建赌局，系统写入 `pending` 状态并指定接收方。
- 接收方可以接受或拒绝；接受后进入 `active`，拒绝后进入 `rejected`。
- 到达截止时间后，系统方法可以把 `active` 赌局推进到 `settling`。
- 详情、时间线、统计和结算接口需要兜底推进已到期的 `active` 赌局，避免页面继续显示“进行中”或无法提交结算。
- `settling` 阶段支持任一方提交结果，另一方同意后进入 `redeeming`；不同意后保留协商消息入口。
- `settling` 阶段支持选择平局不算，状态直接进入 `expired`，不计入双方胜场和履约率。
- `redeeming` 阶段支持输方标记已兑现、赢方确认收到；确认后进入 `completed`，未收到则回到 `redeeming`。
- `active` 阶段支持参与方手动截止赌局，并指定“我赢了 / TA 赢了 / 平局不算”。
- 手动截止选择胜负时进入 `settling` 并创建待确认结果；选择平局不算时进入 `expired`，不计入胜场和履约率。
- 列表接口按日期返回中轴时间线需要的数据：日期分组、左侧 TA 发起、右侧我发起、状态、奖励、截止时间、结果。
- 统计接口返回双方胜场、履约率、最常出现奖励。
- 奖励敏感词检查接口命中时只做温和提醒，不强制拦截创建。
- 状态变化需要保留足够清晰的业务事件和时间字段，供通知与消息模块、回忆录模块后续接入；本模块不直接投递通知，也不直接写入回忆录归档表。
- 新增代码包含中文字段注释、关键日志，且不把 token、openid、session_key 等敏感信息写入日志。
- 执行 `poetry run ruff check app tests` 与 `poetry run pytest` 通过。

`advance_due_active_bets(now, db)`：

## 7. 风险与处理

- 到期推进需要定时任务：本轮先提供 service 方法和测试，真实调度由通知与消息或运维计划承接。
- 跨模块职责容易混入：打赌系统只记录状态变化、关键时间点和可供归档读取的数据；通知投递交给通知与消息，历史归档执行交给回忆录。
- 并发状态流转可能重复提交：service 层校验之外，后续可在状态更新时加入条件更新或事务锁；MVP 先用事务和状态校验兜底。
- 敏感词策略容易过度拦截：本轮只提醒不拦截，符合需求文档“温暖提示”。
- 统计口径可能被产品调整：当前固定为已确认结果和已完成履约率，前端只展示后端结果。
