# 打赌系统稳定双人空间前端 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在 `frontend/couple-diary-f` 中对齐打赌系统的稳定双人空间契约，让赌局页重绑后按 `spaceId` 恢复历史赌局，新建赌局不由前端传归属字段。

**Architecture:** 前端继续使用既有赌局页三态、发起页、详情页和 hooks。空间字段只作为后端响应的展示/调试上下文保存，创建请求不传 `spaceId`、`relationshipId`、`relationshipSegmentNo`；页面是否请求真实赌局仍只看当前是否 `BOUND`。

**Tech Stack:** UniApp、Vue 3 `<script setup>`、TypeScript、Pinia、`request<T>()`、ThorUI / XXT easycom、SCSS。

## Global Constraints

- 前端不能计算或提交赌局归属字段，赌局归属以后端当前关系上下文为准。
- 未绑定状态不请求真实赌局，即使本地 Store 存在历史 `spaceId`。
- 已绑定状态请求时间线/统计，后端按当前 `spaceId` 恢复历史。
- 类型字段必须中文注释清楚：展示按空间，归档按段，创建关系只用于追踪。
- 不重写现有页面结构；只补类型、请求、状态刷新和必要 UI 文案。

## 3. 类型契约

```ts
export interface BetSpaceContext {
  /** 稳定双人空间 ID：同一对用户重绑后保持不变，赌局页默认按它恢复历史。 */
  spaceId: string | number;
  /** 创建该赌局时所在的绑定关系 ID，只用于追踪当时关系段。 */
  relationshipId: string | number;
  /** 创建该赌局时所在的绑定段号，回忆录按该字段分段归档。 */
  relationshipSegmentNo: number;
}

export interface BetCardData extends BetSpaceContext {
  /** 赌局 ID，用于进入详情页。 */
  id: string | number;
  /** 当前用户视角下的中轴线归属，partner 在左侧，self 在右侧。 */
  side: BetSide;
  /** 后端状态机状态。 */
  status: BetStatus;
}

export interface CreateBetRequest {
  /** 赌什么，展示在赌局卡片主标题。 */
  title: string;
  /** 赢的判定规则，详情页用于说明如何结算。 */
  winCondition: string;
  /** 输方需要兑现的奖励。 */
  reward: string;
  /** 截止时间 ISO 字符串。 */
  deadlineAt: string;
}
```

`CreateBetRequest` 禁止出现：

```ts
spaceId?: never;
relationshipId?: never;
relationshipSegmentNo?: never;
```

## 6. 风险与处理

- 本地 Store 有历史 `spaceId`：未绑定态必须忽略它，不请求真实赌局。
- 详情页历史未终态赌局可继续操作：前提是当前双方已经重新绑定且后端授权通过；前端只做状态守卫，最终以后端为准。
- 类型检查历史债：不要为通过 type-check 顺手重构无关旧组件。
