# 打赌系统需求设计文档

> **模块定位：** 负责情侣之间的趣味互动闭环，是产品的第二核心体验。
> **上级入口：** [情侣日记总文档](../../2026-06-11-情侣日记小程序-需求设计总文档.md)

---

## 一、模块目标与边界

### 1.1 模块目标

- 提供轻松有趣的双人打赌体验
- 建立从发起到兑现的完整状态闭环
- 通过时间线和统计增强互动感

### 1.2 模块边界

- 本模块负责赌局主体、状态流转、协商消息和兑现确认
- 奖励敏感词提醒属于本模块
- 系统通知与提醒发送规则由 [通知与消息](../通知与消息/需求设计文档.md) 承接

---

## 二、角色与前置条件

### 2.1 参与角色

- 发起方：创建赌注的人
- 接收方：决定接受或拒绝的人
- 系统：负责状态变更、到期判断、提醒与统计

### 2.2 前置条件

- 双方必须已绑定
- 发起时必须存在有效情侣空间
- 赌注必须有明确截止时间
- 用户仅完成登录但未绑定情侣关系时，可以进入赌局页的待绑定引导态，但不能查看真实赌局、战绩统计或发起赌注
- 同一对用户解绑或拉黑后再次绑定时，赌局页必须按稳定双人空间恢复双方历史赌约；新发起赌约归属到当前最新绑定段号

---

## 三、页面与入口

| 页面 | 入口 | 作用 |
|---|---|---|
| 赌局页 | TabBar 第二页 | 承接未登录、已登录未绑定、已登录已绑定三种状态；绑定后浏览赌局时间线与统计 |
| 发起赌注页 | 已登录已绑定赌局页 `+` / 发起赌约按钮 | 填写赌注内容，发布后创建 `pending` 赌局并返回赌局页刷新 |
| 赌注详情页 | 点击赌局条目 | 查看状态、讨论、结算、兑现 |

## 四、核心流程

### 4.1 发起赌注流程

```text
用户填写赌什么
  -> 填写谁赢了会怎样
  -> 填写奖励是什么
  -> 选择截止时间
  -> 确认当前为“我向 TA 发起挑战”
  -> 系统检测奖励敏感词
  -> 用户确认提交
  -> 系统创建 pending 状态赌注
  -> 返回赌局页并刷新中轴时间线
```

### 4.1.1 发起赌注页进入规则

- 只有已登录且已绑定情侣关系的用户，才能从赌局页看到发起赌约按钮。
- 未登录用户不能进入发起赌注页，应先进入登录流程。
- 已登录未绑定用户不能进入发起赌注页，应先进入绑定流程。
- 发起赌注页顶部使用关闭按钮，点击后返回赌局页，不创建草稿。
- 发布按钮固定在页面底部，提交中需要防止重复点击。
- MVP 中发起方始终是当前登录用户，接收方始终是已绑定的另一半；页面里的“谁向谁挑战”用于确认双方关系与挑战对象，不允许前端伪造为 TA 代发起。

### 4.2 接受或拒绝流程

```text
对方收到赌注通知
  -> 选择接受或拒绝
  -> 接受则进入 active
  -> 拒绝则进入 rejected
```

### 4.2.1 发起与回应双人交互示意

```text
用户A（发起方）                    用户B（接收方）
    │                                  │
    ├─ 填写赌注信息                     │
    ├─ 点击「发起打赌」                 │
    │                                  │
    │       赌注邀请通知 ──────────►    │
    │                                  ├─ 查看赌什么、奖励、截止时间
    │                                  ├─ 选择接受 / 拒绝
    │                                  │
    │   ◄────────── 回应结果通知 ────────┤
    │                                  │
    ├─ 接受后：进入进行中                │
    └─ 拒绝后：记录为已拒绝              │
```

### 4.3 到期结算流程

```text
到达截止时间
  -> 系统将赌注转为 settling
  -> 任一方提交判定结果
  -> 另一方同意或不同意
  -> 同意则进入 redeeming
  -> 不同意则进入协商
  -> 3 天未完成处理则作废
```

### 4.3.1 结算阶段双人交互示意

```text
赌注到期，状态变为「待结算」
    │
    ├─ 任一方提交结果：「我认为是她赢了 / 他赢了」
    │
    ├─ 另一方确认结果
    │   ├─ 同意 ──► 结果确认，进入「待兑现」
    │   └─ 不同意 ──► 进入协商状态
    │                 双方可在赌注下方发送简短消息讨论
    │
    └─ 3 天双方都没完成确认 ──► 赌注自动作废
```

### 4.4 兑现流程

```text
赌注进入待兑现
  -> 系统定时提醒输方
  -> 输方点击已兑现
  -> 赢方确认是否收到
  -> 收到则 completed
  -> 未收到则回到 redeeming
```

### 4.4.1 待兑现阶段示意

```text
结果确认后，状态变为「待兑现」
    │
    ├─ 系统每 12 小时提醒输方一次
    ├─ 输方点击「已兑现奖励」
    │   例如：「我已经给 TA 汉堡包啦！」
    │
    ├─ 赢方确认是否收到
    │   ├─ 确认 ──► 赌注完成，状态变为「已完成」
    │   └─ 没收到 ──► 回到「待兑现」
    │
    └─ 多个待兑现赌局可合并展示
        「你欠 TA 3 个奖励：汉堡包、奶茶、电影票」
```

### 4.5 赌局时间线展示示意

```text
对方发起的赌约                         日期线                         我发起的赌约

┌────────────────────────────┐      │ 2026年6月10日（今天） │
```

### 4.5.1 中轴时间线布局规则

- 日期线固定在页面中间，承担“日期分组 + 时间顺序”的双重视觉职责。
- 左侧卡片固定展示“对方发起的赌约”。
- 右侧卡片固定展示“自己发起的赌约”。
- 同一天内的赌约按时间倒序排列，越新的内容越靠上。
- 结算中、待兑现等高优先级状态需要通过卡片样式进一步强化，但不改变左右归属规则。
- 当某个时间段只有一侧存在赌约时，另一侧允许留空。

### 4.5.2 待兑现动画提醒规则

- 仅 `redeeming`（待兑现）状态的赌约卡片展示提醒动画。
- 动画形式为“轻微呼吸发光 + 小幅上下浮动”，提醒用户当前有未完成兑现事项。
- 动画节奏应偏温和，避免造成持续性打扰或焦虑感。
- 动画优先作用于卡片的状态角标、边框高亮区或提醒徽标，不建议整张卡片剧烈闪烁。
- 用户进入赌约详情页或完成一次明确操作后，列表页动画可以短暂减弱，但在状态未完成前仍保留提醒能力。

## 五、状态流转

### 5.1 赌局状态

```text
pending
  -> rejected
  -> active
  -> settling
  -> redeeming
  -> completed
  -> expired
```

### 5.2 状态定义

| 状态 | 含义 | 是否终态 |
|---|---|---|
| pending | 已发起，待对方同意 | 否 |
| rejected | 对方拒绝 | 是 |
| active | 对方已接受，进行中 | 否 |
| settling | 已到期，待双方确认结果 | 否 |
| redeeming | 结果已确认，待兑现 | 否 |
| completed | 奖励已兑现完成 | 是 |
| expired | 到期后长期未完成结算 | 是 |

## 六、字段与约束

### 6.1 赌注字段

| 字段 | 说明 | 约束 |
|---|---|---|
| 稳定双人空间 ID `space_id` | 该赌约归属的长期情侣空间 | 必填；同一对用户重绑后继续复用，用于恢复历史赌约 |
| 绑定关系 ID `relationship_id` | 创建该赌约时所在的具体绑定关系 | 必填；用于追踪该赌约属于哪一次绑定关系 |
| 绑定段号 `relationship_segment_no` | 该赌约属于稳定空间下第几段绑定 | 必填；首次绑定为 1，同一对用户重绑后递增，供回忆录按段归档 |
| 发起方 ID | 创建赌约的用户 | 必填，必须是当前稳定空间成员 |
| 接收方 ID | 需要回应赌约的另一方 | 必填，必须是当前稳定空间成员 |
| 赌什么 | 事件描述 | 必填 |
| 谁赢了会怎样 | 赢的判定规则 | 必填，需清晰 |
| 奖励是什么 | 输方要兑现的奖励 | 必填 |
| 截止时间 | 赌局失效时间点 | 必填，精确到时间 |
| 当前状态 | 状态机位置 | 必填 |
| 结果 | 谁赢了 | 结算阶段后产生 |

### 6.1.1 重复绑定后的赌约恢复规则

- 赌局列表、战绩统计和待兑现提醒默认按当前 `space_id` 查询，因此同一对用户重新绑定后会自动恢复历史赌约。
- 新赌约必须写入当前最新 `relationship_id` 和 `relationship_segment_no`，不能覆盖旧赌约的绑定段号。
- 回忆录生成某一段关系时，只读取同一 `space_id` 下对应 `relationship_segment_no` 的赌约。
- 历史赌约恢复展示不等于恢复旧关系；操作权限仍要求双方当前已经重新绑定并处于有效情侣空间。
- 如果用户换人绑定，新的两人组合会得到新的 `space_id`，赌约段号从 1 开始，不得混入上一任空间数据。

### 6.2 奖励敏感词规则

- 后端检测奖励中的敏感关键词
- 命中后给出温暖提示，但不强制拦截
- 关键词列表可配置，并支持后续扩展

### 6.3 提醒规则

- 待兑现阶段每 12 小时提醒输方一次
- 多个待兑现赌局可合并展示
- 提醒文案需保持柔和，不使用强制催促语气
- 待兑现卡片在时间线列表中必须带有轻提醒动画，形成“列表可见 + 通知可达”的双提醒机制
- 动画提醒只用于待兑现状态，不能扩散到进行中、已完成、已拒绝等其它状态

### 6.4 展示约束

- 赌局时间线必须采用中轴日期线布局，不能退回单列卡片流
- 左侧固定映射对方发起，右侧固定映射自己发起
- 卡片内必须同时展示发起人、赌约内容、状态、奖励、截止时间或结果信息
- 待兑现状态在视觉层级上高于进行中、待结算和已完成
- 底部战绩统计继续作为时间线收尾区域保留
- 同一对用户多次绑定后，时间线默认展示该稳定双人空间下全部可见赌约；如需要回忆录或筛选视图，再按绑定段号分组

### 6.5 待结算与待兑现双向复核规则

- `settling` 与 `redeeming` 仍保留为顶层主状态，不再额外扩散新的主状态枚举。
- 详情页需要在主状态下再细分操作子阶段，用于驱动按钮显隐、提示文案和事件列表。
- `settling` 初始态下，双方都可以提交 `我赢了 / TA 赢了 / 平局不算`；此时不展示“同意结果”“不同意并协商”。
- 任意一方提交结果后，提交方进入“待对方确认”；另一方只能看到当前提案结果与“同意结果 / 重新确认”。
- 每个有效提案只有一次“重新确认”机会；发起重新确认时必须填写重新确认消息。
- 提案发起方如果“同意重新确认”，双方回到当前主状态的初始可提交态；如果“不同意重新确认”，系统按原提案结果自动落定，并把“请线下确认”写入结构化事件流。
- `settling` 中拒绝重新确认后，赌局自动按原结算结果进入 `redeeming`。
- `redeeming` 完整镜像 `settling`：输方“我已兑现”后，赢方可“确认收到”或“重新确认”；如果输方拒绝重新确认，系统按原兑现结果自动进入 `completed`。
- 普通协商消息仍可保留，但不再负责驱动详情页按钮逻辑；按钮逻辑只由当前有效提案、子阶段和结构化事件决定。

### 6.6 双向复核详细流程说明

#### 6.6.1 设计目标

- 在不重写顶层状态机的前提下，把“待结算”和“待兑现”都升级为可追踪、可回放、可扩展的双人复核流程。
- 所有按钮显隐、可执行动作、提示文案和事件时间线，都必须来自结构化数据，而不是前端硬编码猜测。
- 每一轮有效提案只允许一次重新确认机会，避免无限往返协商。

#### 6.6.2 核心概念

| 概念 | 说明 |
|---|---|
| 主状态 | 仍使用 `settling / redeeming / completed / expired` |
| 子阶段 | 详情页操作区的细化阶段，用于驱动按钮和提示文案 |
| 当前有效提案 | 当前这轮真正生效、等待对方确认的结算或兑现提案 |
| 发起方 | 提交当前有效提案的人 |
| 确认方 | 需要对当前有效提案做确认或重新确认的人 |
| 重新确认机会 | 针对单条有效提案的一次性机会，不是整条赌约永久只有一次 |
| 结构化事件流 | 供前端渲染“协商信息列表”的正式事件，不再只靠纯文本消息 |

#### 6.6.3 `settling` 子阶段定义

| 子阶段 | 含义 | 当前操作者 |
|---|---|---|
| `settling_selecting` | 双方都还没提交本轮结算结果 | 双方都可操作 |
| `settling_pending_confirm` | 一方已提交结果，等待另一方确认 | 确认方操作 |
| `settling_reconfirm_requested` | 确认方发起了一次重新确认 | 发起方操作 |
| `settling_locked_original_result` | 发起方拒绝重新确认，系统锁定原提案结果 | 无人工操作，仅展示结果 |

#### 6.6.4 `settling` 详细流程

```text
赌局进入 settling
  -> 子阶段 = settling_selecting
  -> 双方都可以选择：
     - 我赢了
     - TA 赢了
     - 平局不算
  -> 任一方提交后，生成当前有效提案
  -> 子阶段 = settling_pending_confirm
  -> 提交方显示“待对方确认”
  -> 确认方显示提案结果 + 同意结果 / 重新确认
  -> 如果确认方同意结果：
     - 若提案为 self_win / partner_win：进入 redeeming
     - 若提案为 draw：进入 expired
  -> 如果确认方发起重新确认：
     - 必须填写重新确认消息
     - 子阶段 = settling_reconfirm_requested
     - 发起方看到消息 + 同意重新确认 / 不同意重新确认
  -> 如果发起方同意重新确认：
     - 当前提案失效
     - 回到 settling_selecting
     - 双方重新获得提交权限
  -> 如果发起方不同意重新确认：
     - 写入“不同意重新确认，请线下确认”事件
     - 系统锁定原提案结果
     - 若原提案是胜负结果：自动进入 redeeming
     - 若原提案是平局不算：自动进入 expired
```

#### 6.6.5 `settling` 页面显示规则

- `settling_selecting`
  - 双方都显示“我赢了 / TA 赢了 / 平局不算 / 提交结果”。
  - 不显示“同意结果”“重新确认”。
- `settling_pending_confirm`
  - 发起方按钮全部不可继续提交，展示“待对方确认”。
  - 确认方展示“发起方选择了谁赢 / 平局不算”的结果说明。
  - 确认方显示“同意结果 / 重新确认”。
- `settling_reconfirm_requested`
  - 发起方展示重新确认消息。
  - 发起方显示“同意重新确认 / 不同意重新确认”。
  - 确认方不再重复显示确认按钮，只展示等待态。
- `settling_locked_original_result`
  - 详情页不再显示可继续协商的主流程按钮。
  - 通过状态文案和事件列表告诉用户系统已按原提案落定。

#### 6.6.6 `redeeming` 子阶段定义

| 子阶段 | 含义 | 当前操作者 |
|---|---|---|
| `redeeming_pending_confirm` | 输方已提交“我已兑现”，等待赢方确认 | 赢方操作 |
| `redeeming_reconfirm_requested` | 赢方发起了一次重新确认 | 输方操作 |
| `redeeming_locked_original_result` | 输方拒绝重新确认，系统锁定原兑现结果 | 无人工操作，仅展示结果 |

#### 6.6.7 `redeeming` 详细流程

```text
赌局进入 redeeming
  -> 输方先提交“我已兑现”
  -> 生成当前有效兑现提案
  -> 子阶段 = redeeming_pending_confirm
  -> 输方显示“待对方确认”
  -> 赢方显示“确认收到 / 重新确认”
  -> 如果赢方确认收到：
     - 赌局进入 completed
  -> 如果赢方发起重新确认：
     - 必须填写重新确认消息
     - 子阶段 = redeeming_reconfirm_requested
     - 输方看到消息 + 同意重新确认 / 不同意重新确认
  -> 如果输方同意重新确认：
     - 当前兑现提案失效
     - 回到 redeeming 初始提交态
     - 由输方重新提交“我已兑现”
  -> 如果输方不同意重新确认：
     - 写入“不同意重新确认，请线下确认”事件
     - 系统按原兑现提案自动落定
     - 赌局直接进入 completed
```

#### 6.6.8 结构化事件流要求

- 以下动作必须写入结构化事件流：
  - 提交结算提案
  - 提交兑现提案
  - 发起重新确认
  - 同意重新确认
  - 不同意重新确认
  - 自动按原提案落定
  - 最终进入 `redeeming / completed / expired`
- 事件流主要用于：
  - 详情页“协商信息列表”展示
  - 后续通知模块消费关键状态变化
  - 后续回忆录模块回放赌约过程

#### 6.6.9 与普通协商消息的边界

- 普通协商消息保留，允许双方补充沟通。
- 普通协商消息不负责驱动主流程状态，不决定按钮显隐。
- 所有流程推进必须依赖结构化动作和结构化事件。

#### 6.6.10 关键口径

- “重新确认”是对当前有效提案的一次性复核，不是整条赌约生命周期永久只有一次。
- “不同意重新确认”不是继续进入无限协商，而是系统按原提案自动落定。
- 平局不算一旦落定，直接进入 `expired`，不计入胜场和履约率，也不进入兑现链路。

### 6.7 待确认超时自动确认规则

#### 6.7.1 适用范围

- 只作用于：
  - `settling_pending_confirm`
  - `redeeming_pending_confirm`
- 不作用于：
  - `settling_selecting`
  - `settling_reconfirm_requested`
  - `redeeming_reconfirm_requested`

#### 6.7.2 规则说明

- 当一方已经提交当前有效提案，而另一方处于“待确认”状态时，系统启动自动确认计时。
- 如果“待确认”用户在限定时间内没有处理，系统自动视为其“同意当前结果”。
- 自动确认时间需要可配置：
  - 标准业务规则：`1天`
  - 当前测试默认值：`1分钟`

#### 6.7.3 `settling` 超时自动确认

```text
进入 settling_pending_confirm
  -> 记录当前提案创建时间
  -> 计算自动确认截止时间
  -> 若确认方在截止前未处理
     -> 系统自动同意当前结算提案
     -> 胜负结果进入 redeeming
     -> 平局结果进入 expired
```

#### 6.7.4 `redeeming` 超时自动确认

```text
进入 redeeming_pending_confirm
  -> 记录当前兑现提案创建时间
  -> 计算自动确认截止时间
  -> 若确认方在截止前未处理
     -> 系统自动确认已收到奖励
     -> 赌局进入 completed
```

#### 6.7.5 前端展示要求

- “待确认”用户页面必须明确展示自动确认提示文案。
- 提示文案需要带出具体自动确认时间，例如“系统将于 06-24 18:30 自动同意结果”。
- 当页面停留在详情页时，若自动确认时间已到，页面需要自动刷新到最新状态，不要求用户手动退出重进。

#### 6.7.6 后端实现要求

- 自动确认时间由后端统一计算和下发，前端只负责展示。
- 当前有效提案快照需要带上自动确认时间字段，供详情页提示使用。
- 自动确认发生时，必须写入结构化事件流，便于后续通知模块和回忆录模块消费。

## 七、异常与边界场景

- 截止时间早于当前时间时不能提交
- 判定条件写得过于模糊时，应提示用户补充
- 结算阶段双方长期不处理，3 天后自动作废
- 输方标记已兑现但赢方拒绝确认时，状态回到待兑现
- 已拒绝或已完成的赌局不可再次编辑为进行中

## 八、与其他模块的数据关系

### 8.1 登录与绑定关系边界

- 赌局参与人、稳定双人空间、当前绑定关系 `relationship_id` 和绑定段号 `relationship_segment_no` 来自 [登录与绑定](../登录与绑定/需求设计文档.md)。
- 所有真实赌局都必须归属于稳定双人空间；登录成功但未绑定时只能看到待绑定引导态，不能读取真实赌局、统计或发起赌约。
- 用户解绑或拉黑后，打赌系统在未重新绑定前不允许基于原关系发起新赌局、结算、兑现或推进人工操作。
- 同一对用户重新绑定后，打赌系统必须按原 `space_id` 恢复历史赌局列表、统计和待办提醒；未终态赌局不创建副本、不改旧绑定段号，按当前时间和状态机继续推进。
- 新发起赌局必须写入当前最新绑定关系和绑定段号，避免回忆录分段时把新旧阶段混在一起。

### 8.2 通知与消息边界

- 提醒和结果通知由 [通知与消息](../通知与消息/需求设计文档.md) 承接，打赌系统只产出业务状态变化和提醒所需数据。
- 打赌系统需要为通知模块提供可识别的事件触发点：赌约创建、接受、拒绝、到期待结算、结果提交、结果同意、进入待兑现、输方标记已兑现、赢方确认收到、赌局作废。
- 微信订阅消息、站内消息、重试、合并提醒和通知开关均不在打赌系统内实现。
- 待兑现阶段的列表呼吸动画属于打赌系统前端展示；外部推送和消息中心展示属于通知与消息模块。

### 8.3 回忆录归档边界

- 已解绑后的历史赌局按 `space_id + relationship_segment_no` 归档到 [回忆录](../回忆录/需求设计文档.md)。
- 回忆录需要的归档快照至少包含：稳定双人空间 ID、绑定段号、赌约标题、判定条件、奖励、发起方、接收方、截止时间、最终状态、赢家、完成时间或最后更新时间。
- `completed`、`rejected`、`expired` 等终态赌局按终态归档；`pending`、`active`、`settling`、`redeeming` 等未终态赌局按“该段关系解除时的最后状态”进入该段回忆录，由回忆录负责展示解释。
- 同一对用户重新绑定后，赌局仍保留原绑定段号用于回忆录分段；当前赌局页可按稳定双人空间恢复展示，但回忆录必须按绑定段号切分。
- 打赌系统本轮只保证原始业务数据可被归档读取，不实现回忆录归档落库和回忆录 UI。

### 8.4 设置与安全边界

- 通知开关、隐私设置和账号安全策略由对应设置或账号模块管理，打赌系统只读取最终可用关系和当前用户身份。
- 前端不能通过参数伪造情侣关系、发起方或接收方；后端必须以登录态和绑定关系重新计算双方身份。
