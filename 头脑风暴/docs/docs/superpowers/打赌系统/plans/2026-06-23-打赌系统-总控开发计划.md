## 2. 核心原则

- 登录成功不等于可以使用赌局；只有 `relationship.status === "BOUND"` 才能查看真实赌局、战绩和发起赌注。
- 未登录态保持设计不变，已登录态必须拆为“已登录未绑定”和“已登录已绑定”。
- 前端负责 UI 三态、视觉还原、页面交互、表单校验和状态展示；后端负责身份、情侣空间、状态机、统计口径和强业务校验。
- 接口契约先冻结，再分别开发前后端，避免联调时字段互相漂移。
- 后端新增正式业务模块 `bets_*`，不能写入 `demo_*`，也不能把赌局逻辑塞进登录与绑定模块。
- 前端新增 `pages-bets` 业务分包，视觉必须继承全局暖粉设计系统和赌局页设计指南。
- 打赌系统只负责赌局状态机和可展示数据；通知投递由通知与消息模块实现，解绑后的历史归档由回忆录模块实现。
- 用户解绑或关系失效后，原情侣关系下的赌局不能继续发起、结算或兑现；前端回到已登录未绑定态，历史内容交给回忆录展示。
- 所有核心逻辑保留中文注释和可搜索日志。

## 3. 契约冻结

### 3.1 统一响应

所有后端接口仍返回：

```json
{
  "platform": "BETS",
  "api": "api/v1/bets/timeline",
  "data": {},
  "ret": ["SUCCESS::获取赌局时间线成功"],
  "v": 1
}
```

### 3.2 状态枚举

```text
BetStatus:
  pending
  rejected
  active
  settling
  redeeming
  completed
  expired

BetSide:
  partner  # 左侧，TA / 对方
  self     # 右侧，我 / 自己
```

### 3.3 接口清单

| 接口 | 方法 | 责任 |
|---|---|---|
| `/api/v1/bets/ping` | GET | 模块探针 |
| `/api/v1/bets/reward-check` | POST | 奖励敏感词温和提醒 |
| `/api/v1/bets` | POST | 创建赌局 |
| `/api/v1/bets/timeline` | GET | 赌局页中轴时间线 |
| `/api/v1/bets/stats` | GET | 双方战绩统计 |
| `/api/v1/bets/{bet_id}` | GET | 赌注详情 |
| `/api/v1/bets/{bet_id}/respond` | POST | 接受或拒绝 |
| `/api/v1/bets/{bet_id}/manual-close` | POST | 进行中赌局手动截止并提交初始结果 |
| `/api/v1/bets/{bet_id}/settlement` | POST | 提交结算提案、确认结果、发起重新确认、同意重新确认、拒绝重新确认 |
| `/api/v1/bets/{bet_id}/redemption` | POST | 提交兑现提案、确认收到、发起重新确认、同意重新确认、拒绝重新确认 |
| `/api/v1/bets/{bet_id}/redemption/mark-paid` | POST | 输方标记已兑现 |
| `/api/v1/bets/{bet_id}/redemption/confirm-received` | POST | 赢方确认收到 |
| `/api/v1/bets/{bet_id}/messages` | POST | 协商消息 |

### 3.4 前端页面状态判定

```ts
type BetPageState = 'visitor' | 'unbound' | 'bound';

const pageState: BetPageState = !userStore.isLogin
  ? 'visitor'
  : userStore.relationshipStatus === 'BOUND'
    ? 'bound'
    : 'unbound';
```

规则：

- `visitor`：展示未登录锁定态，点击 CTA 进入登录流程。
- `unbound`：展示已登录未绑定态，点击 CTA 进入绑定流程。
- `bound`：请求真实赌局时间线和统计。

### 3.5 跨模块事件边界

打赌系统需要在后端状态变化处保留清晰事件触发点，供其他模块后续接入：

| 触发点 | 打赌系统责任 | 外部模块责任 |
|---|---|---|
| 赌约创建 | 写入 `pending`，记录发起方、接收方和创建时间 | 通知与消息决定是否提醒接收方 |
| 接受 / 拒绝 | 更新 `active` 或 `rejected`，记录回应时间 | 通知与消息决定是否告知发起方 |
| 到期待结算 | 提供推进到 `settling` 的 service 方法 | 定时调度和到期提醒由通知与消息或运维计划承接 |
| 结果提交 / 同意 | 记录结果提案、赢家、输家和确认时间 | 通知与消息决定是否提醒确认或兑现 |
| 进入待兑现 | 更新 `redeeming`，列表返回 `highlight=true` | 外部推送、合并提醒和通知开关由通知与消息承接 |
| 兑现完成 / 作废 | 更新 `completed` 或 `expired` 及关键时间 | 回忆录在解绑或归档流程中读取历史快照 |

本轮开发不得把微信订阅消息真实投递、通知中心、通知重试、回忆录归档落库写进打赌系统模块。

### 3.6 第二阶段增强契约：详情页手动截止

新增“赌局详情页”参考 UI：

- `designs/赌局页/code/已登录赌局详情页/DESIGN.md`
- `designs/赌局页/code/已登录赌局详情页/code.html`
- `designs/赌局页/code/已登录赌局详情页/screen.png`

详情页必须从“状态操作列表”升级为“赌局结果操作面板”，核心包含：

- 顶部自定义导航，标题为“赌局详情”。
- Hero 卡片展示状态、赌局标题、截止时间和倒计时。
- 赌注信息卡展示奖励、判定条件、双方参与人。
- `active` 状态展示“手动截止赌局”操作，点击后必须选择结果：
  - `self_win`：我赢了。
  - `partner_win`：TA 赢了。
  - `draw`：平局不算。
- `self_win/partner_win` 不直接进入待兑现，而是进入 `settling` 并创建待确认结果，仍由另一方同意后进入 `redeeming`。
- `draw` 直接进入 `expired`，`winnerUserId/loserUserId` 为空，统计不计入双方胜场和履约率。
- 手动截止必须记录 `manualClosedAt` 和 `manualCloseResult`，便于详情页、通知模块和回忆录后续读取。
- 自然到期的 `active` 赌局必须停止倒计时，并按 `settling` 展示胜负判定操作；后端详情、时间线、统计和结算接口都要具备到期推进兜底，不能依赖定时任务作为唯一入口。
- 自然到期后的结算操作必须支持“我赢了 / TA 赢了 / 平局不算”；`SettlementAction.DRAW` 直接进入 `expired`，不计入双方胜场和履约率。
- `redeeming/completed` 状态在时间线和详情页必须展示当前用户视角的赢家文案，例如“我赢了”或“TA 赢了”。

### 3.7 第三阶段设计变更契约：稳定双人空间

同一对用户重绑复用 `space_id`、每次重新绑定递增 `relationship_segment_no` 后，打赌系统需要从“只跟当前关系 ID”调整为“当前页按稳定空间恢复，归档按绑定段号切分”。该变更已转入补充计划：[2026-07-01-打赌系统-稳定双人空间适配-总控开发计划](./2026-07-01-打赌系统-稳定双人空间适配-总控开发计划.md)。后续修改赌局查询、统计、新建赌约或回忆录读取口径时，必须以该补充计划为最新口径。

## 7. 业界主流计划检查

当前计划符合主流工程拆解方式：

- **契约优先：** 先冻结状态枚举、接口字段和统一响应，再开发前后端。
- **后端强约束：** 鉴权、绑定关系、状态机、权限和统计口径都在后端兜底。
- **前端状态清晰：** 页面三态与用户关系状态一一对应，避免 UI 误展示真实数据。
- **分层明确：** 后端按 route/service/schema/model/test 拆分；前端按 type/api/hook/page/component 拆分。
- **可测试闭环：** 后端用 pytest 覆盖状态机，前端用 type-check、构建和微信开发者工具手工链路验收。

### 10.3 总体流程要求

- [ ✅ ] `settling` 与 `redeeming` 都必须以“当前有效提案”为流程中心。
- [ ✅ ] 当前有效提案未产生前，双方都处于初始提交态。
- [ ✅ ] 当前有效提案产生后，只允许确认方推进确认或重新确认。
- [ ✅ ] 发起重新确认时必须填写重新确认消息。
- [ ✅ ] “同意重新确认”后回到当前主状态的初始提交态。
- [ ✅ ] “不同意重新确认”后不再循环协商，而是自动按原提案结果落定。
- [ ✅ ] “待确认”用户超时未处理时，系统自动视为同意当前结果。

### 10.4 `settling` 总控流程说明

```text
进入 settling
  -> 子阶段 settling_selecting
  -> 双方都可提交 我赢了 / TA赢了 / 平局不算
  -> 一方提交后进入 settling_pending_confirm
  -> 提交方等待，确认方可 同意结果 / 重新确认
  -> 确认方同意：
     - 胜负结果 -> redeeming
     - 平局结果 -> expired
  -> 确认方重新确认：
     - 必须填写消息
     - 进入 settling_reconfirm_requested
  -> 发起方同意重新确认：
     - 回到 settling_selecting
  -> 发起方不同意重新确认：
     - 写入结构化事件
     - 系统按原提案自动落定
     - 胜负结果 -> redeeming
     - 平局结果 -> expired
```

### 10.5 `redeeming` 总控流程说明

```text
进入 redeeming
  -> 输方先提交 我已兑现
  -> 进入 redeeming_pending_confirm
  -> 赢方可 确认收到 / 重新确认
  -> 赢方确认收到：
     - 进入 completed
  -> 赢方重新确认：
     - 必须填写消息
     - 进入 redeeming_reconfirm_requested
  -> 输方同意重新确认：
     - 回到 redeeming 初始提交态
  -> 输方不同意重新确认：
     - 写入结构化事件
     - 系统按原兑现提案自动落定
     - 进入 completed
```
