# 打赌系统稳定双人空间适配 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在已完成的打赌系统上适配稳定双人空间：赌局默认按 `space_id` 恢复历史，新发起赌约写入当前 `relationship_id` 与 `relationship_segment_no`，回忆录后续按段归档。

**Architecture:** 本计划是 2026-06-23 打赌系统 MVP 的契约变更补充计划，不重写旧执行记录。后端把赌局归属从单一当前关系扩展为 `space_id + relationship_id + relationship_segment_no`；前端继续以已绑定状态为操作前提，但列表、统计、待兑现提醒默认展示当前稳定空间下的可见历史赌局。

**Tech Stack:** FastAPI + MySQL + SQLAlchemy + Alembic + UniApp/Vue3/TypeScript + Pinia。

## Global Constraints

- 需求主定义以 [../需求设计文档.md](../需求设计文档.md) 为准，本计划只补执行顺序和验收边界。
- 打赌系统不计算情侣空间；`space_id`、`relationship_id`、`relationship_segment_no` 来自登录与绑定模块。
- 新建赌局必须写入当前最新 `relationship_id` 和 `relationship_segment_no`。
- 时间线、统计、待兑现提醒默认按当前 `space_id` 查询，支持同一对用户重绑后恢复历史赌局。
- 未绑定期间不能读取真实赌局、发起赌约、结算或兑现；历史恢复只发生在同一对用户重新绑定后。
- 回忆录按 `space_id + relationship_segment_no` 读取某一段关系下的赌局，本轮只保证原始数据可被读取，不实现回忆录归档。
- 前端、后端新增或修改字段必须补中文业务注释。

## 2. 为什么新增计划而不是改写旧计划

打赌系统已开发完成，旧计划记录了路由、状态机、前端页面和验收结果。稳定双人空间是跨模块数据归属变更，直接改写旧计划会丢掉已经完成的任务轨迹。新增补充计划能让后续开发者明确：不是重做打赌系统，而是在现有系统上调整归属字段、查询口径和联调验证。

## 3. 核心判断

【核心判断】
✅ 值得做：赌局是共同数据，归属必须跟“这两个人”走，而不是跟“当前这一次关系 ID”走。

【关键洞察】
- 数据结构：`space_id` 决定赌局属于哪对人，`relationship_segment_no` 决定它属于哪一段关系。
- 复杂度：列表和统计按 `space_id` 查，回忆录按 `space_id + relationship_segment_no` 查，两个场景自然分开。
- 风险点：未绑定期间不能因为有历史 `space_id` 就允许操作旧赌局。

【Linus式方案】
1. 给赌局主表补三个字段，不搞旁路映射表。
2. 创建时从关系模块拿当前上下文，别让前端传人造关系。
3. 展示按空间，归档按段，权限按当前是否已绑定。
4. 保持现有状态机，不为重绑再造一套赌局状态。

## 4. 契约冻结

### 4.1 赌局字段

| 字段 | 所属 | 说明 |
|---|---|---|
| `space_id` | `bets`、时间线、详情、统计 | 赌局归属的稳定双人空间 |
| `relationship_id` | `bets`、详情、回忆录快照 | 创建赌局时所在的具体绑定关系 |
| `relationship_segment_no` | `bets`、详情、回忆录快照 | 创建赌局时所在的绑定段号 |

### 4.2 查询口径

| 场景 | 查询条件 | 说明 |
|---|---|---|
| 当前赌局页时间线 | 当前 `space_id` | 同一对用户重绑后恢复展示历史赌局 |
| 当前战绩统计 | 当前 `space_id` | 历史 completed/rejected/expired 等终态参与统计口径按产品定义保留 |
| 新建赌局 | 当前 `space_id + relationship_id + relationship_segment_no` | 写入最新绑定段号 |
| 详情页操作 | 当前已绑定 + 当前用户是空间成员 + 赌局属于当前 `space_id` | 不要求赌局创建于当前段，但要求当前双方重新绑定后才可操作 |
| 回忆录归档 | `space_id + relationship_segment_no` | 只读某一段关系下的赌局 |

### 4.3 前端页面状态

不改变既有三态判断：

```ts
type BetPageState = 'visitor' | 'unbound' | 'bound';

const pageState: BetPageState = !userStore.isLogin
  ? 'visitor'
  : userStore.relationshipStatus === 'BOUND'
    ? 'bound'
    : 'unbound';
```

只有 `bound` 状态才请求真实赌局。`unbound` 不因为 Store 中存在历史 `spaceId` 而请求赌局。

## 8. 风险与处理

- 历史赌局缺少关系上下文：迁移必须从创建时的 `couple_id` 或现有关联关系回填，无法回填则记录并中断。
- 当前 `couple_id` 命名可能已表示旧关系 ID：计划执行时必须先确认模型语义，避免把旧字段误当空间字段。
- 操作权限不能只看赌局属于同一 `space_id`：还必须确认当前双方已重新绑定。
- 统计口径可能受历史段影响：当前需求要求重绑后恢复历史统计，后续如要按段筛选再单独设计。
