# 打赌系统结算兑现双向复核增强计划

## 目标

在不扩散顶层状态机的前提下，补齐 `settling` 和 `redeeming` 的双人复核闭环，让详情页能稳定承接：

- 初始提交
- 待对方确认
- 发起一次重新确认
- 同意重新确认并回到初始态
- 不同意重新确认并按原结果自动落定

## 契约冻结

### 顶层主状态

- `settling`
- `redeeming`
- `completed`
- `expired`

### 详情页子阶段

- `settling_selecting`
- `settling_pending_confirm`
- `settling_reconfirm_requested`
- `settling_locked_original_result`
- `redeeming_pending_confirm`
- `redeeming_reconfirm_requested`
- `redeeming_locked_original_result`

### 详情接口新增字段

- `detailPhase`
- `pendingSettlementProposal`
- `pendingRedemptionProposal`
- `availableActions`
- `timelineEvents`
- `canRequestReconfirm`
- `reconfirmWindowUsed`

## 实现要点

### 后端

- 扩展 `bet_result_proposals`，让提案具备类型、选择值、重新确认窗口和锁定状态。
- 新增 `bet_detail_events`，把“提交结果、发起重新确认、同意重新确认、拒绝重新确认、自动落定”全部写成结构化事件。
- `settlement` 接口切换为动作驱动，不再依赖 `winnerUserId`。
- 新增统一 `redemption` 接口，承接兑现阶段的标记、确认和重确认动作。

### 前端

- `detail.vue` 改为由 `detailPhase + availableActions + proposal snapshot + timelineEvents` 驱动。
- `settling` 初始态展示双方都可提交的三选一按钮。
- `settling/redeeming` 的待确认态展示提案结果和“确认 / 重新确认”。
- 重新确认必须通过带输入弹窗提交消息。
- 底部“协商信息列表”渲染结构化事件流，普通消息只作为补充信息。

## 验证

- 后端需要覆盖结算与兑现双向复核主链、一次性机会、越权、空消息和自动落定。
- 前端至少验证 `detail.vue` 在各子阶段的按钮显隐、消息弹窗和事件列表渲染。
- 时间线、赢家文案、统计口径继续保持旧逻辑不回退。
