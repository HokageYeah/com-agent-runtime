# 情侣日记 — 微信小程序需求设计文档

> **版本：** v1.0
> **日期：** 2026-06-11
> **状态：** 待评审
> **定位：** 甜蜜轻松向情侣互动小程序

---

## 一、项目概述

### 1.1 产品简介

「情侣日记」是一款面向情侣用户的微信小程序，提供**共同记录日常**和**趣味打赌**两大核心体验。产品风格温暖甜蜜，注重互动仪式感，让情侣间的每个日常都有迹可循。

### 1.2 目标用户

处于恋爱关系中的年轻情侣，希望在手机上有一个专属的私密空间来共同记录生活、进行趣味互动。

### 1.3 产品定位

**甜蜜轻松向** — 可爱温暖的设计风格，像恋爱备忘录 + 趣味小游戏的感觉，功能偏向趣味互动而非严肃工具。

### 1.4 MVP 范围

第一版只做以下 4 个核心功能：

| # | 功能模块 | 说明 |
|---|---------|------|
| 1 | 用户登录 & 情侣绑定 | 微信登录、选择身份、绑定另一半 |
| 2 | 日记（时间线） | 轻量便签式日常记录，按日期时间线展示 |
| 3 | 打赌系统 | 发起→接受→结算→兑现，完整闭环 |
| 4 | 回忆录 | 解绑后日记归档，加密保存 |

## 三、功能模块详细设计

### 3.1 用户登录 & 情侣绑定

#### 3.1.1 微信登录

- 登录方式：微信一键登录（`wx.login` 获取 code → 后端换取 openid）
- 用户信息：昵称、头像（从微信获取）
- 性别标识：登录后手动选择角色标签 ——「他」或「她」，绑定后不可更改

#### 3.1.2 情侣绑定流程

```
用户A（发起方）                    用户B（接收方）
    │                                  │
    ├─ 点击「邀请另一半」               │
    │   生成专属绑定码 / 二维码          │
    │                                  │
    │       发送绑定邀请 ──────────►    │
    │                                  ├─ 扫码 / 输入绑定码
    │                                  ├─ 看到对方昵称和头像
    │                                  ├─ 点击「同意绑定」
    │                                  │
    │   ◄────────── 绑定成功通知 ────────┤
    │                                  │
    ├─ 双方进入主页（日记时间线）         │
```

**绑定规则：**
- 一个用户同时只能绑定一个情侣
- 已绑定用户不能发起新的绑定邀请
- 绑定后，双方共享同一个「情侣空间」
- 解绑后才能重新绑定其他人

#### 3.1.3 解绑机制（双轨制）

**方式一：和平解绑（双方确认）**

```
用户A 点击「申请解绑」
    │
    ├─ 弹出确认提示：「确定要解绑吗？解绑后日记将保存在回忆录中」
    │
    ├─ 用户A 确认 ──► 通知发送给用户B
    │
    │         用户B 收到解绑请求
    │              ├─ 同意 ──► 解绑成功，日记归入双方「回忆录」
    │              └─ 拒绝 ──► 解绑失败，保持绑定状态
    │
    └─ 7天内无响应 ──► 自动失效
```

**方式二：强制拉黑（单方面）**

适用于对方拒绝配合解绑的情况（如真实分手场景）。

```
用户A 点击「拉黑对方」
    │
    ├─ 弹出严肃提示：
    │   「拉黑将强制解除情侣绑定，且对方将无法联系你。
    │     拉黑后7天内双方不可重新绑定。确定吗？」
    │
    ├─ 二次确认（输入「确定拉黑」文字确认）
    │
    └─ 确认 ──► 立即生效
         ├─ 强制解绑
         ├─ 双方互相拉黑（无法发送绑定邀请）
         └─ 7天冷却期后自动解除拉黑状态（不会自动恢复绑定）
```

### 3.2 日记功能（时间线）

#### 3.2.1 日记条目结构

每条日记是一个轻量便签，包含：

| 字段 | 说明 |
|------|------|
| 内容 | 简短文字，限制 500 字以内 |
| 图片 | 可选，最多 9 张 |
| 作者 | 自动标记是「他」还是「她」写的 |
| 时间 | 精确到分钟，按时间线排列 |
| 日期归属 | 属于哪一天（用于按日查看） |

#### 3.2.2 时间线展示

默认展示「今天」的时间线，上下滑动查看历史：

```
📅 2026年6月10日（今天）
├── 14:30  🌸 她：今天午饭吃了麻辣烫，好辣好好吃！
│           [图片x2]
│
├── 12:15  🧢 他：中午遛狗的时候发现小区门口开了家新咖啡店
│
├── 09:00  🌸 她：早上好呀～今天天气真不错 ☀️
│
📅 2026年6月9日（昨天）
├── 22:00  🧢 他：晚安，明天见 ❤️
│
├── 18:30  🌸 她：下班啦！今晚想吃火锅
│           [图片x1]
└── ...
```

#### 3.2.3 日历模式

除时间线外，提供日历模式：
- 日历上有小圆点标记有日记的日期
- 有照片的日期用不同颜色 / 图标标记
- 点击日期跳转到那天的日记时间线

#### 3.2.4 日记删除规则

- 发布后的日记，任何一方可发起删除请求
- 需**另一方同意**后才正式删除
- 删除请求超过 **7 天**未确认则自动失效
- 发起方可随时撤回删除请求

### 3.3 打赌系统

#### 3.3.1 打赌生命周期

```
发起 ──► 待同意 ──► 进行中 ──► 待结算 ──► 待兑现 ──► 已完成
```

#### 3.3.2 阶段一：发起赌注

用户创建赌注，填写：

| 字段 | 说明 | 示例 |
|------|------|------|
| 赌什么 | 打赌的内容描述 | 「今天会下雨」 |
| 谁赢了会怎样 | 赢的条件 | 「如果下雨 → 她赢」 |
| 奖励是什么 | 输了要给的奖励 | 「汉堡包」 |
| 截止时间 | 必须设定，精确到时间 | 「今晚 22:00」 |

**奖励内容审核：**

用户输入奖励时，后端检测敏感关键词（车、房、钻石、钻戒、别墅、轿车、豪宅 等）。触发时前端弹出温暖提示：

> 🌟 这个奖励也太重啦！
>
> 打赌是生活里的小情趣，不需要用太贵重的东西来下注哦。
>
> 试试一些温暖又有趣的小奖励吧——一顿亲手做的饭、一次肩膀按摩、一张手写情书、一起看场日落……
>
> 真正珍贵的从来不是价格，而是用心 💕

提示后**仍可提交**，决定权在用户。关键词黑名单存储在数据库，后续可持续补充。

#### 3.3.3 阶段二：对方回应

```
用户A 发起赌注
    │
    │   用户B 收到通知：「对方昵称」想跟你打个赌！
    │
    │        ├─ 接受 ──► 赌注生效，状态变为「进行中」
    │        └─ 拒绝 ──► 赌注取消，记录在「被拒绝的赌注」中
```

#### 3.3.4 阶段三：进行中

- 赌注在首页以卡片形式展示，双方随时可查看
- 倒计时显示剩余时间
- 到达截止时间后，状态自动变为**待结算**

#### 3.3.5 阶段四：结算（判定谁赢）

到期后进入结算阶段，**双方共同确认**结果：

```
赌注到期，状态变为「待结算」
    │
    ├─ 任一方提交结果：「我认为结果是：她赢了 / 他赢了」
    │
    ├─ 另一方确认结果
    │   ├─ 同意 ──► 结果确认，状态变为「待兑现」
    │   └─ 不同意 ──► 进入协商状态
    │       └─ 双方在赌注下方可以发简短消息讨论
    │          直到一方重新提交结果，另一方同意
    │
    └─ 3天双方都没操作 ──► 赌注自动作废
```

#### 3.3.6 阶段五：兑现奖励

```
结果确认后，状态变为「待兑现」
    │
    ├─ 系统每12小时提醒输方一次（如早10点、晚10点）
    │   提醒文案带有温度，不是冷冰冰的催债
    │
    ├─ 输方点击「已兑现奖励」
    │   「我已经给 TA 汉堡包啦！」
    │
    ├─ 赢方确认收到
    │   ├─ 确认 ──► 赌注完成！状态变为「已完成」🎉
    │   └─ 没收到 ──► 回到待兑现，继续提醒
    │
    └─ 多个待兑现赌注合并展示：
        「你欠 TA 3 个奖励：汉堡包🍔、奶茶🧋、电影票🎫」
```

#### 3.3.7 赌局时间线展示

首页以时间线串联所有赌局，按日期分组展示：

```
🎰 赌局时间线

📅 2026年6月10日（今天）
│
├── 14:00  🔥 进行中
│   🌧 她：「今天会下雨」
│   奖励：汉堡包🍔  ·  截止：今晚22:00（还剩3小时）
│
├── 10:30  ⏳ 待结算
│   ⚽ 他：「昨晚比赛曼联赢」
│   奖励：奶茶🧋  ·  已到期，快来确认结果！
│
├── 09:00  💰 待兑现
│   🍰 她：「这周末去吃的那家店会排队」
│   结果：她赢了  ·  奖励：蛋糕🍰
│   [我已兑现]
│
📅 2026年6月8日（前天）
│
├── 20:00  ✅ 已完成
│   🐱 他：「小区那只流浪猫今天会出现」
│   结果：他赢了  ·  奖励：一杯咖啡☕（已兑现 ✓）
│
├── 15:00  ✅ 已完成
│   🎬 她：「新上映的电影评分会超过8分」
│   结果：她赢了  ·  奖励：一起看电影（已兑现 ✓）
│
📅 2026年6月5日
│
└── ...

──────────────────────────

📊 我们的战绩
  她 24 胜  ·  他 23 胜
  兑现率 100% ❤️
  最常赌的奖励：奶茶🧋（8次）
```

**设计要点：**
- 默认展示「今天」，往下滚动加载更多历史
- 待兑现的赌注最醒目，用不同颜色 / 样式高亮
- 底部战绩统计始终可见，作为时间线收尾
- 右下角浮动 `+` 按钮发起新赌注

### 3.4 回忆录

#### 3.4.1 设计思路

解绑后，两个人在一起时的日记不会消失，而是进入加密的「回忆录」模块。这是对过去感情的尊重，也是产品的温度所在。

#### 3.4.2 回忆录结构

```
🔐 回忆录
├── 输入密码解锁
│
├── 📖 回忆一：与「对方昵称」的故事
│   │
│   │   绑定时间：2025.03.15
│   │   解绑时间：2026.06.10
│   │   共同记录：328 条日记
│   │   打赌次数：47 次
│   │
│   ├── 按时间线浏览所有日记
│   ├── 按时间线浏览打赌记录（含结果和兑现状态）
│   └── 按日历模式浏览
│
├── 📖 回忆二：与「另一个昵称」的故事（如果有多段）
│   └── ...
```

#### 3.4.3 密码机制

- **设置时机：** 第一次进入回忆录时，系统提示设置独立回忆密码
- **密码规则：** 4-6 位数字
- **每次打开都要输入：** 保护隐私，即使手机被别人拿到也看不到
- **忘记密码：** 可通过微信实名验证重置

## 五、数据模型概要

### 5.1 核心数据表

| 表名 | 说明 |
|------|------|
| `user` | 用户信息（openid、昵称、头像、角色标签） |
| `couple` | 情侣绑定关系（双方ID、绑定时间、状态） |
| `diary` | 日记条目（内容、图片、作者、时间、所属情侣空间） |
| `diary_delete_request` | 日记删除请求（发起方、确认状态、过期时间） |
| `bet` | 赌注（内容、奖励、截止时间、状态、发起方、结果） |
| `bet_message` | 赌注协商消息（结算讨论时的简短消息） |
| `blacklist` | 拉黑记录（双方ID、拉黑时间、冷却截止时间） |
| `memory` | 回忆录（关联原情侣空间ID、双方ID、绑定/解绑时间） |
| `memory_password` | 回忆录密码（用户ID、密码哈希，独立于情侣空间） |
| `reward_blacklist` | 奖励关键词黑名单（敏感词列表） |
| `notification` | 消息通知（类型、内容、已读状态） |

### 5.2 赌注状态流转

```
pending    →  发起，等待对方同意
rejected   →  对方拒绝（终态）
active     →  对方接受，进行中
expired    →  到期未结算，自动作废（终态）
settling   →  到期，待双方确认结果
redeeming  →  结果已确认，待兑现奖励
completed  →  兑现完成（终态）
```

## 六、非功能性需求

| 项目 | 要求 |
|------|------|
| 响应时间 | 页面加载 < 2s，接口响应 < 500ms |
| 可用性 | 99.5% 以上 |
| 数据安全 | HTTPS 传输加密，密码哈希存储，敏感信息不落日志 |
| 并发 | 初期支持 1000 DAU |
| 存储 | 图片上传到对象存储（OSS/COS），单张限制 5MB |
| 消息推送 | 通过微信订阅消息实现，需用户授权 |
